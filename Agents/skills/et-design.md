# et-design - 文档驱动开发

这个 skill 是所有代码开发任务的入口，强制文档先行、开发过程中实时维护开发文档、开发结束后文档同步。

## 使用场景

- 用户要求实现新功能
- 用户要求修改现有功能
- 用户要求修复 bug
- 用户要求重构代码
- **任何涉及代码编写的开发任务**

## 核心原则

1. **无设计文档 = 不准写代码**：强制门禁，没有对应设计文档必须先完成设计
2. **开工即入计划**：任务若不在当前周计划中，开始制作前必须先补充到计划文档中（自动执行，不需要用户额外确认）
3. **开发过程实时记录**：每完成一个有意义步骤必须更新开发文档
4. **开发结束双更新**：设计文档标记实现状态 + 开发文档归档

## 三层文档体系

| 层级 | 文档类型 | 维护时机 | 存放位置 |
|------|---------|---------|---------|
| 宏观 | 版本/周计划 | 任务增删改时 | `Book/08-版本计划/` |
| 中观 | 设计文档 | 开发前 + 开发后 | `Book/{对应功能目录}/` |
| 微观 | 开发文档 | 开发过程中实时 | `Book/{对应功能目录}/` |

## 开发前门禁流程

```
收到开发任务
    │
    ├─ 第1步：检查计划 ──→ 任务是否在 et-plan 周计划中？
    │   ├─ 否 → 【自动补充】将任务添加到当前活跃周的周计划文档（确定优先级、涉及包、备注），更新版本计划变更记录 → 继续
    │   └─ 是 → 继续
    │
    ├─ 第2步：检查设计文档 ──→ Book/ 下是否有对应设计文档？
    │   ├─ 有文档 → 检查时效性（最近更新时间、是否标注"已过时"）
    │   │   ├─ 文档有效 → 基于文档制定开发计划
    │   │   └─ 文档过时 → 先更新设计文档，再制定开发计划
    │   └─ 无文档 → 撰写设计文档 → 用户确认 → 制定开发计划
    │
    └─ 第3步：创建开发文档 → 开始开发
```

## 开发过程流程

```
开始开发（设计文档已确认）
    │
    ├─ 1. 创建开发文档（基于模板）
    ├─ 2. 将设计文档的"实现步骤"拆解为开发文档的"开发进度"清单
    │
    ├─ 3. 逐个步骤执行：
    │   ├─ 编码实现（调用 et-arch / et-tdd 等 skill）
    │   ├─ 【强制】每完成一个步骤 → 更新开发文档：
    │   │   - 打勾"开发进度"
    │   │   - 追加"变更清单"
    │   │   - 如有决策 → 记录"决策记录"
    │   │   - 如有问题 → 记录"问题日志"
    │   └─ 编译验证（调用 et-build skill）
    │
    ├─ 4. 全部步骤完成 → 运行测试（调用 et-test-run skill）
    │
    └─ 5. 开发结束 → 双更新：
        ├─ 更新开发文档"开发总结"区块
        ├─ 更新设计文档"实现追踪"区块
        └─ 推进 et-plan 中任务状态 → "未回归"
```

## 开发文档实时更新规则

以下情况必须立即更新开发文档，不允许延后：

1. **完成一个开发步骤** → 打勾 + 追加变更清单
2. **做出技术决策**（如：改用其他方案、换接口设计） → 记录决策
3. **遇到并解决问题** → 记录问题日志
4. **新增或修改文件** → 追加变更清单
5. **发现设计与实际不符，修改了设计** → 记录偏差
6. **开发被阻塞** → 记录阻塞原因

## 文档存放规范

### 设计文档命名
- `{功能名}设计文档.md`
- 例：`匹配系统设计文档.md`、`装备选择设计文档.md`

### 开发文档命名
- `{功能名}开发日志.md`
- 例：`匹配系统开发日志.md`、`装备选择开发日志.md`

### 存放目录
- 放在 `Book/` 下对应功能的目录中
- 如果没有对应目录，放在 `Book/08-版本计划/` 下
- 与设计文档放同一目录，方便对照

## 设计文档过时检测

检查以下信号判断设计文档是否过时：

1. 设计文档中涉及的文件已被删除或大幅重构
2. 设计文档中的 Entity/Component 定义与实际代码不符
3. 设计文档中的 Proto 消息已变更
4. 距离最后更新超过 30 天且有代码变更
5. 设计文档顶部未标注"最后更新"时间

如检测到过时，在开始开发前先更新设计文档，标注变更原因。

## 与其他 Skill 的衔接

- **et-plan**：开发前检查任务是否在计划中，开发后推进任务状态
- **et-arch**：编码实现时遵守 ECS 架构规范
- **et-tdd**：TDD 流程中的测试先行
- **et-build**：每个步骤完成后编译验证
- **et-test-run**：开发结束后运行测试，状态推进到"未回归"
