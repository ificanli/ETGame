# 局内局外联动起装技术设计文档

## 1. 文档目标
- 将已确认的“当前携带态 / 仓库 / 商店待购买草稿”模型转成可开发的技术方案。
- 明确包级落点、配置变更、协议扩展、服务端权威流程、客户端 UI 结构与分阶段任务。
- 约束实现边界：本期不做 DB 持久化、不做断线重连、不做物品旋转。

## 2. 修订后的核心模型

## 2.1 三层状态

### A. 当前携带态
当前携带态是服务器权威保存的、玩家准备带进下一局的正式状态，包含：
- 固定槽位：
  - 枪械1
  - 枪械2
  - 护甲
  - 背包
- 背包二维布局
- 安全格二维布局

### B. 仓库
仓库保存当前没有带在身上的物品，第一版仍为：
- `ConfigId -> Count`

### C. 商店待购买草稿
商店待购买草稿只存在于客户端会话内：
- 不立即扣钱
- 不立即进入服务器正式状态
- 点击“起装完成”时统一购买

## 2.2 两类操作

### 即时操作
以下操作每次都发通信，服务端立即生效：
- 仓库 -> 当前携带态
- 当前携带态 -> 仓库
- 当前携带态内部移动（固定槽位 / 背包 / 安全格之间）
- 一键卸下

### 延迟结算操作
以下操作只形成草稿，不立即扣钱：
- 商店 -> 固定槽位
- 商店 -> 背包
- 商店 -> 安全格

点击“起装完成”时，只对这部分草稿统一购买。

## 2.3 回合结束规则

### 撤离成功
- 局内最终带出的物品回写为新的当前携带态。
- 不自动进入仓库。
- Gate 侧 `IsConfirmed` 置为 `false`，要求玩家回到局外重新确认。

### 阵亡失败
- 当前携带态清空为“仅保留安全格内容”。
- 固定槽位、背包本体、普通背包物品全部丢失。
- Gate 侧 `IsConfirmed` 置为 `false`。

## 3. 当前代码基线

### 3.1 现有局外链路
- `cn.etetet.equipment` 已有：
  - `LoadoutComponent`
  - `PlayerStorageComponent`
  - `C2G_GetHeroListHandler`
  - `C2G_ConfirmLoadoutHandler`
  - `LoadoutHelper`
- 当前 `LoadoutComponent` 只适合“确认时整套配置下发”，不适合“当前携带态 + 即时仓库操作”。

### 3.2 现有局内链路
- `cn.etetet.item` 当前背包是线性槽位模型：
  - `ItemComponent.Capacity`
  - `ItemComponent.SlotItems`
  - `Item.SlotIndex`
- `cn.etetet.ecanode` 已有容器系统，可参考其：
  - 容器与背包移动
  - 容器协程锁
  - 容器内 `ConfigId + Count` 的表达
- `EvacuationSettlementHelper` 当前会把撤离物直接写入仓库，这与新需求不符。

### 3.3 当前与新模型的主要冲突
1. 当前系统默认“撤离成功 -> 仓库累积”，新需求是“撤离成功 -> 当前携带态”。
2. 当前系统默认“确认起装时整套结算”，新需求是“仓库即时生效 + 商店草稿延迟购买”。
3. 当前死亡逻辑直接清空局内物品，但不会同步修正 Gate 侧当前携带态。

## 4. 包职责划分

### 4.1 `cn.etetet.item`
负责二维物品容器的通用规则：
- 二维占格
- 多格物品
- 背包尺寸变化
- 背包同步协议

### 4.2 `cn.etetet.equipment`
负责局外正式状态与经济规则：
- 当前携带态
- 仓库
- 财富
- 安全格
- 仓库即时操作
- 商店草稿确认
- 撤离/死亡结果写回当前携带态

### 4.3 `cn.etetet.map`
负责进局时读取当前已确认携带态并创建 Unit。

### 4.4 `cn.etetet.statesync`
负责局外 UI：
- 起装主界面
- 背包配置界面
- 商店分类
- 仓库拖拽
- 安全格显示

### 4.5 `cn.etetet.ecanode`
继续负责撤离结算入口，但不再直接把结果写仓库。

说明：

## 6.3 `PlayerStorageComponent`

- `WarehouseItems`
- `LastEvacuationItems`
- `LastEvacuationWealth`
- `TotalWealth`

说明：
- 仓库仍按 `ConfigId -> Count`
- 当前携带态不放在 `PlayerStorageComponent`，而放在 `LoadoutComponent`

## 6.4 `LoadoutGridItemInfo`
建议新增共享 `struct`：
- `ConfigId`
- `Count`
- `AnchorSlotIndex`

用途：
- 背包布局
- 安全格布局
- 客户端与服务端共享

## 6.5 `ItemComponent`
升级为二维容器，但保留锚点兼容：

新增字段：
- `Width`
- `Height`

保留字段：
- `Capacity`
- `SlotItems`

兼容方案：
- `Capacity = Width * Height`
- `SlotItems` 长度依旧等于 `Capacity`
- 多格物品的每个占用格子都可指向同一个 `Item`
- `Item.SlotIndex` 仍记录锚点索引

## 7. 协议设计

## 7.1 设计原则
- 商店列表不走服务端下发，客户端直接读配置。
- 服务端只负责：
  - 同步正式状态
  - 执行即时操作
  - 在点击“起装完成”时购买商店草稿

## 7.2 `Loadout_C_11100.proto` 扩展

### 新增共享结构
- `LoadoutGridItemData`
  - `ConfigId`
  - `Count`
  - `AnchorSlotIndex`

### 扩展 `G2C_GetHeroList`
新增：
- `CurrentBackpackConfigId`
- `CurrentBagWidth`
- `CurrentBagHeight`
- `SecureWidth`
- `SecureHeight`
- `repeated LoadoutGridItemData CurrentBagItems`
- `repeated LoadoutGridItemData CurrentSecureItems`
- `bool IsConfirmed`

说明：
- 返回的是“当前携带态”
- 不返回商店草稿

### 重写 `C2G_ConfirmLoadout`
保留消息名，重写语义。

它只提交：
- 最终目标快照（正式状态 + 商店草稿放置后的全量结果，不是只提草稿差量）
- 用于服务端计算待购买差量

新增字段建议：
- `MainWeaponConfigId`
- `SubWeaponConfigId`
- `ArmorConfigId`
- `BackpackConfigId`
- `BagWidth`
- `BagHeight`
- `repeated LoadoutGridItemData FinalBagItems`
- `repeated LoadoutGridItemData FinalSecureItems`

说明：
- 客户端必须把“服务器正式当前携带态”完整带回，再叠加本地商店草稿形成最终快照。
- 服务端将“客户端最终目标快照”与“服务器正式当前携带态”做比对
- 服务端需要基于全量快照重新做固定槽位、二维占格、空位占用合法性校验。
- 差异只能是“新增的商店草稿”
- 商店草稿只能落到正式状态中的空位，不能覆盖正式物品。
- 若出现服务端认为应已即时同步却没有同步的删除/位移差异，则拒绝并要求客户端重拉

## 7.3 新增局外即时操作协议
建议新增一组 Gate Session 协议：

### `C2G_LoadoutTakeFromWarehouse`
用途：
- 从仓库拿出物品到固定槽位 / 背包 / 安全格

字段建议：
- `ConfigId`
- `Count`
- `TargetAreaType`
- `TargetSlotType`
- `TargetAnchorSlotIndex`

### `C2G_LoadoutPutToWarehouse`
用途：
- 将当前携带态中的物品放回仓库

字段建议：
- `SourceAreaType`
- `SourceSlotType`
- `SourceAnchorSlotIndex`
- `Count`

### `C2G_LoadoutMoveOwnedItem`
用途：
- 当前携带态内部移动
- 例如：
  - 固定槽位 -> 背包
  - 背包 -> 固定槽位
  - 背包 -> 安全格
  - 安全格 -> 背包

### `C2G_LoadoutOneKeyUnload`
用途：
- 一次性把当前携带态正式内容全部回仓库

### `G2C_LoadoutStateChanged`
用途：
- 服务端推送当前携带态、仓库、确认状态变化

说明：
- 这类操作建议统一做成“成功后推送最新正式状态快照”
- 客户端不要靠本地猜最终结果

`A2Map_ApplyLoadoutRequest` 只在真正进图时调用，不再在确认起装时复用。

消息扩展建议：

- `repeated LoadoutGridItemData BagItems`

补充传：
- `SecureWidth`
- `SecureHeight`
- `repeated LoadoutGridItemData SecureItems`

## 7.5 跑局结果同步协议
现有 `Map2G_EvacuationSettlement` 语义不够用了，建议新增/替换为更明确的消息：

### `Map2G_LoadoutCarryResult`
字段建议：
- `ResultType`：`Evacuated` / `Dead`
- `MainWeaponConfigId`
- `SubWeaponConfigId`
- `ArmorConfigId`
- `BackpackConfigId`
- `BagWidth`
- `BagHeight`
- `repeated LoadoutGridItemData FinalBagItems`

- `ResultType = Dead` 时，`TotalWealthDelta` 按 `0` 处理。

## 8. 服务端流程设计

## 8.1 `C2G_GetHeroList`
职责扩展为：
1. 返回英雄列表
2. 返回仓库
3. 返回财富
4. 返回当前携带态
5. 返回 `IsConfirmed`

## 8.2 仓库即时操作

实现要求：
- 所有修改 `LoadoutComponent` / `PlayerStorageComponent` 的即时操作协议，都要在 Gate 按 `PlayerId` 或 `LoadoutComponent` 维度加协程锁串行执行。
- 串行范围至少覆盖：
  - `C2G_LoadoutTakeFromWarehouse`
  - `C2G_LoadoutPutToWarehouse`
  - `C2G_LoadoutMoveOwnedItem`
  - `C2G_LoadoutOneKeyUnload`
  - `C2G_ConfirmLoadout`

### 从仓库拿出
流程：
1. 校验仓库数量
2. 校验目标位置是否合法
3. 立即扣仓库
4. 立即写入当前携带态
5. `IsConfirmed = false`
6. 推送最新正式状态

### 卸下回仓库
流程：
1. 校验来源位置合法
2. 从当前携带态移除
3. 增加仓库计数
4. `IsConfirmed = false`
5. 推送最新正式状态

### 当前携带态内部移动
流程：
1. 校验来源和目标
2. 校验二维摆放/槽位合法
3. 立即更新当前携带态
4. `IsConfirmed = false`
5. 推送最新正式状态

## 8.3 `C2G_ConfirmLoadout`
重写为“购买商店草稿 + 准备进局”。

### 输入
客户端提交“正式当前携带态 + 商店草稿叠加后的全量目标快照”。

### 服务端前置校验
1. 以服务器正式当前携带态作为基线。
2. 对目标快照重新执行固定槽位规则与二维占格校验。
3. 校验商店草稿只落在正式状态空位：
   - 不允许覆盖正式已有物品
   - 不允许删除正式已有物品
   - 不允许把正式已有物品偷偷改位到未即时同步的位置
4. 若发现上述非法差异，直接拒绝并要求客户端重拉正式状态。

### 服务端处理
1. 取当前服务器正式携带态作为基线。
2. 比对客户端目标快照。
3. 从差异中提取“新增商店草稿”集合。
4. 计算新增商店物品总价。
5. 若财富不足则失败。
6. 若财富足够：
   - 扣财富
   - 将新增商店物品写入正式当前携带态
   - `IsConfirmed = true`
   - `ConfirmedAt = now`

### 失败规则
- 不回滚正式当前携带态
- 不回滚已即时生效的仓库变更
- 只视为本次商店草稿购买失败

## 8.4 进局应用
`C2G_EnterMapHandler` 中：
1. 读取 Gate 侧正式当前携带态
2. 校验 `IsConfirmed == true`
3. 创建 Unit
4. 固定槽位进入 `EquipmentComponent`
5. 背包布局进入 `ItemComponent`
6. 安全格布局进入 Unit 级独立运行时组件，并同步给客户端搜索界面

## 8.5 撤离成功
`EvacuationSettlementHelper` 不再直接写仓库，而是：
1. 采集局内最终固定槽位
2. 采集局内最终背包布局
3. 计算财富收益
4. 发 `Map2G_LoadoutCarryResult(ResultType = Evacuated)`

Gate 侧处理：
1. 用局内最终固定槽位 + 背包布局覆盖当前携带态正式状态
2. 用 Map 侧回传的运行时安全格结果覆盖 Gate 侧安全格正式状态
3. 增加财富
4. `IsConfirmed = false`

## 8.6 阵亡失败
Map 侧：
1. 玩家死亡
2. 发 `Map2G_LoadoutCarryResult(ResultType = Dead)`

Gate 侧处理：
1. 清空正式当前携带态中的：
   - 固定槽位
   - 背包本体
   - 背包布局
2. 使用 Map 侧回传的运行时安全格快照作为新的正式安全格状态
3. `IsConfirmed = false`

说明：
- 这一步必须显式同步 Gate
- 不能只清空 Map 上的 Unit
- Gate 侧在 `ResultType = Dead` 时仍读取 `FinalSecureItems`，只清空非安全格内容。

## 9. 客户端/UI 设计

## 9.1 客户端正式状态与草稿分离
客户端 `Scene.LoadoutComponent` 内部分两块：

### 正式状态
- 服务端推送的当前携带态
- 服务端推送的仓库
- 服务端推送的财富
- `IsConfirmed`

### 草稿状态
- 只记录商店新增草稿
- 不记录仓库即时操作

## 9.2 起装主界面
基于现有 `LobbyPanel` 改造，职责：
1. 展示正式当前携带态
2. 展示正式仓库
3. 展示安全格
4. 支持仓库即时拖入
5. 支持正式内容即时卸下
6. 显示商店草稿叠加预览
7. 起装完成时只结算草稿

## 9.3 背包配置界面
职责：
1. 展示商店分类
2. 允许把商店物品放入背包/安全格草稿
3. 不直接动仓库正式状态
4. 可清空本次商店草稿
5. 放置草稿前先校验目标位置在“正式状态 + 草稿预览”下是否为空位；若正式物品占位则拒绝放置并提示

## 9.4 一键卸下
客户端触发：
- UI 先弹二次确认，确认后再发协议
- 发 `C2G_LoadoutOneKeyUnload`
- 本地清空商店草稿

服务端处理：
- 将正式当前携带态全部回仓库
- 清空正式当前携带态中的固定槽位、背包和安全格
- `IsConfirmed = false`
- 推送最新正式状态

## 10. 关键实现细节

## 10.1 `IsConfirmed` 的新语义
旧语义：
- 仅表示“上一次确认起装成功”

新语义：
- 当前正式携带态已准备好进局

因此以下操作都要使其失效：
- 仓库即时取出
- 卸下回仓库
- 当前携带态内部移动
- 一键卸下
- 成功撤离
- 阵亡失败
- 新增商店草稿

说明：
- 第一版接受“只要正式当前携带态发生变化，包括内部位置调整，也需要重新点击起装完成”的 UX 取舍。
- 后续如果要优化，可再细分“物品组成变化”和“纯排布变化”。

## 10.2 草稿生命周期
- 草稿仅在当前客户端进程内存在。
- 若客户端重启，草稿丢失。
- 正式状态不丢，由服务端重新下发。

## 10.3 二维容器兼容策略
为减少现有代码破坏，仍保留：
- `Capacity`
- `SlotIndex`

## 13. 风险与处理

### 风险 1：当前携带态和仓库同时存在，状态同步复杂
处理：
- 所有正式状态修改都由 Gate 侧权威处理
- 成功后统一下发最新快照

### 风险 2：客户端草稿和正式状态混淆
处理：
- 草稿只保留商店新增内容
- 仓库即时操作绝不进入草稿

### 风险 3：撤离不再直接写仓库，会影响旧测试
处理：
- 更新现有 `Equipment_StorageAfterEvacuation_Test` 语义
- 新增“撤离回当前携带态”专项测试

### 风险 4：死亡后 Gate 状态不更新
处理：
- 新增 `Map2G_LoadoutCarryResult(ResultType = Dead)`
- 由 Gate 显式重置正式当前携带态

### 风险 5：Gate 侧即时操作并发导致状态竞态
处理：
- 所有即时操作与 `C2G_ConfirmLoadout` 统一走 Gate 侧协程锁串行执行
- 协议成功后只以下发的最新正式状态快照为准，客户端不自行推演最终正式结果
