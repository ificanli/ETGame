## 决策记录

### 2026-04-16 - 先从运行时布局切入，最终收口为混合方案

- **背景**：`LobbyPanel` 当前背包/安全箱的格子内容已经是运行时按配置渲染，但外层根节点仍是历史绝对定位。
- **方案**：先沿着运行时布局缓存与重排逻辑落地，再把“安全箱跟随背包向下排布”的静态结构收回 prefab，最终采用 `LoadoutOwnedAreaRoot + VerticalLayoutGroup + LayoutElement` 配合运行时尺寸刷新。
- **原因**：块内尺寸和 chrome 偏移本来就依赖运行时格子数；但块与块之间的纵向结构放回 prefab，更符合 YIUI/Unity UI 的职责分层，也更利于后续维护。
- **替代方案**：继续坚持纯运行时代码重排全部结构。放弃原因是会让静态布局长期依赖脚本维持，可读性和可维护性都更差。

### 2026-04-16 - chrome 相对 `BoardRoot` 缓存，不直接硬编码新坐标

- **背景**：需求要求布局跟随不同背包尺寸变化，但项目根规范又明确禁止继续堆死坐标。
- **方案**：首次进入起装页时读取 `Bg/Title/Hint` 相对 `BoardRoot` 的实际矩形关系，后续只根据新的网格尺寸重建板子和外层块。
- **原因**：这样既能复用现有美术 prefab 的视觉关系，又能避免再写第二套针对不同背包尺寸的分支坐标。
- **替代方案**：直接给背包和安全箱写一组固定偏移常量。放弃原因是会在更换背包尺寸后再次失真，本质上没有解决问题。

### 2026-04-16 - 编译验证被既有 helper 接口缺口阻塞，补兼容方法收口

- **背景**：本轮执行 `dotnet build ET.sln` 时，`MapPoiRuntimeComponentSystem.cs` 调用了不存在的 `FlowParamHelper.GetIntParamOrDefault`，导致整体验证被阻塞。
- **方案**：在 `FlowParamHelper` 中补充 `GetIntParamOrDefault(FlowNodeData, ...)` 和 `GetIntParamOrDefault(List<FlowParam>, ...)` 两个对称接口。
- **原因**：`FlowParamHelper` 已存在 `GetStringParamOrDefault`，补对称 int 版本比改调用方更稳，也更符合工具类现有风格。
- **替代方案**：把调用方全部改回 `TryGetIntParam + 默认值分支`。放弃原因是改动面更散，收益不如在 helper 层补齐兼容口。

## 问题日志

### 2026-04-16 - 当前起装格子会自适应，但外层块不会

- **现象**：`RenderOwnedGridArea` 已按 `BagWidth/BagHeight` 与 `SecureWidth/SecureHeight` 渲染格子和物品，但背包背景、安全箱背景和块间位置仍旧停留在旧 prefab 绝对坐标。
- **原因**：现有代码只处理网格层，不处理 `CurrentBagRoot / SecureBagRoot` 外层布局。
- **解决**：新增专项布局任务，改为在同一刷新链路中同步计算 root 与 board 的实际布局。

### 2026-04-16 - `ModelView` 分析器禁止普通 class 布局缓存

- **现象**：首次编译时，`dotnet build ET.sln` 报 `ET0032`，指出 `LobbyPanelComponent.cs` 中的 `LoadoutOwnedAreaLayoutCache` 不能作为普通 class 放在 `ModelView` 程序集。
- **原因**：ET 分析器要求 `Model/ModelView` 中的非 `Object` 类型不能随意声明普通 class。
- **解决**：把布局缓存改为 `struct`，同时把写入方法切到 `ref` 传递，既满足分析器规则，也保留同样的数据结构。

### 2026-04-16 - 纯运行时纵向排布不够理想

- **现象**：初版实现虽然能在运行时把安全箱顶到背包下方，但块与块之间的排布完全依赖脚本设置 `RectTransform`，不符合当前项目里 prefab 承担静态结构的习惯。
- **原因**：最初为了先把功能闭环，优先选了纯脚本方案，没有把纵向结构同步回 `LobbyPanel.prefab`。
- **解决**：在 prefab 中新增 `LoadoutOwnedAreaRoot`，由 `VerticalLayoutGroup` 负责“背包在上、安全箱在下”，运行时代码只负责尺寸和内部节点刷新。

### 2026-04-16 - 编译验证被 `FlowParamHelper` 缺失接口阻塞

- **现象**：重新执行 `dotnet build ET.sln` 时，编译报错 `FlowParamHelper` 不包含 `GetIntParamOrDefault`，阻塞了本任务的最终验证。
- **原因**：`MapPoiRuntimeComponentSystem` 已经开始使用默认值接口，但 `FlowParamHelper` 里还没有对称的 int 版本实现。
- **解决**：补齐 helper 兼容方法后再次执行 `dotnet build ET.sln`，最终 0 warning / 0 error 通过。
