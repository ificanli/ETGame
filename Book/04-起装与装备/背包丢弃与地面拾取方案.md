# 背包丢弃与地面拾取方案

## 1. 文档目标

- 补齐局内背包物品“丢到地上”和“从地上拾取”的完整闭环。
- 优先复用现有 `ECA + Container + SearchPanel` 链路，避免新起一套地面物品系统。
- 在不破坏当前包边界的前提下，给出可分阶段落地的实现方案。

## 2. 当前现状

### 2.1 已确认存在的能力

1. `cn.etetet.item` 已有 `C2M_DiscardItem` 协议和服务端处理器。
2. 当前 `C2M_DiscardItem` 的行为只是从背包中扣除或删除物品，不会生成地上可拾取物。
3. `ecanode` 已有容器交互全链路：
   - `OpenContainerUI`
   - `ContainerTakeItem`
   - `ContainerTakeAll`
   - `ContainerMoveItem`
4. `ContainerOutputMode` 已经有 `GroundDrop` 模式。
5. 玩家尸体盒已经验证过“把背包物品转成世界可交互容器内容”这条路线是可行的。
6. 动态创建承载点位的 `Unit` 也已有现成做法，测试代码里已经在用。

### 2.2 当前缺口

1. 背包物品现在“能删不能落地”。
2. 玩家无法通过现有玩法闭环捡起地上的丢弃物。
3. `GroundDrop` 目前更多只是一个输出模式标记，没有补成完整的动态地面掉落玩法。
4. `SearchPanel` 当前没有明确的“丢弃到地面”入口。

### 2.3 当前数据模型约束

当前 `Item` 实体只包含这些核心字段：

- `ConfigId`
- `Count`
- `SlotIndex`
- `GridWidth`
- `GridHeight`

当前 `ContainerComponent` 里的容器内容也是按 `ConfigId + Count` 组织。

这意味着：

1. 以当前项目现状看，一期方案直接复用容器内容模型是成立的。
2. 如果未来 `Item` 增加更复杂的实例态数据，地面掉落容器结构也要同步升级，不能再只存 `ConfigId + Count`。

## 3. 推荐方案

### 3.1 总体方案

推荐做法：

**不要新建一套“地面物品系统”，而是复用现有 `Unit + ECAPointComponent + ContainerComponent`，把玩家丢弃出来的物品做成“动态地面容器点”。**

具体表现为：

1. 玩家在背包里执行丢弃。
2. 服务端验证后，在同一个请求执行流里完成掉落点创建与背包扣除。
3. 服务端在玩家附近动态生成一个独立 `Unit`。
4. 该 `Unit` 挂：
   - `ECAPointComponent`
   - `ContainerComponent`
5. 容器内容写入刚刚丢弃出来的物品。
6. `container.OutputMode = GroundDrop`。
7. 玩家靠近后，继续走现有交互按钮和 `SearchPanel` 容器拾取链路。
8. 物品被拿空后，自动销毁这个动态掉落点。

### 3.2 为什么推荐这条路

1. 服务端已有容器并发控制和拾取逻辑，不需要重写冲突处理。
2. 客户端已有 `SearchPanel`，一期不需要新做整套拾取 UI。
3. 尸体盒已经证明“背包物品转世界容器内容”是通的。
4. 修改面更集中，返工最少。
5. 后续如果要做“地面快速拾取”“掉落特效”，也可以继续在这个基础上迭代。

### 3.3 不推荐的方案

不推荐直接新建一套独立“地面物品实体 + 新协议 + 新拾取 UI + 新并发逻辑”，原因是：

1. 会和现有容器系统能力重复。
2. 会新增一套状态同步和边界校验逻辑。
3. 会让后续尸体盒、普通容器、地面掉落三套玩法分叉越来越明显。

### 3.4 掉落位置规则

“玩家附近”不能只停留在口头描述，一期就应该给出确定规则。

建议规则：

1. 默认掉落位置为“玩家当前位置 + 朝向前方固定距离”。
2. 固定距离不要硬编码在逻辑里，走统一常量或配置，例如 `DropForwardDistance`。
3. 先对候选位置做一次可行走点/有效落点采样。
4. 如果采样失败，则回退到玩家脚下的有效位置。

这样可以避免：

1. 掉落物刷进墙里。
2. 不同开发者各自写一套“附近”的理解。
3. 后续调参时还要改业务代码。

## 4. 包职责建议

### 4.1 `cn.etetet.item`

职责建议：

1. 继续负责 `C2M_DiscardItem` 的参数校验。
2. 继续负责从背包中扣除/拆分物品。
3. 在同一个请求执行流里，发起可等待的掉落创建请求或事件上下文。

不建议：

1. 不建议由 `item` 包直接创建地图里的掉落点。
2. 不建议让 `item` 包直接依赖 `eca/map/statesync` 的世界物体逻辑。

原因：

`cn.etetet.item` 的边界应该继续保持在“通用物品/背包能力”，不要把地图玩法逻辑直接塞进来。

补充说明：

1. 不建议继续沿用 fire-and-forget 的 `EventSystem.Publish()` 做“扣物品 -> 创建掉落点”闭环。
2. 如果用事件解耦，应该使用可等待的链路，例如 `PublishAsync`，并让上下文携带结果码或创建结果。
3. 更理想的目标是：在同一个请求执行流里完成“校验、创建掉落点、正式扣物品、返回结果”，而不是中间丢一个异步事件后继续往下走。

### 4.2 `cn.etetet.eca`

职责建议：

1. 继续提供 `ECAPointComponent` 生命周期与范围判定能力。
2. 继续维护 `ECAManagerComponent` 的点位注册与回收。

本次需求不建议在这个包里加新协议。

### 4.3 `cn.etetet.ecanode`

职责建议：

1. 继续承载 `ContainerComponent` 数据结构。
2. 提供“动态地面掉落容器”的通用 Helper。
3. 负责容器拿空后的状态更新和清理。

建议新增或补齐的通用能力：

1. 创建地面掉落容器点。
2. 将物品写入容器内容。
3. 地面掉落容器为空时自动销毁。
4. 地面掉落容器超时未拾取时自动销毁。

建议顺手补充的低成本字段：

1. `CreatorPlayerId`
2. `CreateTime`

这两个字段一期成本很低，但二期做“同位置合并”“归属保护”“按创建时间淘汰最旧掉落点”时都会直接用到。

### 4.4 `cn.etetet.statesync`

职责建议：

1. 作为玩法胶水层，处理可等待的掉落创建请求或事件上下文。
2. 在地图场景里生成动态掉落点。
3. 处理客户端 `SearchPanel` 的丢弃入口。
4. 后续承接掉落特效、拾取特效、快速拾取等表现逻辑。

这样能避免让 `item` 包直接越界到地图玩法层。

## 5. 一期落地范围

一期目标只做最小闭环，不追求最终表现。

### 5.1 玩家体验

1. 玩家在背包里点击丢弃按钮，或拖到明确的“丢弃区”。
2. 物品从背包中移除。
3. 玩家脚边生成一个可交互掉落点。
4. 玩家靠近后可以像搜容器一样打开并拿回。
5. 掉落被拿空后从地图中消失。

补充限制：

1. 一期不做归属保护，所有玩家都可以拾取地面掉落物。
2. 这条限制需要在需求和验收阶段就明确，不要等实现后再讨论。

### 5.2 服务端建议流程

1. 客户端继续发送现有 `C2M_DiscardItem`。
2. 服务端校验：
   - 物品存在
   - 数量合法
   - 当前场景允许丢弃
   - 丢弃冷却是否通过
   - 玩家当前地面掉落点数量是否超限
   - 候选掉落位置是否可用
3. 计算掉落位置：
   - 玩家前方固定距离
   - 做有效落点采样
   - 失败回退到玩家脚下
4. 在同一个请求执行流里完成掉落创建，不建议使用 fire-and-forget 事件。
5. 如果仍然使用事件解耦，则必须使用可等待的事件链路，例如 `PublishAsync`。
6. 掉落创建成功后，再正式从背包中扣除物品。
7. 创建动态掉落 `Unit`。
8. 建议优先复用 `UnitFactory.Create` 或等价的标准建单位链路；如果不用，则必须显式补齐 AOI 相关组件。
9. 给该 `Unit` 挂 `ECAPointComponent + ContainerComponent`。
10. `OutputMode` 设为 `GroundDrop`。
11. 容器内写入对应物品。
12. 注册到 `ECAManagerComponent`。
13. 确保掉落 `Unit` 进入 AOI，让附近玩家能看到并交互。

注意：

1. 当前项目里 AOI 一般是通过给 `Unit` 挂 `AOIEntity` 后自动进入 `AOIManager`，不是一句抽象的“注册 AOI”就结束。
2. 如果实现时绕开了标准建单位链路，这一步很容易漏。

### 5.3 客户端建议流程

1. `SearchPanel` 增加明确的丢弃入口。
2. 一期建议优先做“按钮丢弃”或“拖到专用丢弃区”。
3. 不建议一期做“拖出面板外即丢弃”，误触成本太高。
4. 地面拾取继续复用当前 `SearchPanel`。
5. 一期地面掉落容器复用 `SearchPanel` 的 `ContainerSearch` 模式。
6. 与《搜索界面三模式需求与方案说明》保持一致，二期再考虑 `GroundDrop` 专属表现。

### 5.4 动态掉落点建议行为

1. 点类型继续用 `Container`。
2. 交互按钮可直接复用当前搜索/拾取按钮链路。
3. 可先不区分“搜索容器”和“地面掉落”的 UI 结构。
4. 先保证玩法闭环，再考虑做 `GroundDrop` 专属表现。

### 5.5 一期拾取粒度

当前容器协议和实现只支持“按槽整堆拿取”，不支持同一槽位拆分数量拾取。

所以一期建议明确：

1. 地面掉落沿用当前容器能力，整堆拿取。
2. 一期不补“拿 50 里的 30”这种部分拾取。
3. 如果后续要支持部分拾取，需要单独扩展：
   - 协议
   - 服务端容器扣减逻辑
   - 客户端交互 UI

不要把这部分误判成“现成系统已经支持”。

## 6. 二期优化方向

一期闭环之后，再做这些增强更稳：

1. 地面掉落的 3D 模型或特效表现。
2. `GroundDrop` 模式下的专用 UI 样式。
3. 单个地面物品直接拾取，不再打开完整 `SearchPanel`。
4. 自动拾取或按品质筛选拾取。
5. 同位置掉落合并。
6. 丢弃物的短暂归属保护或防抢规则。

## 7. 关键风险与注意事项

### 7.1 包边界风险

最大风险不是逻辑写不出来，而是把职责写乱。

建议明确：

1. `item` 只管背包和丢弃结果。
2. 地图里的掉落点生成放到更高层玩法包。

### 7.2 数据模型风险

当前容器只保存 `ConfigId + Count`。

所以一期方案默认前提是：

1. 当前掉落物不需要复杂实例态。
2. 丢到地上再捡起，本质上允许重新生成背包里的 `Item` 实体。

如果后续要支持带实例态的装备、耐久、词条、绑定信息，则必须扩容容器数据结构。

### 7.3 地图清理风险

动态掉落点如果只创建不清理，地图里会越积越多。

所以一期至少要补 2 条清理规则：

1. 容器拿空立即销毁。
2. 超时自动销毁。

注意：超时时长不要硬编码，应该走配置或统一常量。

### 7.4 反刷与数量上限风险

如果不加限制，玩家可以在短时间内连续丢弃，快速创建大量掉落 `Unit`，给服务端、AOI 和客户端同步都带来压力。

一期建议至少补齐：

1. 丢弃冷却时间。
2. 单玩家同时存在的地面掉落点上限。
3. 超上限时优先淘汰最早创建的掉落点。
4. 如有需要，再加单区域总量上限。

注意：

1. 冷却、上限、淘汰策略都不应直接写死在业务逻辑里。
2. 建议走统一常量或配置。

### 7.5 一期归属规则说明

一期默认规则是：

1. 地面掉落物创建后，所有玩家都可见。
2. 地面掉落物创建后，所有玩家都可拾取。

这不是遗漏，而是一期范围内的明确取舍。

## 8. 验收点

一期完成后，至少要满足这些验收点：

1. 背包物品可以主动丢到地上。
2. 丢弃后背包数据立即正确同步。
3. 地上会生成可交互掉落点。
4. 玩家靠近后可以打开并拾取。
5. 拾取后物品能正确回到背包。
6. 多人同时操作同一个掉落点时，拾取结果保持服务端权威。
7. 掉落点拿空后会自动清理。
8. 超时未拾取的掉落点会自动清理。
9. 一期为整堆拾取，不支持部分拆堆拾取。
10. 一期无归属保护，其他玩家可正常拾取。

## 9. 最终建议

最终建议按下面顺序推进：

1. 先做“一期最小闭环”：丢弃生成动态地面容器点，拾取继续走现有容器链路。
2. 再做“二期表现优化”：地面掉落特效、快速拾取、专用 UI。

这个方向的核心原则是：

**复用现有容器体系做地面掉落，而不是再造一套平行系统。**
