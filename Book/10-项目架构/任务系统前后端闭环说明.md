# 任务系统前后端闭环说明

**关联模块**：`cn.etetet.quest`、`cn.etetet.map`  
**关联文档**：[任务系统现状.md](任务系统现状.md)  
**目的**：补齐任务系统从协议到客户端表现的真实链路，明确现在闭环到哪一步、断在哪一步。  
**说明**：本文只记录当前代码中的真实实现，不补未来设计。

## 1. 服务端当前已接通的部分

### 1.1 接取任务

入口：`C2M_AcceptQuestHandler`

当前服务端会依次做这些事：

1. 读取 `QuestConfig`。
2. 校验接任务 NPC 是否存在。
3. 校验玩家与 NPC 距离是否小于 `10f`。
4. 校验任务是否已接取。
5. 调用 `QuestHelper.CanAcceptQuest` 防止非法请求。
6. 通过 `QuestHelper.AddQuest(unit, request.QuestId)` 创建任务实体。

### 1.2 提交任务

入口：`C2M_SubmitQuestHandler`

当前服务端会：

1. 从 `QuestComponent` 取出任务实体。
2. 校验提交 NPC 是否存在。
3. 校验玩家与 NPC 距离是否小于 `10f`。
4. 调用 `quest.CanSubmit()` 校验是否满足完成条件。
5. 通过 `QuestHelper.SubmitQuest(unit, quest.Id)` 完成提交。

### 1.3 同步任务数据

入口：`C2M_SyncQuestDataHandler`

当前服务端会遍历 `QuestComponent.Children`，把每个任务和子目标写进 `M2C_SyncQuestData.QuestList`。  
但这个实现目前只明确填写了：

- `QuestId`
- `Objectives[].QuestObjectiveId`
- `Objectives[].Count`

下面这些字段在当前代码里没有回填：

- `QuestInfo.Status`
- `QuestInfo.AcceptTime`
- `QuestInfo.CompleteTime`

因此客户端即使收到了同步消息，也只能拿到“任务 ID + 目标计数”的骨架数据。

### 1.4 查询 NPC 可接任务

入口：`C2M_QueryAvailableQuestsHandler`

当前实现只做了两步：

1. 校验 `NPCId` 非 0。
2. 校验该 NPC 在当前地图中存在。

之后就直接结束，没有真正把“可接任务列表”写回响应体，所以这条 RPC 目前还停在骨架阶段。

## 2. 客户端当前已接通的部分

### 2.1 场景初始化

入口：`AfterCreateCurrentScene_AddQuestComponent`

- 当前场景创建后，会直接向场景挂一个 `QuestComponent`。
- 这一步只保证客户端有任务组件容器，不代表已经拿到服务端数据。

### 2.2 登录后初始化

入口：`LoginFinish_InitQuestData`

看起来这里应该在登录完成后主动同步任务数据，但 `RequestSyncQuestData` 里的真正发包代码仍是注释掉的 TODO。  
也就是说：

- 会打印“请求同步任务数据”的日志。
- 实际不会发送 `C2M_SyncQuestData`。

这条“登录后自动同步任务”的链路当前并没有真正跑起来。

### 2.3 收到同步消息后的客户端重建

入口：`M2C_SyncQuestDataHandler`

如果客户端真的收到了 `M2C_SyncQuestData`，当前会：

1. 新建/追加 `QuestComponent`。
2. 按 `QuestInfo.QuestId` 重建 `Quest` 子实体。
3. 按 `QuestObjectiveInfo.QuestObjectiveId` 重建 `QuestObjective` 子实体。
4. 发布 `QuestDataSyncedEvent`。

但因为服务端当前没有填 `Status/AcceptTime/CompleteTime`，这些字段会落成默认值。

### 2.4 任务进度更新

入口：`M2C_UpdateQuestObjectiveHandler`

这个 Handler 当前只做了一件事：

- 打日志。

它没有真正把服务器下发的目标进度更新回 `QuestComponent`，也没有更新 UI 或通知层。

### 2.5 点击 NPC

入口：`UnitClickHelper.Click`

当前点击 NPC 后，如果服务端返回 `response.questInfo`，客户端已经能识别“这个响应里带了任务信息”，但“显示任务界面”的分支还是空的。

### 2.6 NPC 任务交互骨架

`QuestNPCInteractionEvent` 目前只有骨架：

- `CheckAvailableQuests` 是 TODO
- `CheckSubmittableQuests` 只拿到了 `GetSubmittableQuests()`，还没按 NPC 配置过滤
- `ShowAvailableQuestsUI` / `ShowSubmittableQuestsUI` 都只是日志

## 3. 当前真实闭环判断

| 链路 | 当前状态 | 断点 |
|---|---|---|
| 服务端接取任务 | 基本可用 | 客户端缺少对应 UI 闭环 |
| 服务端提交任务 | 基本可用 | 客户端缺少完整提交流程呈现 |
| 登录后自动同步 | 未闭环 | `LoginFinish_InitQuestData` 没有真实发包 |
| 手动同步后本地重建 | 部分可用 | 服务端没回填 `Status/AcceptTime/CompleteTime` |
| NPC 可接任务查询 | 未闭环 | `C2M_QueryAvailableQuestsHandler` 没有写响应内容 |
| 任务目标进度提示 | 未闭环 | `M2C_UpdateQuestObjectiveHandler` 只打日志 |
| 点击 NPC 弹任务 UI | 未闭环 | `UnitClickHelper` 没有实际打开界面 |

## 4. 对任务 4 的文档结论

任务系统现状文档已经说明了“服务端骨架有了、客户端主链路未闭环”；本文补的是更细一级的断点定位：

1. 服务端接取/提交并不是完全没做，而是已经有 RPC 入口和基础校验。
2. 真正缺的不是单个类名，而是“登录同步、NPC 查询、进度推送、UI 呈现”整段客户端闭环。
3. 因此当前任务系统应继续被描述为“服务端骨架已具备，前后端闭环未完成”，而不是“任务系统已完整可用”。
