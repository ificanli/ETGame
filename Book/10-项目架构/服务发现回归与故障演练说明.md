# 服务发现回归与故障演练说明

**关联模块**：`cn.etetet.servicediscovery`  
**关联文档**：[服务发现系统现状.md](服务发现系统现状.md)  
**目的**：补齐服务发现模块的回归检查项与故障演练步骤，说明当前代码下“注册是否成功、缓存是否更新、服务异常退出后订阅侧如何感知”。  
**说明**：本文基于当前代码做静态演练说明，不代表已经做过线上实战演练。

## 1. 当前真实链路

### 1.1 服务注册

`ServiceDiscoveryProxy.Awake` 会先通过 `StartSceneConfigCategory.Instance.GetBySceneName(nameof(SceneType.ServiceDiscovery))` 找到服务发现场景地址。  
`RegisterToServiceDiscovery` 注册时会写入以下最小信息：

- `SceneName`
- `ActorId`
- `Metadata.SceneType`
- `Metadata.Zone`
- 调用方额外传入的元数据

注册成功后，会启动 `HeartbeatInterval = 2000ms` 的重复心跳定时器。

### 1.2 订阅与本地缓存

- `SubscribeServiceChange(filterName, filterMeta)` 负责向服务发现服务订阅变更。
- `OnServiceChangeNotification` 收到新增/删除通知后，会更新本地：
  - `SceneNameServices`
  - `ServicesIndexs`
- 更新完后会发布：
  - `OnServiceChangeAddService`
  - `OnServiceChangeRemoveService`

### 1.3 查询入口

当前主要查询接口有 3 个：

- `GetBySceneType(sceneType)`
- `GetBySceneTypeAndZone(sceneType, zone)`
- `GetServiceInfoByFilter(filterMetadata)`

### 1.4 正常退出

`DestroyAsync` 的顺序是：

1. `UnsubscribeServiceChange`
2. `UnregisterFromServiceDiscovery`

也就是说，优雅退出路径下会先撤销订阅，再主动注销。

## 2. 回归检查清单

### 2.1 注册回归

1. 启动一个带 `ServiceDiscoveryProxy` 的场景实例。
2. 确认该实例执行了 `RegisterToServiceDiscovery`。
3. 重点检查注册请求里是否总是带上：
   - `SceneType`
   - `Zone`
4. 如果本轮改动涉及自定义元数据，确认查询端的过滤条件与注册端字段名完全一致。

### 2.2 查询回归

1. 同一 `SceneType` 启动多个实例时，`GetBySceneType` 应能返回完整列表。
2. 不同 `Zone` 混合存在时，`GetBySceneTypeAndZone` 应只命中目标区服。
3. 如果查询结果异常，先看 `ServicesIndexs` 是否已建立对应索引键，再看通知是否真的进入了 `OnServiceChangeNotification`。

### 2.3 缓存更新回归

1. 新实例注册后，订阅侧应收到新增通知并更新 `SceneNameServices`。
2. 实例下线后，订阅侧应收到删除通知并从本地缓存中移除。
3. 如果业务层拿到的是旧 `SceneName` 或已失效 `ActorId`，优先排查本地缓存是否没刷新，而不是先怀疑调用方逻辑。

## 3. 基于当前代码的故障演练步骤

## 3.1 场景实例异常退出

**目标**：验证订阅侧最终不再把故障实例当成可用服务。  
**建议步骤**：

1. 先启动一个服务实例 A，并让消费方订阅它。
2. 再启动第二个同类服务实例 B，确认消费方本地缓存里已有 A/B 两个实例。
3. 人为关闭 A 所在进程或打断其 Fiber，让它走非正常退出路径。
4. 观察消费方后续是否还能收到该实例的删除通知，以及本地查询是否还会返回 A。

**当前代码边界**：

- 代理侧只负责“收到删除通知后更新本地缓存”。
- 如果是异常退出，最终能否收到删除通知，取决于服务发现服务端对心跳超时/失联实例的处理，而不是代理侧自己重试。

## 3.2 服务发现服务不可达

**目标**：确认当前系统在注册、心跳、订阅阶段的真实退化方式。  
**建议步骤**：

1. 在业务场景启动前，让 `SceneType.ServiceDiscovery` 不可达，或阻断到该服务的消息链路。
2. 观察 `RegisterToServiceDiscovery` 是否报错。
3. 再让已注册实例运行过程中失去到服务发现服务的连接，观察后续 `SendHeartbeat` 是否报错。

**当前代码边界**：

- `RegisterToServiceDiscovery` 在失败时只记录错误日志，不会自动退避重试。
- `SendHeartbeat` 也没有内建的恢复策略。
- 因此当前模块更像“基础设施薄代理”，不是“带自愈能力的服务注册中心客户端”。

## 3.3 订阅过滤条件写错

**目标**：区分“服务没注册成功”和“订阅条件本身写错”两类问题。  
**建议步骤**：

1. 用正确的 `SceneType/Zone` 完成注册。
2. 让消费方刻意用错误的过滤条件订阅或查询。
3. 如果注册成功但订阅结果为空，优先比对：
   - 元数据键名是否完全一致。
   - `Zone` 是否被字符串化后再参与过滤。
   - 查询端是否真的使用了 `GetBySceneTypeAndZone` 而不是更宽/更窄的过滤器。

## 4. 当前已知空缺

1. 没有统一的回归脚本或控制台命令，本轮仍以静态步骤说明为主。
2. 没有自动重试、退避、断线恢复或健康状态分级。
3. 代理层没有“订阅已过期/缓存已陈旧”的显式标记，业务层只能依赖通知和查询结果判断。

## 5. 本轮结论

服务发现模块的“注册、心跳、订阅、查询、退出”主链路已经可描述清楚；本轮补的是运维/回归维度说明，而不是新增实现。后续如果继续演进，可再追加自动化演练脚本或健康检查面板。
