# 9.1 项目模块化架构说明

更新时间：2026-03-02 15:49:55

## 1. 文档目标

本文基于项目当前代码结构自动扫描生成，目标是帮助你：
- 先理解再修改：明确每一层和每个包的职责边界。
- 快速定位改动落点：按 Package -> Scripts程序集 -> 具体System/Entity 找到入口。
- 降低改造风险：提前识别依赖链、同层访问和元数据异常。

## 2. 项目总体架构

### 2.1 顶层目录职责

- Assets/：Unity资源与场景。
- Packages/：模块化包（主要业务与框架代码）。
- Scripts/：项目级脚本与工具。
- Bin/：工具与运行产物（如 ET.App.dll、导表导协议工具）。
- Luban/：配置表工作区。
- Proto/：协议定义。
- Logs/：运行与测试日志。
- Book/：文档。

### 2.2 ET程序集层次（按et-arch规范）

```text
ET.HotfixView -> ET.Hotfix -> ET.ModelView -> ET.Model -> ET.Loader -> ET.Core
```

### 2.3 ECS职责分离（修改时必须遵守）

- Entity/Component：只放数据，不写业务逻辑。
- System：写逻辑，且是静态扩展方法。
- await 后访问Entity：必须通过 EntityRef<T> 重新获取。

## 8. 学习与改造建议（按风险从低到高）

1. 先读 Level 1 + Level 2：理解公共能力、启动链、资源链。
2. 再读目标业务层（通常 Level 5）：从 Model 的Entity入手，再看 Hotfix 的System。
3. 涉及UI时，再进入 ModelView/HotfixView，避免把表现逻辑塞进Model层。
4. 改依赖前先检查 package.json 递归依赖和层级规则，再改 packagegit.json 的脚本引用。
5. 每轮修改后统一用 dotnet build ET.sln 验证分析器与分层约束。
