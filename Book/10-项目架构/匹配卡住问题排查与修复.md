# 匹配卡住问题排查与修复设计文档

**创建时间**：2026-04-13
**最后更新**：2026-04-13
**状态**：已完成
**关联任务**：M0.2-W3 #28
**涉及包**：cn.etetet.match, cn.etetet.map, cn.etetet.actorlocation, cn.etetet.login

## 需求概述

当前现场问题已经从此前的“匹配成功后等待窗残留、进图后肉鸽牌点不了”切换为新的阻塞：

1. 点击匹配后，客户端能收到匹配成功；
2. 但后续长时间停留在匹配态，等不到 `Wait_SceneChangeFinish`；
3. 用户表现为“点击匹配后卡住，每把都卡”。

本次修复目标不是继续处理大厅 UI 生命周期，而是恢复匹配成功后的稳定进图能力。

## 现状复核

以下两类旧问题已经在当前代码中落地，不能再作为本次卡住的主因：

1. `BUG-012` 中的 `LobbyPanel/MatchView` 残留关闭链路已经修过；
2. `Map2G_HomeStorageSummaryRequest / OperateRequest` 的 Gate handler 已改成 `MessageLocationHandler`。

因此，当前“匹配卡住”需要作为独立任务继续处理。

## 根因判断

### 1. 当前真实卡点在匹配成功后的服务端转图

匹配成功后，Gate 侧 `Match2G_MatchSuccessHandler` 会：

1. 给客户端发送 `G2C_MatchSuccess`；
2. 再通过 `LocationType.Unit` 给当前玩家 Unit 发送 `MapManager2Map_NotifyPlayerTransferRequest`；
3. 由当前所在地图上的玩家 Unit 自己执行 `TransferHelper.TransferLock(...)` 进入目标副本。

客户端一直等不到 `Wait_SceneChangeFinish`，说明问题发生在第 2 步或第 3 步，而不是等待窗关闭逻辑。

### 2. 更前置的卡点是 GateMap -> Home 传送期间的 HomeStorage RPC 超时

最新现场日志显示，在玩家登录进 `Home` 的首段传送里，`M2M_UnitTransferRequestHandler -> HomeEnterHelper.OnEnterHome -> HomeStorageGateHelper.RefreshSummary` 会向 Gate 发送 `Map2G_HomeStorageSummaryRequest`，但该 RPC 最终超时：

1. `HomeStorageGateHelper` 使用 `UnitGateInfoComponent.ActorId` 发起请求；
2. 该 `ActorId` 实际上绑定的是 `PlayerSessionComponent`，其 mailbox 类型为 `GateSession`；
3. `GateSession` mailbox 不会把消息分发给 Gate 侧 `MessageHandler<Player, ...>` / `MessageLocationHandler<Player, ...>`，而是只会把消息原样转发给客户端 Session；
4. 结果是 `Map2G_HomeStorageSummaryRequest` 没有任何服务端 handler reply，`GateMap -> Home` 传送在 `HomeEnterHelper` 内部超时；
5. 玩家后续匹配时，Gate 再去找当前 Unit 转图，自然也会因为前一次 Home 进图未完成而继续卡住。

因此，当前链路里需要区分两类 Gate actor：

1. `ActorId`：继续用于 `Map -> Gate -> Client` 的 `M2C_*` 转发；
2. `PlayerActorId`：专门用于 `Map -> Gate Player` 的服务端消息和 RPC。

### 3. Location 仍可能残留失效的 Unit actor

`MessageLocationSenderOneType.Call(... ILocationRequest)` 每次都会重新从 `Location` 获取当前 Unit actor。

如果 `LocationType.Unit` 保存的是旧 actor：

1. Gate 会把转图请求打到已失效的 Unit actor；
2. 服务端返回 `ERR_NotFoundActor`；
3. 客户端永远等不到真正的切场消息。

### 4. 当前工程缺少“玩家 Unit 被直接移除时”的 location 清理

正常跨图时，`TransferHelper` 通过 `Lock/UnLock` 维护 `LocationType.Unit`。

但 `G2Map_LogoutHandler` 这类“直接移除玩家 Unit”的路径里，没有同步执行 `Remove(LocationType.Unit, unit.Id)`。这会让旧 actor 有机会残留在 location 中，后续再被 Gate 命中。

### 5. 仅补 location 清理还不够，需要匹配成功转图兜底

即使补上 `RemoveLocation`，历史脏数据或未来其他异常转图仍可能再次把 location 留成失效 actor。

如果只做根因清理，不做匹配成功时的兜底，用户仍可能继续遇到“匹配成功但不进图”。

## 技术方案

### 整体思路

采用“两层修复”：

1. **Gate actor 纠正**：给 `Player` 本体增加 mailbox，`UnitGateInfoComponent` 新增 `PlayerActorId`，把 `Map2G_HomeStorage*`、`Map2G_LoadoutCarryResult` 等真正面向 Gate `Player` 的服务端消息切到 `PlayerActorId`；
2. **根因收口**：在玩家 Unit 的直接退出路径补 `LocationType.Unit` 清理，减少 stale actor 再出现；
3. **止血兜底**：匹配成功后若按当前 location 转图失败，则在 Gate 上临时重建一份 GateMap Unit，并直接执行标准 `TransferHelper.TransferLock(...)` 进入目标地图。

这样可以同时满足：

1. 立即恢复“匹配成功后能进图”；
2. 不继续依赖一条已经被脏 location 卡死的旧链路；
3. 不引入新的怪异专用转图协议，仍然复用现有标准 Transfer；
4. 不破坏现有 `Map -> Gate -> Client` 的消息转发口径。

### 架构约束

1. 不新开专用协议，继续复用现有 `TransferHelper`；
2. GateMap 兜底必须复用正式玩家 Unit 创建流程，避免再造一套测试专用假链路；
3. 所有 `await` 后访问 `Player / Unit / GateMapComponent` 时，必须通过 `EntityRef` 重新获取；
4. 不回退已有 `BUG-012` 修复，只补本次匹配转图问题。

## 实现步骤

1. 补计划与设计/开发文档，把本问题从旧 `Home` 临时止血任务中独立出来；
2. 给 `Player` 本体补 mailbox，并让 `UnitGateInfoComponent` 同时记录客户端转发 actor 与 Gate Player actor；
3. 抽离 GateMap 临时建 Unit + 应用起装 + 执行 Transfer 的公共 helper；
4. `C2G_EnterMapHandler` 改为复用该 helper，避免登录进 Home 与匹配兜底分叉；
5. `HomeStorage` / `LoadoutCarryResult` 等 Map->Gate 服务端消息改走 `PlayerActorId`；
6. `Match2G_MatchSuccessHandler` 在 location 转图失败后，走 GateMap 兜底转图；
7. `G2Map_LogoutHandler` 补 `LocationType.Unit` 清理；
8. 执行 `dotnet build ET.sln`，回写文档与计划状态。
