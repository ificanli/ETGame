# 搜索界面三模式方案 — 审阅建议

## 1. 格式问题

第 60 行 `## 4. 推荐方案` 和第 63 行 `## 4.1 总体方案` 层级相同，4.1 应改为 `###`。

## 2. 建议去掉 `LeftPanelKind` / `RightPanelKind`

三种模式下左右区域内容是确定性的：

- 容器搜索 = 左容器、右背包
- 背包查看 = 只有背包
- 尸体搜索 = 左尸体、右背包

从 `OpenMode` 就能推导，单独存这两个字段会引入"模式和面板类型不一致"的冗余状态。建议去掉，直接在 `RenderLeftAreaByMode` / `RenderRightAreaByMode` 里根据 `OpenMode` 决定。

除非预期未来会有任意左右组合的需求，否则没有必要。

## 3. 补充关闭触发条件的差异

三种模式的关闭时机不同，建议在方案中明确：

- 容器搜索：离开交互范围自动关闭。
- 背包查看：手动关闭。
- 尸体搜索：离开范围关闭，或尸体被销毁时强制关闭。

实现时容易漏掉这些差异，提前写清楚可以减少返工。

## 4. ModeRoot 三套节点的取舍

一个 prefab 里放 3 个 ModeRoot，不管当前用哪个模式，3 套 UI 节点都常驻内存。

建议区分情况：

- 如果三种模式只是标题、背景、图标不同，用同一套节点 + 样式切换更轻量。
- 只有在布局结构真的差异很大时（比如背包模式要居中放大），才用独立根节点。

可以折中：容器搜索和尸体搜索共用一套双栏根节点（只换样式），背包查看单独一套单栏根节点。这样只需要 2 个 ModeRoot。

## 5. 补充打开时的数据传递方式

文档定义了 `OpenMode`、`CorpseSubType`、`CurrentPointId` 等字段，但没说调用方怎么把这些值传进来。

建议明确：

- 是通过 ECA 的 `ui_key` 扩展参数传递？
- 还是在打开前由调用方直接赋值到 `SearchPanelComponent`？
- 还是新增一个带参数的打开消息？

这是实现时第一个要碰到的问题，方案里应该给出推荐做法。

## 6. 预留地面掉落容器的区分口子

地面掉落容器也会通过 SearchPanel 打开（见背包丢弃方案）。当前方案里没有提到这个场景。

建议在 `ContainerSearch` 模式下预留一个子类型（类似尸体的 `CorpseSubType`），例如：

- `ContainerNormal`：普通容器
- `ContainerGroundDrop`：地面掉落容器

一期可以不做差异表现，但数据结构上预留，二期做 GroundDrop 专属 UI 时就不需要改模式设计。

## 7. 尸体子类型建议考虑扩展性

当前只定义了 `CorpsePlayer` 和 `CorpseMonster`。如果后续有 Boss 尸体、NPC 尸体等需要不同表现，建议子类型枚举预留空间，或者直接用 int 而非 enum，方便配置驱动。
