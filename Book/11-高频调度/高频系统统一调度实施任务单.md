# 高频系统统一调度实施任务单

## 1. 文档目标

- 将《高频系统统一调度最终方案》拆解为可执行的开发任务。
- 明确每个任务的包落点、改动类型、前置依赖、完成标准。
- 方便按阶段排期、分人、联调和验收。

设计依据：

- `Book/高频系统统一调度最终方案.md`

本文职责：

- 负责落地执行拆分
- 不重复论证“为什么这样设计”

---

## 2. 任务拆分原则

- 先建立统一高频调度底座，再迁移具体业务。
- 先解决移动和子弹两条主链，再清查其它 `<50ms` 系统。
- 先保证服务端固定步长与调度一致性，再补观测、测试和收口规范。
- 禁止通过“全局放开 `TimerComponent <50ms` 限制”作为替代方案。
- 高频调度器由场景 Fiber 的 `Update` 周期直接驱动，不额外起 `WaitAsync(1)` 主循环。
- 所有高频逻辑必须可统计、可测试、可移除、可限流。

---

## 3. 里程碑划分

### M1：高频调度底座建立

目标：

- 服务端拥有场景级统一高频调度器。
- 可以创建高频通道、注册实体、固定步长驱动 Tick。
- 调度器接口契约完成冻结，可供业务并行接入。
- 不依赖 `<50ms` 的 `TimerComponent.NewRepeatedTimer`。

### M2：移动系统迁移

目标：

- 摇杆移动从“每单位一个 16ms timer”迁移到 `Move16ms` 通道。
- 保留现有 NavMesh 防穿墙和沿墙滑动逻辑。
- 平地、撞墙、停步链路重新稳定。

### M3：子弹系统迁移

目标：

- 子弹从 `33ms` repeated timer 迁移到 `Bullet33ms` 通道。
- 子弹飞行、命中、销毁在统一调度器下稳定运行。

### M4：其它高频系统清查与迁移

目标：

- 全仓识别所有 `<50ms` 高频系统。
- 为每类系统确定归属通道与迁移方案。
- 清理“业务直接起高频 timer”的剩余入口。

### M5：测试、观测与性能验收

目标：

- 高频调度器、移动、子弹拥有稳定自动化回归。
- 通道级统计、补帧、耗时、活跃对象数可观测。
- 明确正常口径和压力口径的验收值。

### M6：规范收口

目标：

- 项目内形成统一开发规范。
- 后续任何新高频系统都按统一入口接入。

## 5. 详细任务拆分

## 5.1 核心调度层

### T001 新增高频调度器运行时组件

目标：

- 在 `Scene` 级建立统一高频调度入口。

建议落点：

- `Packages/cn.etetet.core/Scripts/Model/Share`

建议组件：

- `HighFrequencySchedulerComponent`

建议字段：

- `Channels`
- `ActiveChannelCount`
- `LastUpdateTime`
- `TotalTickCount`

改动类型：

- 新增 Entity 组件

完成标准：

- 调度器组件可挂到 `Scene`
- `HighFrequencySchedulerComponent` 实现 `IUpdate`，由 ET `UpdateSystem` / `UpdateEvent` 驱动
- 每个 `Map Scene` 持有独立调度器实例
- 通道注册表、活跃对象集合、运行时状态均为场景内数据，不允许落到全局静态容器
- 生命周期完整
- 不包含业务逻辑，只包含调度所需运行时数据

### T002 新增高频通道数据结构与标识

目标：

- 定义统一通道模型，支持移动、子弹和未来其它高频系统。

建议落点：

- `Packages/cn.etetet.core/Scripts/Model/Share`
- `Packages/cn.etetet.core/Scripts/Core/Share`

建议内容：

- `HighFrequencyChannelId`
- `HighFrequencyChannelRuntime`
- 通道注册参数结构
- Tick 事件参数结构

建议首批通道：

- `Move16ms`
- `Bullet33ms`

完成标准：

- 通道标识统一
- 单个通道能表达间隔、补帧上限、活跃实体集合和统计信息

### T003 实现固定步长驱动与补帧控制

目标：

- 在 `Update` 中按固定步长推进通道 Tick。

建议落点：

- `Packages/cn.etetet.core/Scripts/Hotfix/Share`

建议系统：

- `HighFrequencySchedulerComponentSystem`

核心职责：

- 使用 `TimeInfo.Instance.ServerNow()` 作为唯一 `nowMs` 时间源
- 累积真实经过时间
- 按固定步长推进通道
- 控制每帧最大补帧次数
- 丢弃超限积压并记日志

完成标准：

- 任意通道可按固定 `dt` 连续推进
- 不出现无限补帧
- 通道无活跃对象时几乎无额外开销

风险点：

- 需要明确 Tick 执行时机，避免与网络消息处理顺序冲突

### T004 场景挂载高频调度器

目标：

- 在需要高频模拟的场景挂载统一调度器。

建议落点：

- `Packages/cn.etetet.map/Scripts/Hotfix/Server`
- 或对应 Scene `FiberInit`

首批挂载场景：

- `Map`

完成标准：

- 目标场景启动后具备高频调度能力
- 同进程多个 `Map Scene` 并行存在时，各自独立驱动、独立注册、互不共享运行时状态
- 非高频场景不强制挂载

### T004-B 输出调度器接口契约

目标：

- 在完整实现前先冻结调度器对外契约，解除移动与子弹并行开发阻塞。

建议落点：

- `Packages/cn.etetet.core/Scripts/Model/Share`
- `Packages/cn.etetet.core/Scripts/Hotfix/Share`

契约至少包括：

- 通道标识定义
- 调度器注册/移除 API
- Tick 派发参数结构
- `nowMs` 时间源契约，统一使用 `TimeInfo.Instance.ServerNow()`
- 统计与告警的最小输出口径

特别约束：

- 不在 Entity 上定义业务方法接口
- 保持 ET 的 Entity 纯数据规范
- 业务 Tick 逻辑仍落在 `System` / `Helper`

完成标准：

- 移动和子弹侧可以在不等待完整调度器实现的情况下并行接入
- 契约稳定，不在接入中途频繁变更

### T005 高频通道统计与告警

目标：

- 为后续性能压测和线上排查提供统一观测能力。

建议统计项：

- 通道活跃对象数
- 单帧 Tick 次数
- 单帧耗时
- 累计耗时
- 补帧丢弃次数
- 超预算次数

完成标准：

- 移动和子弹通道都能输出基础统计
- 出现持续补帧或耗时异常时可日志告警

### T006 高频调度器基础测试

目标：

- 保障统一调度器自身可靠。

建议覆盖：

- 固定步长推进
- 多通道并行
- 补帧上限
- 重复注册保护
- 销毁时自动清理

建议落点：

- `Packages/cn.etetet.test/Scripts/Hotfix/Test`

完成标准：

- 基础行为可自动回归
- 未来迁移业务时，不再重复怀疑调度器本身

说明：

- 该任务不依赖场景正式挂载
- 可在测试 Fiber 中手动创建组件完成基础单元测试

## 5.2 移动系统迁移

### T007 改造 `JoystickMoveComponent` 状态结构

目标：

- 让移动组件从“自己持有 timer”转为“被调度器驱动”。

建议落点：

- `Packages/cn.etetet.statesync/Scripts/Model/Server`

建议调整：

- 保留方向、序号、上次 Tick 时间等数据
- 去掉或废弃 `<50ms` timer 专用状态
- 增加“是否已注册到高频通道”的状态字段
- 保留并强化输入序号状态，用于防止旧输入覆盖停步

完成标准：

- 移动组件状态与统一调度模型兼容
- 服务端只接受最新输入序号
- 停步包不会被旧 move 包乱序覆盖

### T008 将移动注册/反注册接入 `Move16ms` 通道

目标：

- 非零输入时注册，停步时反注册，不再启动 16ms timer。

建议落点：

- `Packages/cn.etetet.statesync/Scripts/Hotfix/Server/C2M_JoystickInputHandler.cs`
- `Packages/cn.etetet.statesync/Scripts/Hotfix/Server/JoystickMoveComponentSystem.cs`

完成标准：

- 输入方向非零时进入移动通道
- 停步时标记待移除，并在当前通道 Tick 完成后统一提交移除
- 停步广播与反注册提交时序一致，不允许出现“本帧已广播停步但当前 Tick 仍推进了一步”
- 旧输入乱序保护逻辑不退化

### T009 拆分并接入固定步长移动 Tick 入口

目标：

- 把现有移动推进逻辑改造成调度器可调用的固定步长入口。

建议内容：

- 从原 `Tick()` 中抽出固定步长版本
- 入参改为统一 `dt`
- 保留 NavMesh 约束、沿墙滑动、旋转和同步广播
- Tick 入口保持同步方法，不允许 `async ETTask`

完成标准：

- 业务逻辑不依赖 `RepeatedTimer`
- 同一单位每个固定步长只推进一次
- 零输入停步与本轮 Tick 结束时的移除提交保持一致

### T009-B 移动双路并行验证

目标：

- 在正式切换前对比旧路径和新路径输出，降低切换风险。

建议方式：

- 在开关控制下保留旧路径输出
- 新旧两路同时产出位置结果
- 记录关键差异日志

重点对比：

- 平地直线移动
- 停步
- 撞墙
- 贴墙滑动

完成标准：

- 新旧两路在可接受误差内一致
- 确认不存在明显行为回归后，再移除旧路径

### T010 移除移动对 `<50ms` repeated timer 的依赖

目标：

- 移动链路彻底脱离 `NewRepeatedTimer(16, ...)`。

完成标准：

- `JoystickMoveComponentSystem` 不再通过 `TimerComponent` 启动 16ms 高频循环
- DOTNET 下移动系统与 Timer 护栏不再冲突

### T011 移动回归测试与日志验收

目标：

- 重新建立移动链路的自动化验收基线。

建议覆盖：

- 迁移前延迟基线记录
- 平地连续移动
- 停步生效
- 旧输入不覆盖停步
- 撞墙不穿墙
- 贴墙滑动
- 离墙恢复不瞬移

建议首批压力口径：

- `64` 个单位同时移动

建议依赖现有测试继续扩展：

- `Test_Joystick_StopResponseLatency_Test`
- `Test_Navmesh_SDCMap_WallCollision_Test`

完成标准：

- 有“正常口径”和“压力口径”两套数据
- 日志可定位输入、调度、服务端推进、停步广播各阶段耗时
- 可对比迁移前后的延迟基线，确认手感不退化

## 5.3 子弹系统迁移

### T012 改造子弹注册/反注册接入 `Bullet33ms` 通道

目标：

- 子弹创建后统一进入高频调度器，销毁时立即移出。

建议落点：

- `Packages/cn.etetet.statesync/Scripts/Hotfix/Server/BulletTickComponentSystem.cs`

完成标准：

- 子弹生命周期与通道注册状态一致
- 无重复注册和漏移除
- 子弹销毁遵循“先移出通道、后 Dispose”的顺序

### T013 拆分并接入固定步长子弹 Tick 入口

目标：

- 把子弹逻辑改造成调度器驱动的固定步长推进。

完成标准：

- 子弹飞行、命中、生命周期逻辑不再依赖 repeated timer
- 同一发子弹每个固定步长只执行一次
- Tick 入口保持同步方法，不允许 `async ETTask`

### T014 移除子弹对 `<50ms` repeated timer 的依赖

目标：

- 子弹链路彻底脱离 `NewRepeatedTimer(33, ...)`。

完成标准：

- 子弹系统在 DOTNET 下与 Timer 护栏不再冲突
- 与移动共存时不会互相争抢离散 timer

### T015 子弹回归测试与压力验证

目标：

- 建立子弹系统在新调度器下的正确性和性能基线。

建议覆盖：

- 单子弹推进
- 多子弹并发
- 命中后移除
- 销毁后不再被调度
- 高并发下补帧与耗时统计

建议首批压力口径：

- `200` 颗子弹并发

完成标准：

- 子弹核心链路有自动化回归
- 压力下行为可预期，日志可观测

## 5.4 其它高频系统治理

### T016 全仓扫描其它 `<50ms` 高频系统

目标：

- 找出除移动、子弹外所有直接或间接依赖 `<50ms` 高频调度的逻辑。

建议扫描范围：

- `NewRepeatedTimer`
- 自定义高频循环
- 高频 `WaitAsync`
- 帧驱动模拟逻辑

输出内容：

- 系统名称
- 当前调度方式
- 当前频率
- 是否必须固定步长
- 迁移优先级

完成标准：

- 形成完整清单
- 不遗漏已上线链路

### T017 其它高频系统迁移与归类清单

目标：

- 为扫描出的系统确定接入策略。

输出要求：

- 哪些系统迁移到已有通道
- 哪些系统需要新通道
- 哪些系统可降级为 `>=50ms` 普通 timer
- 哪些系统需要延后处理

完成标准：

- 高频系统全量归类完成
- 后续治理顺序明确

## 8. 本轮不接受的实现方式

- 直接全局删除 `TimerComponent <50ms` 限制
- 移动继续保留“每单位一个 16ms timer”
- 子弹继续保留“每对象一个 33ms timer”
- 新增业务私有高频循环绕开统一调度器
- 高频系统没有统计、告警和测试就直接上线

- 是否已确认移动和子弹的测试口径
- 是否已确认其它 `<50ms` 系统的扫描口径

---

## 10. 验收口径

- 不接受业务直接创建 `<50ms` 的 `NewRepeatedTimer`
- 不接受高频系统没有通道归属
- 不接受移动迁移后手感明显退化
- 不接受子弹迁移后并发下出现不可解释的漏 Tick
- 不接受没有自动化回归就结束本次治理

建议量化口径：

- 移动迁移前必须先记录基线延迟
- `Move16ms` 在 `64` 单位同时移动时统计单帧耗时
- `Bullet33ms` 在 `200` 子弹并发时统计单帧耗时
- 单帧耗时超过通道步长 `50%` 触发告警
- 单帧耗时超过通道步长 `100%` 触发补帧丢弃统计
