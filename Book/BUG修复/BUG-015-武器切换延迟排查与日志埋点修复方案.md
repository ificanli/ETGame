# BUG-015 武器切换延迟排查与日志埋点修复方案

> 文档版本：v1.2  
> 创建时间：2026-04-21  
> 最后更新：2026-04-21  
> 状态：已验收  
> 关联 BUG：BUG-015（BUG追踪.md）

---

## 1. 现象描述

当前局内点击武器切换按钮后，玩家会明显感觉切枪“慢一拍”：

- 点击武器栏槽位后，不是立刻切到目标武器
- 武器栏选中态和当前弹药显示要等一段时间才更新
- 人物手上的枪模切换也有明显滞后

从体验上看，像是“按钮点下去了，但切枪要等服务端确认或等资源加载”。

---

## 2. 根因判断

静态排查后，当前切枪链路具备两个天然延迟源：

1. **服务端确认门**
   - 客户端点击武器槽后，只发送 `C2M_SwitchWeapon`
   - 客户端本地不会立即切 `WeaponComponent.CurrentSlot`
   - 必须等地图服处理并广播 `M2C_SwitchWeapon` 后，客户端才真正执行 `weaponComponent.SwitchWeapon(...)`
2. **视图刷新门**
   - 客户端收到 `M2C_SwitchWeapon` 后，除了刷新 WeaponBar，还会触发 `EventWeaponSwitched_SyncWeaponView`
   - 该事件会进入 `WeaponViewComponentSystem.RefreshWeaponAsync(...)`
   - 新枪模切换过程中可能再叠加 `WaitViewReadyAsync`、武器 prefab 异步加载和实例化耗时

因此本问题不能只凭体感判断“是不是服务器延迟”，需要把整条链路的时序打出来：

- 按钮点击时刻
- 客户端发包时刻
- 服务端收包和广播时刻
- 客户端收包与实际切槽时刻
- WeaponBar 刷新时刻
- 枪模刷新开始/资源加载完成/实例化完成时刻

---

## 3. 本轮目标

本轮先不直接改切枪策略，也不强行上本地预测切枪，而是先把诊断链路补完整；在你追加反馈“射击本身也有延迟”后，本轮目标同步扩展为“切枪 + 射击”两条链路的时序拆分：

1. 补计划、BUG 追踪、修复方案和开发日志入口
2. 给武器切换链路加统一 `WeaponSwitchTrace` 日志
3. 给射击链路补统一 `WeaponFireTrace` 时序日志
4. 明确拆出“网络确认耗时”和“客户端视图刷新/表现耗时”两段
5. 执行 `dotnet build ET.sln`，确保日志埋点版本可编译
6. 输出一套复现和看日志的方法，方便你在真机/联机环境下判断根因

## 4. 技术方案

### 4.1 日志链路

本轮沿切枪主链路补以下日志点：

1. `WeaponItemComponentSystem.OnEventClickInvoke`
   - 记录 UI 点击时刻、点击槽位、当前槽位、当前两把武器 ID
2. `WeaponSwitchHelper.SwitchWeapon`
   - 记录客户端真正发 `C2M_SwitchWeapon` 的时刻和本地状态快照
3. `C2M_SwitchWeaponHandler`
   - 记录服务端收到请求、校验结果、切槽完成、广播前后的时间点
4. `M2C_SwitchWeaponHandler`
   - 记录客户端收到 `M2C_SwitchWeapon` 的时刻
5. `PendingWeaponSyncComponentSystem.ApplySwitch`
   - 记录客户端真正执行 `weaponComponent.SwitchWeapon(...)` 并发布 `EventWeaponSwitched` 的时刻
6. `EventWeaponSwitched_RefreshWeaponBar`
   - 记录 WeaponBar 刷新时刻和当前槽位
7. `WeaponViewComponentSystem.RefreshWeaponAsync`
   - 记录枪模刷新开始、等待视图 ready 耗时、资源缓存命中与否、prefab 加载耗时、实例化完成时刻

### 4.2 日志格式约束

统一使用前缀：

`[WeaponSwitchTrace][阶段名]`

例如：

- `[WeaponSwitchTrace][UIClick]`
- `[WeaponSwitchTrace][ClientSend]`
- `[WeaponSwitchTrace][ServerRecv]`
- `[WeaponSwitchTrace][ServerBroadcast]`
- `[WeaponSwitchTrace][ClientRecv]`
- `[WeaponSwitchTrace][ClientApply]`
- `[WeaponSwitchTrace][UIRefresh]`
- `[WeaponSwitchTrace][ViewRefreshBegin]`
- `[WeaponSwitchTrace][ViewPrefabLoaded]`
- `[WeaponSwitchTrace][ViewRefreshDone]`

统一输出以下关键字段：

- `clientNow` / `serverNow`
- `unitId`
- `slot`
- `weaponId`
- `currentSlot`
- `slot1WeaponId` / `slot2WeaponId`
- 资源加载相关的 `prefab`、`cacheHit`、`loadCostMs`

## 5. 最新日志观察与补充修复

### 5.1 切枪链路的初步结论

从 `Unity Editor.log` 中已经能看到一段完整切枪 trace，例如：

- `UIClick / ClientSend`：`clientNow=1776738466502~1776738466505`
- `ServerRecv / ServerBroadcast`：`serverNow=1776738467058~1776738467059`
- `ClientApply / ClientRecv`：`clientNow=1776738467524`，客户端侧 `serverNow=1776738467452~1776738467457`
- `ViewRefreshDone`：`clientNow=1776738467527`，`totalCostMs=2`

这说明最近这次“切枪慢”的主要耗时不在枪模刷新：

1. `ClientSend -> ServerRecv` 约 `553ms`
2. `ServerBroadcast -> ClientApply` 约 `393~398ms`
3. `ViewRefreshDone` 仅 `2~3ms`

因此就当前这批日志看，**切枪延迟主要卡在客户端到服务端再回客户端的权威确认链路**，不是最近这次的 prefab 加载或本地视图刷新。

### 5.2 射击链路的当前缺口

`Editor.log` 里已经能看到：

- 服务端 `CanFire ready`
- 服务端 `Server fired`
- `M2C_WeaponFire` 经地图服 / Gate / NetClient 转发
- 客户端收到 `M2C_WeaponFire`
- 客户端实例化投射物

但现有日志还缺少统一的 `clientNow / serverNow` 时序字段，所以当前只能确认：

- 射击表现同样是**服务端权威确认后再落到客户端**
- 还不能像切枪一样，直接量化“服务端决定可开火 -> 客户端真正出表现”的耗时

因此本轮追加射击时序埋点，用于下一轮复现时直接量化网络确认与客户端表现开销。

### 5.3 最新定位结论与修正策略

最新这轮 `Editor.log` 进一步说明了两个关键点：

1. **切枪的主要耗时仍然不在武器视图**
   - 本机一次典型切枪：
   - `ServerRecv.serverNow=1776740016027`
   - `ServerBroadcast.serverNow=1776740016028`
   - `ClientApply.serverNow=1776740016362`
   - `ViewRefreshDone.totalCostMs=3`
   - 说明服务端处理仍然只有 `1ms`，本地枪模刷新仍然只有 `3ms`
2. **切枪真正大的延迟在等待权威消息**
   - 本机一次切枪点击：
   - `ClientSend.serverNow=1776739991461`
   - `ServerRecv.serverNow=1776740016027`
   - 中间约 `24.5s`
   - 这说明继续坚持“只等 `M2C_SwitchWeapon` 再切枪”，体感一定会被网络/队列延迟放大
3. **射击慢也主要不是投射物生成慢**
   - 本机一次典型开火：
   - `ServerSend.serverNow=1776739961651`
   - `ClientRecv.serverNow=1776739961946`
   - 中间约 `295ms`
   - 但 `ClientProjectileDone.totalCostMs=2`
   - 说明射击表现的主要等待也在服务端权威回包
4. **射击体感里还叠加了武器规则差异**
   - `50001`（锋刃 自动步枪）配置：`AttackRange=8`、`CanMoveWhileFire=False`
   - 日志里多次出现 `ServerCanFireBlocked ... moving=True`
   - `50003`（气泡 冲锋枪）配置：`AttackRange=6`、`CanMoveWhileFire=True`
   - 切到 `50003` 后，本机连续出现 `HasTarget no target`
   - 所以“切完枪后不打/晚打”里，有一部分其实是目标不在 6 米射程内，不全是网络

基于这轮日志，本轮把切枪策略从“只等服务端回包”推进为：

- 同槽点击不再重复发包
- 空槽点击直接拦截
- 合法切枪先做客户端本地预测切换
- 服务端 `M2C_SwitchWeapon` 后续继续做最终校正

### 5.4 最新补充：武器栏未选中态发白 UI 回归

在你继续回归本地预测切枪版本时，又暴露了一个新的局部 UI 问题：

- 切到某个武器后，另一个武器槽位会明显发白/泛灰
- 这不是新的资源绑定问题，也不是图标资源丢失
- 当前 `WeaponItem.prefab` 已经具备独立的 `WeaponBg / WeaponIcon / WeaponSelect` 三层结构

静态排查确认，这次问题仍在 `WeaponItemComponentSystem.RefreshBackgroundColor(...)`：

- 图标层 `WeaponIcon` 本身会保持 `Color.white`
- 真正被动态着色的是背景层 `WeaponBg`
- 原逻辑会把“未选中但有武器”的槽位额外染成灰白色，叠加当前 prefab 表现后，视觉上会像“另一个武器变白了”

因此本轮追加一个最小 UI 修正：

- 未选中但有武器的槽位，不再额外做灰白染色
- 占用槽位统一保持正常背景底图
- 当前武器只通过 `WeaponSelect` 高亮框区分
- 空槽和换弹态维持现有特殊底色

### 5.5 最新补充：选中高亮纯白块的真实原因

在你继续看武器栏选中效果时，又发现当前高亮会直接显示成一块纯白色：

- 根因不是图标丢失，也不是 `WeaponBg` 染色
- 真正的问题在 `WeaponItem.prefab/WeaponSelect`
- 该节点之前只有 `Image.color`，但 `m_Sprite` 为空
- 运行时 `SetSelected(true)` 又会把它的 alpha 拉到 `1`
- 最终 Unity 会把默认白图完整铺到槽位上，所以看起来像一整块白色高亮

因此这轮继续把高亮收口到资源层：

- `WeaponSelect` 直接换成项目内已存在的选择框 sprite
- 初始颜色改成与现有装备选择一致的暖金系，而不是默认纯白
- 渲染层级从“盖在图标上面”调整为“位于背景和图标之间”，保证有完整高亮框，但不会把武器图标洗白
