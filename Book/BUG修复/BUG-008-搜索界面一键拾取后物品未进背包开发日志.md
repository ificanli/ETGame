## 决策记录

### 2026-03-29 - 修复下沉到通用物品层

- **背景**：表面问题出现在 `SearchPanel` 的“一键拾取”，但手动拖拽同一路径正常，说明核心差异在自动入包而不是 UI 事件。
- **方案**：把二维合法找位下沉到 `cn.etetet.item`，由 `ItemHelper.AddItem` 统一使用。
- **原因**：这样普通容器、地面掉落、尸体盒等所有走自动入包的共用链路都能一起修正。
- **替代方案**：只在 `ContainerRuntimeHelper.TakeAll` 里单独补判断。放弃原因是容易形成重复逻辑，后续其他自动入包入口还会再次踩坑。

### 2026-03-29 - 顺手收敛同类自动回包入口

- **背景**：代码扫描发现 `FindEmptySlot()` 除了一键拾取，还被“整理背包”和“卸装备回包”使用。
- **方案**：把这两条同类自动找位链路一起切到二维合法锚点。
- **原因**：用户要求按共用链路修；如果只修 `TakeAll`，很快会在卸装备或整理背包时复现同样的问题。
- **替代方案**：只改 `AddItem`。放弃原因是修复面不完整。

### 2026-03-30 - BUG-008 退回开发中，补拖拽入包链路

- **背景**：用户实机回归明确反馈“部分物品失败”，且手动拖拽一个物品进入背包也报错或表现异常。
- **方案**：把 `ContainerRuntimeHelper.MoveContainerToBag / MoveBagToContainer` 纳入本次修复面，同时复核 `ItemHelper.MoveItem` 的二维服务端校验。
- **原因**：当前问题不再只是自动入包；容器拖拽入包链路仍然会把旧配置多格物品按旧一维语义写进背包，继续制造脏数据。
- **替代方案**：只补客户端 SearchPanel 的跨区拖拽校验。放弃原因是服务端仍会接受非法请求，不能从根上兜住数据正确性。

### 2026-03-30 - 二维锚点校验继续下沉到 `ItemComponent`

- **背景**：第二轮问题同时涉及 `ItemHelper.MoveItem` 与 `ContainerRuntimeHelper`，如果每条链路各自拼二维判断，会很快再次分叉。
- **方案**：在 `ItemComponentSystem` 新增 `CanPlaceAtAnchorSlot`，统一基于共享 `LoadoutGridPlacementHelper` 校验“指定锚点是否合法”。
- **原因**：这样自动入包、背包移动、容器拖拽入包/回包都复用同一套服务端二维规则，后续不会再出现“有的入口校验、有的入口不校验”。
- **替代方案**：只在 `ContainerRuntimeHelper` 里写局部判断。放弃原因是会继续复制逻辑，也兜不住 `ItemHelper.MoveItem` 的非法请求。

### 2026-03-30 - 第三轮保持“空背包可进图”，只补客户端提示

- **背景**：继续看现场日志后确认，这次用户手上的局内 live unit 根本没有背包，`C2G_ConfirmLoadout`、`LoadoutRuntimeSync`、`M2C_SyncBagData` 都是 `0x0`；服务端报 `bag is full` 属于当前规则下的正常结果。
- **方案**：不改“空背包可进图”的服务端规则，只在 `SearchPanel` 客户端补提示，覆盖一键拾取和拖拽到背包区两类静默失败入口。
- **原因**：用户已经明确选择保留当前规则；当前真正缺的是反馈，不是再改一次服务端行为。
- **替代方案**：禁止空背包确认起装。放弃原因是这会改变现有设计与服务端行为，不符合用户本轮选择。

## 问题日志

### 2026-03-29 - 自动入包仍使用旧一维空槽语义

- **现象**：一键拾取后容器内容被移除，但背包不显示新增物品。
- **原因**：`ItemHelper.AddItem` 新建物品时仍调用一维 `FindEmptySlot()`，可能把多格物品放进二维非法锚点。
- **解决**：准备引入二维合法锚点查找，并让自动入包复用该能力。

### 2026-03-29 - 全量编译首次波动后已恢复

- **现象**：第一次执行 `dotnet build ET.sln` 时，编译被 `GameObjectComponentSystem.cs` 的类型不匹配报错打断；随后同文件现场内容发生了同步变化。
- **原因**：该文件在我工作期间存在并行修改，导致第一次构建看到的工作区状态不是最终状态。
- **解决**：重新读取现场代码并再次执行 `dotnet build ET.sln`；第二次构建结果为 `0 warning / 0 error`。

### 2026-03-30 - 容器拖拽入包仍在写错误尺寸和旧配置

- **现象**：`Editor.log` 显示 `C2M_ContainerMoveItem` 对 `eca_sdcmap_container_0019` 返回成功，容器被清空，但背包收到的是 `ConfigId=10012, GridWidth=1, GridHeight=1, SlotIndex=8`。
- **原因**：`MoveContainerToBag` 没有走 `ItemHelper.AddItem`，而是直接 `CreateBagItem`；它既没校验二维合法锚点，也没把旧配置 `10012` 归一到真实配置 `22012`，也没写入真实 `2x3` 尺寸。
- **解决**：把容器<->背包移动链路的服务端二维合法落点校验、旧配置归一、正确尺寸写入补齐，并新增自动化回归。

### 2026-03-30 - 当前这次现场的直接原因是 live unit 没有背包

- **现象**：用户点击一键拾取时，容器里物品还在，但背包一直没有新增；拖拽到背包区也像“点了没反应”。
- **原因**：日志确认本局起装时上报的是 `BackpackConfigId=0, BagWidth=0, BagHeight=0`，Map live unit 也是 `bag=0x0`，随后 `M2C_SyncBagData` 返回 `Capacity=0, Width=0, Height=0`。在这个前提下，服务端 `ItemHelper.AddItem` 稳定报 `bag is full`，行为本身符合当前设计。
- **解决**：保持规则不动，在客户端提前提示“未装备背包，无法拾取容器物品”，避免继续把“空背包导致无法入包”误解成“拾取逻辑没修好”。
