> 状态：已过时

> 2026-04-21 回退说明：用户确认不继续沿“客户端权威移动 + `C2M_MoveState` 服务端连续推进 + 客户端本地交互预测拆权”方案收敛。当前代码已回退到旧服务端权威主链：客户端恢复发送 `C2M_JoystickInput`，交互按钮/门箱子/拾取/容器 UI 重新只认服务端范围与服务端回包；同日又继续清理了客户端权威时期遗留的动画/朝向显示层逻辑，包括移除 `preferred facing` 缓存、恢复移动动画旧口径、撤掉锁定相机 authority 方向 fallback。下面内容仅保留为本次排查和尝试修复的历史记录，不再作为当前实现口径。

---

## 1. 现象描述

当前局内交互出现新的断链现象：

- 玩家移动到门、箱子等交互物附近后，交互按钮能够立即显示
- 玩家点击交互按钮后，没有打开门、没有打开容器 UI，也没有任何明显提示
- 现象不只发生在容器，所有依赖服务端处理的交互点位都类似“没反应”

这说明当前问题已经不在“按钮是否显示”，而在“按钮点击后的服务端交互链”。

---

## 2. 根因判断

结合 `W3#42 移动系统优化：客户端权威移动+服务端校验` 的最新实现，真正的问题不只是“交互提示和交互执行有时间差”，而是客户端与服务端的位置口径已经明显分叉：

1. **客户端**
   - `InputSystemComponentSystem` 每帧基于输入和速度推进本地预测位置
   - 客户端自己的 `unit.Position` 也会被预测位置持续回写，用来驱动提示、显示和本地体验
2. **服务端**
   - `C2M_MoveState` 以 `20Hz` 上报
   - 旧实现里服务端只在收到 `C2M_MoveState` 时把 `unit.Position` 跳到客户端上报点
   - 两个包之间没有“收到输入后继续按相同方向和速度持续推进”的服务端过程

于是会出现系统性分叉：

- 客户端看起来已经走到门、箱子、任务点旁边了
- 服务端却仍落在更早的历史位置
- 所有依赖服务端位置的链路都会被一起拖坏，包括交互、拾取、容器打开、技能前置距离判定等

所以 BUG-014 只是位置分叉在交互链上的一个显性症状，不是唯一问题。

在连续推进补上后，最新回归又确认出两个客户端侧补充问题：

6. **本地预测范围和服务端 hint 共用同一套运行时字段**
   - `RefreshLocalInteractState` 每帧重建 `InRangePointIds`
   - `M2C_ECAInteractHint` 也在修改 `InRangePointIds / PointCanInteract / FocusPointId`
   - 当服务端刚下发 `inRange=false` 时，本地下一帧又会把点重新放回范围集合，甚至把 `PointCanInteract` 兜底成 `true`
   - 于是就会出现“日志里 hint=false，但按钮还能点”的混线现象
7. **容器 UI 打开前额外同步背包，导致高延迟下界面晚开**
   - `M2C_ContainerOpen` 到达客户端后，本来已经拿到了容器物品
   - 但 `ECAContainerOpenUIEventHandler` 还会先 `await C2M_SyncBagData`
   - 面板要多等一次 RTT 才会真正打开，所以在高延迟下会明显感觉“点了之后过一会儿界面才出来”

---

## 3. 修复目标

本次修复不改客户端手感，也不把交互/拾取一类业务都改回纯服务端表现，而是把服务端位置推进能力补回去：

1. 保留客户端本地预测和当前移动手感
2. 服务端恢复“收到输入后按固定 Tick 持续推进位置”的能力
3. `C2M_MoveState` 从“唯一推进位置的来源”改为“输入同步 + 校验 + 漂移锚点”
4. 让服务端真实位置持续逼近客户端当前运动状态，减少交互与技能类服务端门禁误判
5. 本地预测只负责“提示立即出现”，服务端 hint 只负责“是否真的允许交互”
6. 容器面板收到打开消息后先显示，再异步补背包同步，不再阻塞 UI 打开
7. 执行 `dotnet build ET.sln` 与定向测试验证编译和核心行为

---

## 4. 技术方案

### 4.1 整体思路

修复点改为“服务端连续推进位置”，临时交互补丁不保留：

1. 复用服务端已有 `JoystickMoveComponent` 的 16ms 高频调度能力
2. 当服务端收到 `C2M_MoveState` 时：
   - 校验客户端上报位置
   - 合法时把当前点作为服务端锚点
   - 更新最新输入方向、输入序号和时间戳
   - 让 `JoystickMoveComponent` 接管后续连续推进
3. 服务端在每个 `Move16ms` Tick 中：
   - 按当前方向和速度推进 `unit.Position`
   - 保留现有 NavMesh 贴墙/防穿墙逻辑
   - 对客户端权威模式抑制旧 `M2C_JoystickMove` 广播，避免和 `MoveState` 体系冲突
   - 对玩家周期性执行一次 `ECAHelper.CheckPlayerInRange(unit)`，让服务端交互范围跟着真实服务端位置走
4. 客户端原先“交互前强制同步当前位置”的临时补丁撤掉
5. 客户端交互状态按职责拆开：
   - `InRangePointIds / FocusPointId` 继续作为本地预测提示状态
   - `PointCanInteract / PointButtonTextIds` 只接受服务端 hint 更新
   - 服务端一旦明确下发 `inRange=false`，客户端按钮立即禁点，本地刷新不能再把它恢复成可点击
6. 容器面板打开链改为：
   - `M2C_ContainerOpen` 到达后立即发 UI 打开事件
   - `SearchPanel` 先打开
   - 背包同步改为后台异步刷新，避免高延迟下额外阻塞一次界面出现
7. 新增自动化测试覆盖“单次 `C2M_MoveState` 后服务端位置会持续前进，停步后会停止”以及“服务端 hint=false 后本地刷新不能恢复可点击状态”

### 4.3 架构约束

- 不修改 `C2M_ECAInteract` 协议结构，也不放宽服务端范围门禁
- 不把业务侧的交互、拾取、技能前置距离全部改成客户端权威
- 不保留 `Hotfix -> HotfixView` 的跨层调用临时补丁
- 服务端连续推进必须继续遵守现有 NavMesh 约束和 ET ECS / 分层规范
