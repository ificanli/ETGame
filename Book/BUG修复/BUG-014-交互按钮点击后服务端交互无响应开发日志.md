## 决策记录

### 2026-04-20 - 不放宽服务端交互门禁，改为修服务端位置推进

- **背景**：用户明确要求不要把交互、拾取、技能距离等全部改回服务端口径，也不接受继续靠容差或交互前强制同步这种补丁维持。
- **方案**：保持客户端预测手感，同时把服务端收到 `C2M_MoveState` 后的行为改为“校验 + 锚点矫正 + 16ms 连续推进位置”。
- **原因**：这样修的是客户端/服务端位置长期分叉的根因，而不是只修门、箱子交互这一条表象链路。
- **替代方案**：在交互前强制同步一次当前位置。放弃原因是它只能掩盖交互 BUG，无法修复拾取、技能前置距离等所有依赖服务端位置的链路，而且还引入了 `Hotfix -> HotfixView` 跨层依赖。

### 2026-04-21 - 本地预测只管提示，服务端 hint 只管真实可交互状态

- **背景**：最新日志已经证明，服务端会下发 `inRange=false`，但客户端按钮仍可点击；继续加日志后确认是 `RefreshLocalInteractState` 和 `M2C_ECAInteractHint` 同时写 `InRangePointIds / PointCanInteract / FocusPointId`。
- **方案**：保留 `InRangePointIds / FocusPointId` 作为本地预测提示状态；`PointCanInteract / PointButtonTextIds` 改成只接受服务端 hint 更新，本地刷新不再兜底写 `true`。
- **原因**：这样能保留“按钮立即出现”的手感，同时堵住“服务端明确说不在范围里了，但客户端还继续当可点击”的口径污染。
- **替代方案**：把所有按钮口径完全改回服务端。放弃原因是会重新引入“客户端已经到位但按钮迟迟不出现”的体验问题。

### 2026-04-21 - 容器 UI 先开面板，再后台同步背包

- **背景**：`M2C_ContainerOpen` 到达后，客户端还会先 `await C2M_SyncBagData`，高延迟下容器面板要多等一次 RTT 才显示。
- **方案**：`ECAContainerOpenUIEventHandler` 改成先 `OpenPanelAsync(SearchPanel)`，随后后台异步同步背包数据。
- **原因**：`SearchPanel` 本身会在 `LateUpdate` 基于 `ItemComponent` 自动刷新，背包同步没有必要阻塞整个面板出现。
- **替代方案**：保留同步前置不动。放弃原因是高延迟环境下玩家会明显感觉“点了有反应，但界面晚开”，而且这段等待并不是容器数据本身必需的。

### 2026-04-21 - 放弃本轮补丁，整体回到旧服务端权威主链

- **背景**：最新日志虽然证明交互链最终能成功，但高延迟环境下仍存在明显体感问题；用户明确要求停止继续修补客户端权威链路，直接回退到旧服务端权威方案。
- **方案**：客户端移动输入恢复发送 `C2M_JoystickInput`，不再把预测位置回写到本机 `unit.Position`；撤掉 BUG-014 新增的本地交互预测状态拆权、交互前补发移动状态、容器 UI 异步补包与服务端连续推进补丁。
- **原因**：当前最重要的是恢复稳定、可预期的老链路，先把“按钮显示、交互执行、容器打开、拾取、技能距离判定”重新统一到服务端口径，再决定是否重做移动优化。
- **替代方案**：继续沿 `C2M_MoveState + 服务端连续推进` 方向补日志和补容差。放弃原因是用户已明确不接受继续在现有客户端权威方案上打补丁。

### 2026-04-21 - 动画/朝向显示层也必须完全回到旧口径

- **背景**：交互主链回退后，用户继续指出“动画相关的好像还没有回退”；静态排查确认 `Input/GameObject/Weapon/CombatLockCamera` 仍残留 `preferred facing` 和 authority 直驱显示逻辑。
- **方案**：移除 `preferred facing` 字段、方法和所有调用；移动动画恢复为旧的视觉位移推导，只保留 authority 停步兜底；锁定相机移动方向恢复只认 `UnitViewInterpolationComponent`。
- **原因**：这些残留虽然不直接决定门、箱子是否能交互，但会继续把显示层行为拖向旧的客户端权威方案，污染回退后的验证结论。
- **替代方案**：只回退交互主链，保留动画/朝向残留。放弃原因是用户明确要求“全部回调”，而且残留会继续制造客户端和服务端口径不一致的体感。

## 问题日志

### 2026-04-20 - 客户端预测位置与服务端真实位置分叉过大

- **现象**：门、箱子、任务点等所有依赖服务端位置判定的链路都开始“有按钮但没反应”，用户同时感觉客户端和服务端位置差得太多，移动速度像不一样。
- **原因**：客户端每帧都在推进预测位置，但服务端只在 `20Hz` 的 `C2M_MoveState` 到包时跳一次 `unit.Position`，包和包之间没有持续推进，导致服务端真实位置长期落后。
- **解决**：把 `C2M_MoveState` 接入服务端现有 `JoystickMoveComponent` 高频 Tick，让服务端在两次输入包之间也持续推进位置，并在客户端权威模式下抑制旧 `M2C_JoystickMove` 广播。

### 2026-04-20 - 临时交互补丁触发跨层编译错误，直接撤掉

- **现象**：先前“交互前强制同步当前位置”的补丁在 `ECAInteractHelper.cs` 中引用了 `InputSystemComponent`，`dotnet build ET.sln` 直接失败。
- **原因**：`ECAInteractHelper.cs` 位于 `Hotfix`，而 `InputSystemComponent` 在客户端 `HotfixView/ModelView` 侧，违反程序集分层约束。
- **解决**：临时补丁整体撤掉，回到只保留根因修复方案；同时新增服务端连续推进测试，避免回归。

### 2026-04-21 - 服务端 hint=false 仍可点击，根因是状态混线

- **现象**：日志明确打印 `inRange=false`，但按钮依旧可点，点下去后在高延迟下还会晚一会儿才出现容器界面。
- **原因**：本地预测和服务端 hint 共用 `PointCanInteract` 等字段；服务端 false 被本地下一帧的预测刷新覆盖成可点击，容器界面又额外被“打开前同步背包”阻塞了一次 RTT。
- **解决**：把本地预测范围和服务端可交互状态拆权；同时把容器 UI 的背包同步改成打开后的后台异步刷新，并新增定向测试兜底。

### 2026-04-21 - 用户要求停止沿客户端权威方案继续修补

- **现象**：连续推进补丁后，问题从“完全没反应”收敛成“最终能成功但高延迟下仍明显发晚”；但用户对客户端/服务端位置分叉已经失去信心，明确要求整条链路回退。
- **原因**：当前代码口径与文档、任务状态都默认“BUG-014 已修好待回归”，如果不回退同步文档，后续很容易继续按错误方案扩修。
- **解决**：代码恢复旧服务端权威主链，删除两条仅服务于本轮补丁的定向测试，并把 `BUG-014` 文档标记为历史方案。

### 2026-04-21 - 动画与朝向显示层残留未完全回退

- **现象**：主移动/交互链已回到旧服务端权威口径，但移动朝向、连发武器朝向缓存、锁定相机移动偏移等显示层仍夹带客户端权威时期逻辑。
- **原因**：上一轮回退优先处理的是输入、交互、容器和服务端移动主链，`preferred facing` 缓存、authority 直驱 `MoveSpeed`、相机方向 fallback 仍留在客户端显示层文件里。
- **解决**：删除 `preferred facing` 相关字段/方法/调用，恢复移动动画旧的视觉位移推导口径，撤掉锁定相机里的 authority 方向 fallback，并重新执行 `dotnet build ET.sln`。
