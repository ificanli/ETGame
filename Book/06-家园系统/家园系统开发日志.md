## 决策记录

### 2026-04-10 - 家园文档从单页需求升级为三层结构

- **背景**：当前目录里同时存在系统方案稿、私有副本方案稿和 `Home` 首页需求文档，但“系统需求”和“页面设计”没有正式拆开。
- **方案**：重构为《家园系统需求文档》《家园UI设计文档》《家园系统开发日志》三层结构。
- **原因**：后续要做的是完整家园系统正式版 demo，而不是继续扩一份首页文档；如果不拆层，系统规则、页面职责和实现记录会继续混写。
- **替代方案**：继续沿用 `Home主界面需求文档` 承接所有后续需求。这样文档职责会继续失真，因此不选。

### 2026-04-10 - 旧 `Home主界面需求文档` 保留为历史稿

- **背景**：现有 `Home主界面需求文档` 已经对应过一轮真实首页落地和开发追踪，直接覆盖会丢失上下文。
- **方案**：旧文档继续保留，新文档作为正式版 demo 主基线。
- **原因**：这样既保留首轮实现依据，也能让后续正式版设计拥有干净的主入口。
- **替代方案**：直接删除或改写旧文档。会丢失首轮实现背景，因此不选。

### 2026-04-10 - 正式版系统文档不再按一期/二期拆分

- **背景**：用户明确要求家园系统需求文档直接按完整系统写全，不再按一期/二期切分需求。
- **方案**：系统需求按完整体系组织，但保留“当前正式版 demo 的首批建筑范围”和“当前实现优先级”的落地口径。
- **原因**：这样既满足完整系统定义，也能保证后续实现收敛。
- **替代方案**：继续按一期/二期组织文档。与当前用户要求不符，因此不选。

### 2026-04-10 - 正式版 UI 目标从 `BuildPanel` 过渡实现提升为独立家园页面体系

- **背景**：当前 `BuildPanel` 承接 `Home` 首页是首轮真实落地的合理方案，但不适合作为完整家园系统长期壳。
- **方案**：在 UI 设计文档中把正式版目标定义为独立 `HomePanel` 与多建筑详情页结构，同时保留当前 `BuildPanel` 首页作为历史实现参考。
- **原因**：继续围绕单页壳扩展，后续结构会越来越乱。
- **替代方案**：继续围绕 `LobbyPanel.BuildPanel` 扩所有后续功能。短期快，但长期结构会失控，因此不选。

### 2026-04-13 - 家园正式版主结构从抽象功能模块改为建筑驱动

- **背景**：前一版新文档仍以“工坊/合同/恢复/出击准备”作为当前正式版主结构，和用户最新确认的家园规则不符。
- **方案**：把正式版 demo 主结构改写为“主城 + 建筑槽位 + 4 个可建建筑”，即 `大红收藏馆`、`物品回收间`、`农场`、`仓库`。
- **原因**：用户已经明确要求家园围绕可点击建筑组织，而不是围绕抽象功能标签组织。
- **替代方案**：继续保留抽象模块主结构，只在文字里补充建筑示例。这样会导致文档口径继续摇摆，因此不选。

### 2026-04-13 - 主城作为等级门与任务门的唯一核心建筑

- **背景**：正式版规则里，主城不是普通建筑，而是整个家园规则的等级门和任务门。
- **方案**：在需求文档中明确主城默认存在、不可拆除、不可替换，且其他建筑等级上限、槽位解锁和当前任务组都由主城等级驱动。
- **原因**：如果主城只写成普通建筑，后续所有等级限制都会分散。
- **替代方案**：把主城和其他建筑平级处理。这样会削弱家园核心循环，不选。

### 2026-04-13 - 仓库作为当前优先细化模块

- **背景**：用户确认这轮先把 `仓库` 做深，并明确“先做家园存储闭环，不接复杂背包整理”。
- **方案**：在需求文档和 UI 文档里把仓库写成当前优先建筑，首版范围聚焦“容量表达、库存表达、来源表达、满仓阻塞”。
- **原因**：仓库同时是回收间产物承接层，也是后续建筑扩展的底座，优先级必须前置。
- **替代方案**：先把仓库写成完整跨容器整理器。范围会过大，也和当前用户要求不符，因此不选。

### 2026-04-13 - 家园场景交互不复活旧直点单位链路

- **背景**：当前工程已明确废弃旧的场景直点单位交互，家园后续如果继续写“点击建筑”但不说明入口，会误导实现方向。
- **方案**：在新文档里先明确“不复活旧 `click-unit`”，后续家园默认使用轻量场景建筑交互层，以 `BuildingId/SlotId` 打开对应 UI。
- **原因**：这样既和当前工程现状一致，也不会把私有基地误写成必须走 `ECA` 的关卡点位系统。
- **替代方案**：继续沿用旧 `click-unit` 语义描述建筑点击。与当前工程不符，因此不选。

### 2026-04-13 - Home 场景默认只有地块，家园内容按数据动态加载

- **背景**：用户补充说明 `Home` 默认只有一块地块，上面没有固定内容，场景里的物品和建筑都要根据家园数据加载。
- **方案**：把需求文档和 UI 文档改为“默认地块/槽位锚点 + 数据驱动加载主城与建筑内容”的结构；同时把“家园默认走 ECA”修正为“家园默认走轻量场景建筑交互层，ECA 只作为可选复用”。
- **原因**：这更符合家园场景，不会把私有基地误建模成关卡点位系统，也能避免把主城模型写死在场景里。
- **替代方案**：继续保留“主城固定预摆”或“家园默认走 ECA”口径。两者都会偏离当前真实需求，因此不选。

### 2026-04-13 - 先补 Home 正式配置源，再进入默认主城初始化与仓库正式页实现

- **背景**：继续往下梳理实现时，发现当前工程还没有 `HomeBuildingConfig / HomeSlotConfig / HomeMainCityLevelConfig` 等正式配置表；现有 `Home` 样机里仍保留 `prototypeIndex + 1` 这种 fallback。
- **方案**：先创建《家园数据驱动加载与仓库正式页设计文档》，明确最小配置集、快照扩展、数据驱动场景加载链路和仓库正式页首版范围；后续实现顺序调整为“先补配置，再写初始化与场景加载”。
- **原因**：如果现在直接写主城/仓库 `ConfigId`、容量和槽位数，只能硬编码，违反项目根规范。
- **替代方案**：先临时硬写主城和仓库，再回头替换成配置。会制造额外返工，也违反当前规范，因此不选。

### 2026-04-13 - Home 首页建造流程改为“先选槽位，再选建筑”

- **背景**：前一版 `LobbyPanel.BuildPanel` 仍然按“点击固定原型按钮 -> 自动选最小空槽位”工作，这和当前正式需求里“玩家决定某个槽位建造什么”不一致。
- **方案**：首页增加 `SelectedHomeSlotId` 选择态，列表区改为“建筑与槽位”，先选中空槽位，再由动态建造入口把建筑落到该槽位。
- **原因**：这样后续无论是首页点击还是场景点击空地，都能复用同一套槽位选择语义，不会继续依赖临时 fallback。
- **替代方案**：只在首页补第 4 个固定建造按钮，继续自动找最小空槽位。这样仍然偏离正式规则，因此不选。

### 2026-04-13 - 建造入口改为按正式配置动态生成

- **背景**：当前可建建筑已经扩到 `大红收藏馆`、`物品回收间`、`农场`、`仓库` 四类，继续保留 3 个固定按钮会让 UI 和配置天然错位。
- **方案**：运行时根据 `HomeBuildingConfig + UnlockedBuildingConfigIds` 动态生成建造按钮池，并按当前槽位兼容类型控制是否可点。
- **原因**：这能彻底移除首页对按钮数量的硬编码，也能支持后续继续加建筑。
- **替代方案**：在 prefab 里手工补第 4 个按钮。短期可用，但还是固定数量结构，因此不选。

### 2026-04-13 - 客户端本地响应同步槽位占用，避免首页闪空

- **背景**：首页升级为槽位驱动后，如果 `ApplyBuildResponse/ApplyDemolish` 只改建筑列表、不改槽位占用，界面会短暂显示“建筑建好了但槽位还空着”。
- **方案**：在客户端本地响应里同步回写 `HomeClientSlotData.BuildingId/BuildingConfigId`。
- **原因**：这能在服务端补发完整快照到达前先保持 UI 连续性。
- **替代方案**：完全等待服务端补快照。这样会有可见闪动，因此不选。

### 2026-04-13 - Home 场景锚点先落在 `HomeSlot.SceneAnchorKey`

- **背景**：`Home.unity` 当前几乎是空场景，没有预摆主城、槽位锚点或 Home 专用挂点；如果继续等待场景资源准备完成，当前正式版 demo 无法跑通。
- **方案**：当前先把槽位坐标直接写入 `HomeSlot.SceneAnchorKey`，格式采用 `x,y,z` 字符串；`statesync` 侧运行时解析坐标并生成主城、建筑、空槽位和锁定位表现。
- **原因**：这样可以在不回滚 Unity 场景、不引入新硬编码配置表的前提下，先跑通数据驱动加载链路。
- **替代方案**：继续等待场景里补锚点或把位置写死在代码里。前者会阻塞当前开发，后者违反当前配置驱动口径，因此不选。

### 2026-04-13 - Home 场景运行时放在 `statesync`，不反向依赖 `home`

- **背景**：家园权威数据和快照属于 `home` 包，但场景表现、点击和 YIUI 联动属于客户端表现层。
- **方案**：在 `statesync` 新增 `HomeSceneRuntimeComponent` 与运行时系统，直接读取 `HomeClientComponent` 快照，并把点击结果回写到 `LobbyPanelComponent.SelectedHomeSlotId / SelectedHomeBuildingId`。
- **原因**：这样依赖方向仍然是 `statesync -> home`，不会让 `home` 包反向引用表现层。
- **替代方案**：把场景表现写进 `home` 包或继续强依赖旧 `click-unit / ECA`。这两条都不符合当前工程分层和家园场景定位，因此不选。

### 2026-04-13 - 回收间最小真链路先复用现有仓储桥与大厅仓库

- **背景**：当前家园最挡体验的不是静态文案，而是 `物品回收间` 还停留在只有 helper、没有请求、没有仓库进出、没有首页操作入口的半成品状态。
- **方案**：扩 `Map2G_HomeStorageOperateRequest`，让 Home -> Gate 仓储桥先支持“单个物品按配置消耗 / 入仓”；回收间在开始回收时消耗仓库里的一个真实物品，完成后再把随机产物放回仓库。
- **原因**：这样可以在不新起独立回收页的前提下，先拿到真实的“取材 -> 等待 -> 入仓”链路，而且仍然复用现有 `Loadout / PlayerStorageComponent` 基础，不会再造一套假仓库。
- **替代方案**：先做纯本地假回收或只回消息不入仓。这样无法验证真实流程，也偏离当前需求，因此不选。

### 2026-04-13 - 首页详情先做建筑专属语义，而不是继续堆通用文案

- **背景**：场景点击和槽位建造已经接通，但右侧详情仍然主要显示通用文字，无法体现主城/回收间/农场/仓库/收藏馆的差异。
- **方案**：继续保留 `LobbyPanel.BuildPanel` 作为临时壳，但把详情状态、提示文案和按钮文案都按建筑类型动态计算。
- **原因**：这样能在不重建独立正式页的情况下，把首页先提升到“能做真实操作和状态判断”的程度。
- **替代方案**：等待独立 `HomePanel` 和建筑详情页资源齐全后再改。这样会继续拖住人工体验闭环，因此不选。

### 2026-04-13 - 主城任务采用“配置 + 累计计数即时计算”，不新建持久化任务实体

- **背景**：主城升级前需要校验当前等级任务组是否全部完成，但当前家园并没有单独的任务状态实体。
- **方案**：新增 `HomeMainCityTask.xlsx` 配置表，只持久化 `回收收取次数 / 农场收取次数 / 收藏馆展示列表` 这些最低必要状态，其余建造数、建筑等级和展示数都按当前家园状态即时计算。
- **原因**：这样状态最少、配置最清晰，也不会再造一套和建筑状态重复的数据。
- **替代方案**：新起完整 `HomeMainCityTaskComponent` 持久化每条任务进度。会增加状态冗余和维护成本，因此不选。

### 2026-04-13 - 收藏馆摆放必须按 `ItemUid` 精确取 1 个单位

- **背景**：收藏馆展示单位要求“每个大红都是独立单位，可摆上去可取下来”，如果沿用按 `ConfigId` 模糊扣减，会在同类多件物品时拿错对象。
- **方案**：扩 `Map2G_HomeStorageOperateRequest`，新增 `TakeWarehouseItemByUid` 操作；收藏馆摆放请求改为传 `ItemUid`，Gate 侧按真实仓库物品取 1 个单位后再放入展示列表。
- **原因**：这样收藏馆管理才是面向真实物品，而不是面向抽象库存数字。
- **替代方案**：继续按 `ConfigId` 扣减仓库物品。会让收藏馆展示对象和仓库真实单位脱节，因此不选。

### 2026-04-13 - 仓库建筑先跳现有正式仓库页，不新起一套假仓库页面

- **背景**：家园需要尽快形成完整人工流程，但当前项目里已经有一套可用的正式仓库页。
- **方案**：点击 Home 里的 `仓库` 建筑时，直接切到现有 `EquipPanel / Warehouse` 页签；同时 Home 内所有会影响金币或仓库的动作成功后，都主动刷新 `Loadout` 快照。
- **原因**：这样仓库状态只维护一套，Home 和 Loadout 不会分裂成两份不同的“仓库真相”。
- **替代方案**：在 Home 里临时再拼一套只读仓库页。短期看似独立，长期会制造双份状态与双份 UI，因此不选。

### 2026-04-13 - 正式页主链路不再继续扩旧 `BuildPanel`

- **背景**：即使首页样机已经可用，继续把主城任务、收藏馆、回收间和仓库都堆在 `LobbyPanel.BuildPanel` 里，会把正式页职责、场景点选和大厅页签继续混在一起。
- **方案**：通过 YIUI MCP 正式生成独立 `HomePanel` 与 `HomeBuildingDetailCard`，把首页/详情/建筑页统一迁到独立家园 Panel。
- **原因**：家园已经是独立场景和独立玩法域，正式页必须有自己清晰的 Panel 边界。
- **替代方案**：继续在 `BuildPanel` 上加子模式。短期省事，但后续维护和资源结构都会继续失控，因此不选。

### 2026-04-13 - Home 场景运行时直接跟 `HomePanel` 选中态同步

- **背景**：场景里主城、建筑和空槽位已经按快照生成，但旧链路仍然把点击结果写回 `LobbyPanel` 的 Home 状态字段。
- **方案**：`HomeSceneRuntimeComponentSystem` 改为直接读写 `HomePanel.SelectedHomeSlotId / SelectedHomeBuildingId`，并在进入/离开 `Home` 场景时自动开关 `HomePanel`。
- **原因**：这样场景交互、正式页刷新和 `Lobby Build` 入口会回到同一条独立主链路，不再依赖历史样机字段。
- **替代方案**：保留 `LobbyPanel` 作为中间转发层。这样会长期同时维护两套 Home 选中态，不选。

### 2026-04-13 - Home 正式页必须显式保留中间场景操作区

- **背景**：独立 `HomePanel` 首版虽然已接通，但资源布局把左栏、右栏和整屏底板铺得过满，玩家视觉上看不到中间场景窗口，点击也容易被 UI 拦截。
- **方案**：把 `HomePanel` 收口为“顶部状态条 + 左侧窄导航 + 中间场景操作区 + 右侧固定详情浮层”，并要求全屏 `Background` 使用低透明且 `raycastTarget = false`。
- **原因**：家园正式页的核心入口仍然是场景点选，布局必须先保证场景可见、可点，再谈详情页承接。
- **替代方案**：在运行时代码里绕过 `EventSystem.current.IsPointerOverGameObject()` 强行点穿 UI。这样会让真正的 UI 点击与场景点击互相污染，因此不选。

### 2026-04-13 - HomePanel 运行时禁止按秒全页重建

- **背景**：独立 `HomePanel` 首版虽然功能都接上了，但页面刷新策略还是“快照一变就把总览、任务、收藏馆、回收间、农场、仓库 6 页全部重建”，进入家园或打开基地时如果仓库物品较多，会直接把主线程压死。
- **方案**：把 `HomePanel` 改为“左侧列表和详情卡始终刷新，但正式页只渲染当前可见页”；农场/回收的时间推进只保留按秒节流的定时刷新；进入 `Home` 和首次打开 Panel 时再额外收掉重复强刷。
- **原因**：家园正式页的性能瓶颈不在单个按钮，而在列表页实例化和 `LayoutRebuilder.ForceRebuildLayoutImmediate(...)` 被同时打到所有页面上。必须先把刷新粒度收口，才能避免再次出现“点基地像卡死”的体验。
- **替代方案**：仅继续压缩 prefab 布局或只改 UI 遮挡。这样解决不了整页列表重建和重复打开的成本，因此不选。

- **解决**：新增系统级文档与 UI 设计文档，把旧首页文档降级为历史稿。

### 2026-04-13 - 新三层文档仍残留旧抽象模块口径

- **现象**：新建的《家园系统需求文档》《家园UI设计文档》里仍把工坊、合同、恢复、出击准备写成当前正式版主模块。
- **原因**：文档重构先完成了结构搭建，但还没有完全接上用户后续连续确认的建筑规则。
- **解决**：本轮按用户已确认规则整段重写为建筑驱动口径，并把 `仓库` 作为优先细化模块。

### 2026-04-13 - 首页样机仍残留 3 个固定建造按钮和“建筑列表”旧语义

- **现象**：即使正式配置和服务端槽位规则已经接入，首页仍然只能显示 3 个固定建造按钮，且列表只展示已建建筑，空槽位和锁定槽位都缺失。
- **原因**：首轮首页样机是为了快速承接基础闭环，UI 结构还停留在“建筑列表 + 原型按钮”阶段。
- **解决**：本轮把首页结构收口为“动态建造入口 + 建筑与槽位列表 + 选槽位再建造”。 

### 2026-04-13 - 独立 `HomePanel` 首版布局把场景点击区挡没了

- **现象**：进入 `Home` 场景后，正式页大面积铺满屏幕，用户几乎只能看到 UI，看不到明确的中间 3D 场景窗口，也难以把点击落到地块或建筑上。
- **原因**：`HomePanel` 首版 Builder 把 `Background` 设计成整屏深色底板，且左右面板占宽过大；虽然运行时代码本身没问题，但视觉和输入上都没有给场景留出操作窗口。
- **解决**：调整 `HomePanelYiuiBuilder`，把背景改为低透明且不拦截射线，左栏收窄，右栏改成固定宽度浮层，详情卡按钮改成自适应三列；随后通过 YIUI MCP 重新生成 `HomePanel.prefab` 与 `HomeBuildingDetailCard.prefab`。

### 2026-04-13 - 点击基地后界面像卡死，真实根因是 HomePanel 首次打开时整页多页签同时重建

- **现象**：用户点击基地按钮后界面长时间无响应，看起来像“Home` 场景又被 UI 挡住了”，但实际上不是射线遮挡，而是主线程被刷新逻辑压满。
- **原因**：`HomePanel.Update` 会持续触发刷新判定；`RenderPages(...)` 又在每次刷新时无条件重建 `总览/任务/收藏馆/回收间/农场/仓库` 六个页面，并对多个列表同时执行 `LayoutRebuilder.ForceRebuildLayoutImmediate(...)`；同时打开 Panel 和进入 `Home` 场景还会出现额外重复强刷。
- **解决**：新增 `NeedTimedRefresh / NextTimedRefreshSecond` 节流字段，只在农场/回收或选中其建筑时按秒刷新；`RenderPages(...)` 改为只渲染当前页；`ForceRebuildLayouts(...)` 改为只重建当前页对应布局；`OpenHomePanelAsync` 和 `AfterCreateCurrentScene_OpenHomePanel` 也补掉首次打开 / 进家园的重复强刷。

### 2026-04-13 - Home 正式配置表最初为空，导表产物也是空数组

- **现象**：`HomeBuilding / HomeSlot / HomeMainCityLevel / HomeBuildingLevel` 四张正式表只有表头，导出的运行时 JSON 也全部为空数组，导致场景运行时没有任何建筑或槽位可读。
- **原因**：前面链路和代码已先接通，但最小正式数据源还没有真正回填。
- **解决**：本轮补齐 4 张表的最小正式数据，修正 Excel 数据列起始位，并重新执行 `dotnet Bin/ET.ExcelExporter.dll Luban`，恢复非空导表。

### 2026-04-13 - `HomeSlot.CanBuildTypes` 的 `array,int` 输入格式不明确

- **现象**：首次导表时，`HomeSlot.xlsx` 里写入的 `2,3,4,5` 被 Luban 判定为“不是 int 类型值”。
- **原因**：当前仓库里没有可直接复用的非空 `array,int` Excel 样例，无法确认本项目实际约定的分隔格式。
- **解决**：当前先把 `CanBuildTypes` 留空，利用现有代码“空数组即允许全部建筑”的语义跑通正式链路，避免继续阻塞场景版本落地。

### 2026-04-13 - `HomeProductionHelper` 与快照 helper 之间形成循环依赖调用链

- **现象**：本轮给回收间补“入仓容量校验”后，`dotnet build ET.sln` 被 ET 分析器拦下，提示 `HomeProductionHelper.CanStoreOutput() -> HomeSnapshotMessageHelper.CreateWarehouseSummary() | HomeSnapshotMessageHelper.CreateSnapshot() -> HomeProductionHelper.RefreshOrders()` 的循环调用链。
- **原因**：容量校验偷懒复用了快照 helper，而快照 helper 又为了刷新订单状态反调了生产 helper。
- **解决**：把回收间的仓库容量计算改回直接扫描仓库建筑等级，不再依赖快照 helper，切断循环链。

### 2026-04-13 - 首页返回概览按钮引入了局部变量重名编译错误

- **现象**：补 `Home` 子模式后，`LobbyPanelComponentSystem_Home.cs` 在 `RefreshPrototypeButtons` 内新增了一个“返回家园概览”按钮，但局部 `selfRef` 名称和后续建造按钮逻辑的局部变量重名。
- **原因**：同一方法内两个局部闭包都沿用了 `selfRef` 命名，触发 C# 作用域冲突。
- **解决**：把子模式返回按钮的闭包引用改名为 `backSelfRef`，重新编译后确认该错误消失，整仓只剩既有旧测试错误。

### 2026-04-13 - 独立 `HomePanel` 首次落地时被 `LoadoutWarehouseItemInfo` 值类型和 ET await 分析器同时卡住

- **现象**：`HomePanelComponentSystem.cs` 首版运行时代码在编译时同时出现两类错误：一类把 `LoadoutWarehouseItemInfo` 当引用类型做 `null` 判断，另一类是在 `await` 后继续直接访问 `Scene/HomePanel`。
- **原因**：仓库页、收藏馆页和回收间页复用 Loadout 数据时忽略了 `LoadoutWarehouseItemInfo` 是 `struct`；同时多段请求后刷新 UI 的代码没有完全按 ET `EntityRef` 规范收口。
- **解决**：仓库物品读取统一改为 `TryGetWarehouseItem(...)`，所有 `await` 后的 `Scene/HomePanel` 都通过 `EntityRef` 回取；修完后 `dotnet build ET.sln` 再次验证，本轮只剩既有旧测试错误。

## 开发总结

- **实际完成**：已补齐 `HomeMainCityTask` 配置表并完成导表；服务端完成主城任务即时计算、主城升级前置校验、收藏馆摆放/取下权威逻辑，以及 Home -> Gate 仓储桥按 `ItemUid` 精确取物；客户端 `Home` runtime 已接通主城任务和收藏馆展示数据；本轮进一步用 YIUI MCP 生成并接入独立 `HomePanel` 与 `HomeBuildingDetailCard`，正式落地 `总览/主城任务/收藏馆网格/独立回收间/农场/Home 专属仓库` 六类页面，`Home` 场景点击、进入/离开场景和 `Lobby Build` 入口都已切到独立 `HomePanel`；同时已把 `HomePanel` 收口为“左窄栏 + 中间场景 + 右侧固定浮层”的正式布局，恢复场景可见与可点，并进一步完成“点击基地卡死”止血：`HomePanel` 现在只重建当前页，农场/回收按秒节流刷新，首次打开/进家园不再重复强刷；`dotnet build ET.sln` 已通过。
- **未完成**：正式场景模型替换、收藏馆/仓库更细的筛选与物品交互、首页/详情动效和更完整的美术表现仍未完成。
- **与设计的偏差**：当前正式页虽然已迁到独立 `HomePanel`，但收藏馆、回收间和仓库仍主要使用按钮卡片/列表页表达，尚未替换为更完整的正式美术组件表现。
- **后续待办**：继续补正式场景资源、美术化建筑表现、收藏馆与仓库更细的物品管理体验，以及更完整的详情页视觉强化。
