# 家园数据驱动加载与仓库正式页设计文档

**创建时间**：2026-04-13  
**最后更新**：2026-04-13  
**状态**：开发中  
**关联任务**：M0.2-W3 #17  
**涉及包**：`cn.etetet.home`、`cn.etetet.statesync`、`cn.etetet.map`、`cn.etetet.item`、`cn.etetet.excel`

## 设计目标

本文档只解决当前家园正式版实现前的三个关键问题：

1. `Home` 场景如何从“默认只有一块地块”过渡到“按家园数据加载主城、建筑和展示物”。
2. 在不违反“绝对禁止 hard code”的前提下，主城、槽位、建筑和仓库能力的配置源应该如何建立。
3. `仓库正式页` 首版最小闭环到底做到什么程度，哪些能力先不做。

本文档不是总需求文档。系统口径仍以 [家园系统需求文档.md](./家园系统需求文档.md) 为准，页面职责仍以 [家园UI设计文档.md](./家园UI设计文档.md) 为准。

## 文档状态更新（2026-04-13）

本文创建时，核心目标是明确 Home 正式配置源和最小实现切口。到 2026-04-13 晚些时候，以下内容已经落地：

1. `HomeBuildingConfig / HomeSlotConfig / HomeMainCityLevelConfig / HomeBuildingLevelConfig` 已建表并导表通过。
2. `M2C_HomeSnapshot` 已补齐槽位、主城摘要、仓库摘要，客户端 `HomeClientComponent` 也已接入。
3. 默认主城初始化、槽位解锁、主城等级上限、仓库摘要与 Gate 仓储桥已经进入运行时。
4. `LobbyPanel.BuildPanel` 首页已从固定原型按钮收口为“选槽位 + 动态建造入口 + 建筑与槽位列表”。

因此，本文中“当前真正阻塞是 Home 正式配置表缺失”的描述已经完成历史使命。当前新的剩余缺口主要是：

1. `Home` 场景里的数据驱动建筑加载层还没正式落地。
2. 主城任务页、仓库正式页、回收间页、收藏馆页还没迁到独立页面体系。
3. 首页虽然已经改成槽位驱动，但仍然暂住在 `LobbyPanel.BuildPanel`，不是最终正式壳。

## 当前现状

结合当前工程，家园链路已经有一批可复用基础：

1. 进入 `Home` 时，地图服已经会调用 `HomeEnterHelper.OnEnterHome(unit)` 并推送 `M2C_HomeSnapshot`。
2. `PlayerHomeComponent`、`HomeBuilding`、`HomeProductionComponent`、`HomeContractComponent` 已存在。
3. 客户端 `HomeClientComponent` 已能接收基础快照。
4. `LobbyPanel.BuildPanel` 已承接首轮 `Home` 首页样机。

但当前正式实现存在 4 个真正阻塞点：

1. **没有 Home 正式配置表**。
2. **主城/仓库/回收间等建筑还没有正式配置来源**。
3. **客户端还没有“根据家园数据加载场景内容”的链路**。
4. **仓库正式页还没有独立数据摘要与独立页面结构**。

## 直接开写代码为什么会违规

当前工程里，`Home` 方向还没有正式的 `HomeBuildingConfig / HomeSlotConfig / HomeMainCityLevelConfig` 等配置表。

这意味着如果现在直接实现：

1. “首次进入自动创建主城”
2. “默认可建仓库”
3. “主城等级 1 解锁几个槽位”
4. “仓库等级 1 有多少格”

就只能把 `ConfigId`、容量、等级、槽位数写死进代码。

这会直接违反项目根规范里的两条硬规则：

1. **绝对禁止 hard code**
2. **配置应走正式表与正式运行时**

所以这轮最小可行切口不是“先硬写主城和仓库”，而是：

1. 先把最小 Home 配置表建立起来。
2. 再把 `Home` 的数据初始化、快照扩展、场景加载和仓库页首版接到这些配置上。

## 正式版最小配置集

为了支持“默认地块 + 数据驱动加载 + 主城任务 + 仓库首版”，当前至少需要 4 张正式配置表。

### 1. HomeBuildingConfig

作用：

1. 定义建筑的基础身份。
2. 告诉系统某个 `ConfigId` 对应的是主城、仓库还是农场。
3. 给场景加载和 UI 提供基础展示语义。

建议字段：

1. `Id`
2. `BuildingType`
3. `Name`
4. `PrefabKey` 或 `SceneVisualKey`
5. `CanRepeat`
6. `SortOrder`
7. `DefaultUnlock`
8. `DefaultSlotType`

当前最小必须覆盖的 `BuildingType`：

1. `MainCity`
2. `Museum`
3. `RecycleRoom`
4. `Farm`
5. `Warehouse`

### 2. HomeSlotConfig

作用：

1. 定义家园地块上的槽位。
2. 解决“场景里有哪些固定锚点”和“某个槽位几点解锁”的问题。

建议字段：

1. `Id`
2. `SlotType`
3. `SceneAnchorKey`
4. `UnlockMainCityLevel`
5. `CanBuildTypes`
6. `SortOrder`

说明：

1. 当前 `Home` 场景默认只有地块和槽位锚点。
2. 场景里不写死哪一块地上是什么建筑，而是根据 `HomeSlotConfig + 家园数据` 动态决定。

### 3. HomeMainCityLevelConfig

作用：

1. 定义主城每级的规则。
2. 承接槽位解锁、其他建筑等级上限、主城升级金币消耗和任务组切换。

建议字段：

1. `Level`
2. `UpgradeGoldCost`
3. `UnlockSlotCount`
4. `OtherBuildingMaxLevel`
5. `TaskGroupId`
6. `PreviewText`

### 4. HomeBuildingLevelConfig

作用：

1. 定义非主城建筑每一级的具体数值。
2. 统一承接收藏馆容量、回收间处理位、农场产金币效率、仓库总格子数。

建议字段：

1. `BuildingConfigId`
2. `Level`
3. `UpgradeGoldCost`
4. `CapacityValue1`
5. `CapacityValue2`
6. `OutputValue`
7. `ExtraParams`

说明：

1. `ExtraParams` 建议在正式表中定义为 `string(JSON)`。
2. 该字段只用于承接不同建筑等级下少量不共用的扩展参数，运行时按 `BuildingType` 解析。
3. 不能把本应独立建字段的核心数值全部塞进 `ExtraParams`。

映射建议：

1. `大红收藏馆`：`CapacityValue1 = 展示容量`
2. `物品回收间`：`CapacityValue1 = 处理位数量`
3. `农场`：`OutputValue = 周期金币`
4. `仓库`：`CapacityValue1 = 总格子数`

## 当前不建议先补的配置

为了控制首版范围，以下配置可以先不落：

1. 完整的建筑图标配置表
2. 完整的建筑剧情文案表
3. 收藏馆单位专属展示配置
4. 回收间复杂配方表

这些都不是当前“默认地块 + 数据驱动加载 + 仓库正式页”最小闭环的阻塞项。

## 服务端数据结构调整

当前 `PlayerHomeComponent + HomeBuilding` 的整体方向是可复用的，不需要推翻，但需要做 3 类补充。

### 1. PlayerHomeComponent

建议新增或明确以下语义：

1. `MainCityBuildingId`
2. `CurrentMainCityLevel`
3. `CurrentTaskGroupId`
4. `UnlockedSlotIds`

说明：

1. 当前只有 `UnlockedBuildingConfigIds` 不足以表达“哪几个槽位开了”。
2. 家园现在是“地块 + 固定槽位 + 建筑实例”，槽位解锁状态必须进权威数据。

### 2. HomeBuilding

当前字段可继续保留：

1. `ConfigId`
2. `Level`
3. `State`
4. `SlotId`
5. `LastCollectTime`
6. `LastProductionTime`

建议补充：

1. `BuildingType` 不必冗余存字段，运行时可通过 `ConfigId` 查 `HomeBuildingConfig`
2. 但建筑内部状态数据应按建筑类型继续外扩，例如：
3. 收藏馆摆放单位列表
4. 回收间处理槽结果
5. 仓库容量摘要或关联容器信息

### 3. 仓库数据

首版不建议在 `HomeBuilding` 内直接塞一堆仓库格子字段。

更合理的方向：

1. 继续复用现有 `item` 体系承接物品存储。
2. `仓库建筑` 只负责提供容量规则与入口语义。
3. `PlayerHomeComponent` 或专门的 `HomeWarehouseComponent` 负责持有与家园仓库容器相关的运行时引用和摘要。

当前首版最小要求：

1. 能根据当前仓库等级算出“总格子数”。
2. 能拿到当前仓库存货列表和已占用格子数。
3. 能让回收间收取动作在仓库满时被正确阻塞。

## 快照协议扩展建议

当前 `M2C_HomeSnapshot` 只有：

1. 家园版本
2. 已解锁建筑配置
3. 建筑列表
4. 生产与合同列表

这不足以支撑正式版家园。

建议最少扩以下 4 组数据：

### 1. HomeSlotInfo

作用：

1. 告诉客户端每个槽位当前是否解锁。
2. 告诉场景层应该生成空槽位还是建筑。

建议字段：

1. `SlotId`
2. `Unlocked`
3. `SceneAnchorKey`
4. `BuildingId`

### 2. MainCitySummary

作用：

1. 告诉首页和主城详情页当前主城状态。

建议字段：

1. `BuildingId`
2. `ConfigId`
3. `Level`
4. `TaskGroupId`
5. `TaskFinishedCount`
6. `TaskTotalCount`
7. `CanUpgrade`

### 3. WarehouseSummary

作用：

1. 告诉首页和仓库页当前仓库容量压力。

建议字段：

1. `BuildingId`
2. `Level`
3. `TotalCellCount`
4. `UsedCellCount`
5. `ItemCount`
6. `Full`

### 4. SceneDisplayInfo

作用：

1. 给客户端场景层一个最小可还原清单。

建议字段：

1. `DisplayType`
2. `ConfigId`
3. `SlotId`
4. `EntityId`
5. `SceneAnchorKey`

说明：

1. 这组数据不是为了替代 `Buildings`。
2. 它的目的是让场景层加载对象时不必自己反推全部逻辑。

## 首次进入 Home 的初始化链路

当前建议把“首次进入创建默认主城和默认槽位状态”放在 `HomeEnterHelper` 内部完成，但数据必须来自正式配置。

正式链路应改为：

1. 玩家进入 `Home`
2. `M2M_UnitTransferRequestHandler` 调用 `HomeEnterHelper.OnEnterHome(unit)`
3. `HomeEnterHelper` 检查 `PlayerHomeComponent`
4. 若为首次进入：
5. 读取 `HomeBuildingConfig / HomeSlotConfig / HomeMainCityLevelConfig`
6. 初始化默认主城数据
7. 初始化默认已解锁槽位
8. 初始化默认仓库/主城摘要所需基础结构
9. 构建正式版快照
10. 推送 `M2C_HomeSnapshot`

关键点：

1. 不是在场景里默认摆一个主城。
2. 而是在家园数据里默认创建“主城建筑实例”。
3. 场景层再根据该数据去加载主城对象。

## 客户端数据应用链路

当前客户端只会把快照写进 `HomeClientComponent`，但没有真正驱动场景层。

正式链路建议如下：

1. `M2C_HomeSnapshotHandler`
2. `HomeClientHelper.ApplySnapshot`
3. `HomeClientComponent` 保存：
4. 建筑实例列表
5. 槽位列表
6. 主城摘要
7. 仓库摘要
8. 发布 `HomeSnapshotChanged` 事件
9. 首页 UI 和场景加载器分别监听事件刷新

这样可以把两个职责拆开：

1. UI 层只关心摘要与选中态。
2. 场景层只关心“现在应该在这个地块上显示什么”。

## 场景数据驱动加载链路

正式版不建议继续把 `Home` 只当成一个 UI 页签。

最小可行实现如下：

### 1. 场景内固定内容

场景里只保留：

1. 家园地块/底座
2. 槽位锚点
3. 建筑加载根节点
4. 交互碰撞或点击承载节点

### 2. 场景运行时加载器

建议新增一层 `HomeSceneRuntime`，职责只有两个：

1. 根据快照在对应 `SlotId/AnchorKey` 下生成或刷新建筑表现对象
2. 维护 `BuildingId/SlotId -> 场景对象` 的映射

### 3. 交互层

建议不要走旧 `click-unit`，也不要默认走完整 `ECA`。

首版家园交互层建议是：

1. 场景对象挂 `BuildingId` 或 `SlotId`
2. 点击后发出本地事件
3. `HomePanel` 接收事件并打开对应详情页

即：

`点击空槽位 -> 打开 HomeBuildSelectPanel`

`点击主城 -> 打开 MainCityDetail`

`点击仓库 -> 打开 HomeWarehousePanel`

## 仓库正式页首版范围

当前 `仓库正式页` 先收敛成“家园存储总览页”，不做背包整理器。

### 必做

1. 展示仓库等级
2. 展示总格子数
3. 展示已占用格子数
4. 展示剩余格子数
5. 展示当前库存列表
6. 展示物品来源摘要
7. 在容量不足时给出阻塞提示

### 不做

1. 复杂拖拽整理
2. 跨容器批量搬运
3. 多维过滤器
4. 排序策略编辑
5. 仓库内直接装备/拆分/丢弃

### 首页联动

首页至少要能读到：

1. `仓库等级`
2. `已占用 / 总格`
3. `是否快满`

## 最小实现顺序

当前建议按以下顺序推进，而不是并行全做：

1. 建 Home 最小配置表
2. 改 `HomeEnterHelper`，接首次进入默认主城初始化
3. 扩 `M2C_HomeSnapshot` 与客户端 `HomeClientComponent`
4. 增加 `HomeSceneRuntime`，接数据驱动加载
5. 独立仓库摘要与 `HomeWarehousePanel`
6. 首页接仓库摘要与主城摘要

## 当前结论

当前真正可直接进入代码实现的前置条件只有一个：

**先补 Home 正式配置源。**

如果不先补这个前置，就只能把：

1. 主城配置
2. 槽位解锁
3. 仓库容量
4. 建筑等级上限

全部硬写进代码，这不符合当前项目规范。

因此，本轮最小正确切口是：

1. 先补 Home 最小配置表设计
2. 再接首次进入默认主城初始化
3. 再做数据驱动场景加载
4. 最后做仓库正式页

## 2026-04-13 实现回写

本轮已经按上面的最小顺序完成到“数据驱动场景加载”这一步，当前实际落点如下：

1. `HomeBuilding.xlsx / HomeSlot.xlsx / HomeMainCityLevel.xlsx / HomeBuildingLevel.xlsx` 已补最小正式数据，并重新跑通 `dotnet Bin/ET.ExcelExporter.dll Luban`。
2. `HomeSlot.SceneAnchorKey` 当前实际采用 `x,y,z` 坐标字符串，用来承载空场景下的临时槽位锚点。
3. `statesync` 已新增 `HomeSceneRuntimeComponent`，在进入 `Home` 当前场景后按 `HomeClientComponent` 快照运行时生成主城、已建建筑、空地块和锁定地块。
4. 场景对象点击后会回写 `LobbyPanelComponent.SelectedHomeSlotId / SelectedHomeBuildingId`，现有首页详情区和建造入口会同步刷新。
5. 当前 Home 场景仍然使用程序化几何体做占位表现，后续接入正式模型和锚点后，可继续复用这条数据驱动链路。
6. `Map2G_HomeStorageOperateRequest` 已扩到支持单个仓库物品的消耗与入仓，回收间最小真链路已能复用现有大厅仓库。
7. `LobbyPanel.BuildPanel` 右侧详情已改为建筑专属状态与按钮语义，回收间可直接从仓库取一个真实物品开始回收，并在完成后把随机产物放回仓库。
