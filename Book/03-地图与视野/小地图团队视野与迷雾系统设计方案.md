# 小地图团队视野与迷雾系统设计方案

## 1. 文档目标

- 为局内折叠小地图与展开大地图提供统一设计方案。
- 将团队共享视野、迷雾记忆、小地图动态点位纳入同一套权威架构。
- 明确哪些能力本次就做，哪些能力预留后续扩展，避免前后返工。

## 2. 当前已确认需求

### 2.1 小地图形态

- 小地图分为两种形态：
  - 折叠态：显示玩家附近范围。
  - 展开态：显示整张地图范围。
- 小地图固定北朝上，不随玩家朝向旋转。
- 当前阶段不支持点击小地图。
- 后续技能可能需要“小地图选点施法”，本次需要为该能力预留结构。

### 2.2 点位与显示

- 小地图点位必须是动态的，怪物、玩家移动时需要同步更新。
- 需要精确区分：
  - 自己
  - 友军玩家
  - 敌军玩家
  - 怪物
  - 后续的 Boss
  - 可选的中立/NPC/战术单位

### 2.3 视野与迷雾

- 小地图显示受距离和 AOI 限制。
- 视野与迷雾要与小地图一起设计，而不是后补。
- 玩家与队友共享一套视野。
- 本次先不做复杂材质效果，但要把迷雾底层数据结构和同步链路一起定下来。
- 草丛/遮蔽场景下，如果某个队友合法看见目标，则该目标应进入团队共享视野，小地图对全队可见。

- 当前 Boss 尚未定义，不能把 Boss 判断硬编码到 `Monster` 逻辑里。

## 4. 核心设计结论

### 4.1 小地图和视野/迷雾必须一起设计

原因：

- 小地图最终显示什么，取决于团队当前可见与已探索结果。
- 如果先只做 UI，不把团队共享视野和迷雾边界定义清楚，后续加入共享视野时一定会重构同步链路。
- 当前项目已经存在 AOI、遮蔽、Ward、Detector 等多种可见性来源，不能再按“客户端拿到什么就画什么”的简单方式继续扩展。

### 4.2 YIUI 负责 UI 外壳，运行时状态独立

推荐原则：

- `YIUI` 负责：
  - 折叠小地图组件
  - 展开大地图面板
  - 交互入口和数据绑定
- 独立运行时组件负责：
  - marker 缓存
  - 视野数据缓存
  - 迷雾数据缓存
  - 世界坐标与小地图坐标换算

不推荐：

- 把视野计算和 marker 真相直接塞进 `MainPanelComponentSystem`
- 把每个动态点位都做成重量级 YIUI 逻辑实体

### 4.3 小地图应复用现有单位可见性同步链路

本次修订后的推荐原则：

- 单位是否存在、单位位置、单位朝向，优先复用现有单位同步链路。
- 小地图单独新增的同步内容，只包含：
  - 迷雾相关数据
  - marker 元信息
  - 小地图配置

原因：

- 现有 `M2C_CreateUnits/M2C_RemoveUnits` 已经承载了 AOI、额外视野、遮蔽后的最终可见结果。
- 如果再为每个 marker 建一套独立位置同步，会产生双份真相和双份带宽开销。

### 4.4 迷雾首版采用“服务端权威可见性 + 客户端计算表现”

首版建议：

- 服务端继续权威决定“团队当前能看见哪些单位”。
- 客户端根据：
  - 友方玩家位置
  - 共享视野源位置
  - 小地图配置
  本地计算迷雾贴图表现。

这样可以显著降低首版复杂度，同时不破坏现有可见性权威链路。

前提条件：

- 客户端必须始终拿到同阵营队友的位置。
- 如果现有主画面链路无法保证远处队友位置可用，则需要补一条“同阵营玩家始终互相可见/始终同步”的规则。

## 5. 总体架构

### 5.1 分层职责

#### 规则层

- 服务端基于现有 `TacticalVisionComponent` / `TacticalVisionHelper` 聚合队伍/阵营视野。
- 计算团队当前可见区域。
- 统一处理 Ward、Detector、遮蔽、AOI 等可见性来源。

#### 同步层

- 向客户端下发小地图初始化数据。
- 向客户端下发小地图所需的补充元数据。
- 向客户端下发迷雾初始化参数。

#### 运行时层

- 客户端缓存 marker、地图参数、迷雾数据。
- 对折叠态与展开态提供统一查询接口。

#### UI 层

- 折叠态小地图组件。
- 展开态全图面板。
- 后续小地图选点交互。

### 5.2 推荐组件拆分

#### 服务端

- `TacticalVisionComponent`
  - 继续作为地图级战术视野驱动组件。
  - 本次不平行新增语义相同的 `TeamVisionComponent`。
  - 通过扩展现有 `TacticalVisionComponent` / `TacticalVisionHelper` 承担团队共享视野聚合职责。

- `FogOfWarComponent`
  - 地图级组件。
  - 首版可以只维护必要的团队迷雾状态缓存。
  - 如果首版采用客户端迷雾计算表现，则该组件可先收缩为配置与共享视野源辅助数据，不强制服务端维护完整网格。

- `MinimapSyncComponent`
  - 地图级组件。
  - 首版不强制要求成为独立长生命周期组件。
  - 如果后续只负责“小地图初始化参数整理与下发”，可先降级为 `Helper` 或进入地图初始化流程中的一段逻辑。
  - 只有在后续明确需要维护独立脏标记、地图切换缓存、专用初始化状态时，再升级为独立组件。

#### 客户端

- `MinimapRuntimeComponent`
  - 客户端运行时组件。
  - 缓存地图边界、marker 列表、当前可见网格、已探索网格、显示模式。

- `MinimapComponent`
  - 折叠态 YIUI 子组件。
  - 负责附近范围小地图显示。

- `WorldMapPanel`
  - 展开态 YIUI Panel。
  - 负责整张地图显示。

## 7. 团队共享视野设计

### 7.1 共享原则

- 共享单位：同一 `CampId` 的玩家。
- 共享内容：
  - 玩家自身主视野
  - 队友主视野
- 队友放置的 Ward 视野
- 队友的 Detector 揭露能力
- 遮蔽规则依然生效，不能因为共享视野直接绕开底层隐藏逻辑。

这里的“玩家自身主视野”和“队友主视野”是明确要求，不是仅共享 Ward/Detector 的缩水版。

### 7.2 遮蔽与团队共享视野交互规则

团队共享视野的推荐规则：

1. 先按单个观察者计算其合法可见结果。
2. 再将同一 `CampId` 下所有观察者的合法可见结果做并集。
3. 并集结果即为团队视野结果。

这意味着：

- 如果队友 A 因为自身位置、Ward 或 Detector 合法看到目标 X，
- 即使队友 B 自己本地看不到 X，
- B 的小地图也应显示 X，因为团队视野已经覆盖该目标。
- 该规则同样适用于草丛/遮蔽场景，这是当前明确确认的设计预期。

### 7.3 推荐可见性来源

- `AOI` 原生视野
- `ExtraUnitVisibilityComponent` 提供的额外可见目标
- `TacticalVisionHelper` 提供的 Ward/Detector 结果
- 后续扩展：
  - 技能显形
  - 烟雾/隐身
  - Boss 侦测

### 7.4 当前可见结果

建议优先复用服务端现有“最终单位可见结果”，不要在首版额外维护一套独立的完整 `VisibleUnitIds + VisibleCells` 权威网格真相。

但需要明确：

- 当前现有链路主要覆盖“单观察者最终可见结果”。
- 为满足“同队主视野并集 = 团队视野”，首版需要扩展现有 `TacticalVisionHelper`，将同阵营玩家 AOI 主视野结果纳入团队共享视野。

## 8. 迷雾设计

### 8.1 迷雾状态划分

- `CurrentVisible`
  - 当前团队视野覆盖区域。
- `Explored`
  - 本局当前地图副本中，团队曾经探索过的区域。
- `Unexplored`
  - 尚未探索区域。

### 8.2 展示规则

#### 折叠态

- 背景只显示附近窗口。
- marker 仅显示当前团队可见目标。
- 首版可以不做复杂迷雾遮罩材质。

#### 展开态

- 显示整张地图底图。
- 当前可见区域正常亮度。
- 已探索但当前不可见区域降低亮度。
- 未探索区域显示为黑色。

### 8.3 首版实现策略

首版推荐：

- 服务端权威决定单位可见性。
- 客户端本地根据共享视野源计算迷雾表现。
- 迷雾表现不要求首版即具备完整服务端网格同步。

### 8.4 生命周期

- 迷雾记忆只在当前地图副本内有效。
- 玩家离开当前地图副本后清空。

## 9. Marker 设计

### 9.1 建议的通用枚举

建议预留显式 marker 类型，而不是通过 `UnitType` 和 `ConfigId` 硬编码推断：

- `Self`
- `FriendlyPlayer`
- `EnemyPlayer`
- `Monster`
- `Boss`
- `NeutralNpc`
- `FriendlyNpc`
- `Ward`
- `Objective`

### 9.2 MarkerType 归属

首版推荐由客户端推导 `MarkerType`，而不是服务端专门同步。

推导依据包括：

- `UnitType`
- `ConfigId`
- `CampComponent` / 阵营数值
- 后续补充到 `UnitConfig` 的显式小地图标记字段

这样可以减少专门的 marker 类型同步成本。

### 9.3 Boss 预留策略

- 当前 Boss 尚未实现。
- 本次不做 Boss 特化逻辑。
- 但同步结构和 UI 映射中应保留 `Boss` 类型扩展位。
- 后续 Boss 可以是：
  - 独立 `UnitType`
  - `Monster` 下的子类型
  - 配置驱动的显式 marker 类型

本方案推荐第三种，即显式配置驱动。

### 9.4 残影/最后已知位置

- 本次不作为首版强制需求。
- 但建议在运行时结构中预留“最后一次被团队看见的位置与时间戳”扩展位，便于后续实现展开态残影显示。

## 10. 小地图配置设计

建议新增一套小地图配置，按地图维度提供：

- `MapName`
- `TextureName`
- `WorldMinX`
- `WorldMaxX`
- `WorldMinZ`
- `WorldMaxZ`
- `CompactRange`
- `FogCellSize`

### 10.1 作用

- 为客户端提供世界坐标转小地图坐标所需的边界。
- 为展开态和折叠态共用同一份坐标映射逻辑。
- 为迷雾网格提供统一精度。

说明：

- `FogGridWidth` 与 `FogGridHeight` 可通过世界边界和 `FogCellSize` 推导，不建议额外做成源配置，避免配置不一致。

## 11. 客户端运行时设计

### 11.1 `MinimapRuntimeComponent` 职责

- 保存当前地图的小地图配置。
- 保存当前模式：
  - `Compact`
  - `Expanded`
- 保存 marker 字典。
- 保存迷雾当前可见网格和已探索网格。
- 预留“最后已知位置”缓存扩展位。
- 提供：
  - 世界坐标转展开态地图坐标
  - 世界坐标转折叠态局部坐标
  - marker 可见性过滤

### 11.2 为什么不要把 runtime 放进 YIUI

- 折叠态与展开态需要共享同一份真相。
- 后续可能出现“切换面板但不销毁状态”的需求。
- 后续小地图选点施法也需要复用坐标换算与 marker 查询。

## 12. UI 设计建议

### 12.1 折叠态

- 做成 `MainPanel` 下的 YIUI 子组件。
- 玩家箭头固定在中心。
- 背景固定北朝上。
- 周围 marker 按玩家附近范围裁剪。

### 12.2 展开态

- 单独做 `WorldMapPanel`。
- 同样固定北朝上。
- 不支持点击。
- 展示整张地图和迷雾状态。

### 12.3 Marker 表现

- 建议不要让每个 marker 都成为重量级 YIUI 逻辑实体。
- 推荐：
  - 外层容器是 YIUI
  - marker 视图走轻量 prefab + 对象池

## 13. 同步设计建议

### 13.1 初始化同步

玩家进入地图后，下发：

- 小地图配置
- 当前已可见单位所需的 marker 元信息全量
- 迷雾初始化参数

### 13.2 增量同步

后续只同步变化：

- marker 元信息新增
- marker 元信息移除
- marker 类型变化
- 必要的迷雾辅助数据变化

说明：

- 单位的位置、朝向、创建、移除，优先复用现有单位同步链路。
- 小地图侧不再额外复制一套完整位置同步。

### 13.3 Marker 更新频率与精度建议

首版建议：

- 小地图 marker 位置刷新依赖客户端已同步到的单位位置。
- 不单独增加高频网络推送。
- 如果后续要增加独立 marker 运动体，再评估：
  - 更新频率：建议不高于现有关键移动同步频率
  - 精度：优先使用降精度地图坐标，而不是额外全精度 `float3`

### 13.4 不建议的做法

- 不建议为小地图 marker 再建一套完整的单位位置同步通道。
- 不建议由客户端自行推导团队视野真相。

## 14. 推荐实施顺序

### 第一阶段：底层打通

1. 补小地图配置结构。
2. 扩展现有 `TacticalVisionComponent`，明确团队共享视野聚合职责。
3. 定义小地图初始化与元信息同步协议。
4. 搭建客户端迷雾本地计算所需的数据结构。
5. 增加客户端 `MinimapRuntimeComponent`。

其中第 2 步建议细化为：

1. 在现有视野聚合流程中，明确“同阵营玩家主视野并集 = 团队视野”。
2. 评估并实现“同阵营玩家始终互相可见/始终同步位置”的前提条件。
3. 复用 `ExtraUnitVisibilityComponent.ResetViewerTargets()` 的现有 diff 逻辑，避免频繁创建/移除抖动。
4. 视野聚合 Tick 频率首版建议继续复用现有战术视野刷新节奏，避免并行引入第二套高频 Tick。

### 第二阶段：先跑通 UI

1. 接折叠态 `MinimapComponent`。
2. 接展开态 `WorldMapPanel`。
3. 先使用简单迷雾视觉。

### 第三阶段：扩展玩法

1. 小地图点击选点施法。
2. Ward/Boss/Objective 特殊图标。
3. 更复杂的迷雾材质和过渡表现。

## 15. 当前方案的收益

1. 小地图与团队共享视野从一开始就是一套结构，不会后补返工。
2. 复用现有可见性同步链路，避免重复造轮子。
3. 迷雾逻辑与 UI 表现解耦，便于逐步落地。
4. YIUI 继续负责 UI 外壳，符合当前项目结构。
5. Boss、战术道具、小地图施法都能在现有方案上平滑扩展。

## 16. 当前明确不做的内容

- 小地图点击交互
- Boss 特化逻辑
- 复杂迷雾材质表现
- 大量额外视觉特效

这些能力都在当前方案中预留了结构，但不作为首批落地内容。
