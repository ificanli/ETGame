# 搜索界面三模式需求与方案说明

## 1. 需求背景

当前项目里已经有一个 `SearchPanel`，但它的实现还是固定的“双栏容器 + 背包”搜索界面。

现在需要把搜索界面扩展成 3 种打开情况，并且 3 种情况下界面样式要明显不同：

1. 搜索容器
2. 直接点开背包
3. 搜索尸体

其中“搜索尸体”还要考虑玩家尸体和怪物尸体后续可能存在表现差异的问题。

## 2. 你的需求

本次需求的核心不是简单换个标题，而是让同一个搜索能力可以在不同打开来源下，表现出不同的界面结构和视觉样式。

具体需求可以整理为：

1. 搜索界面要支持 3 种打开模式。
2. 3 种模式的 UI 样式不能完全一样。
3. 背包、容器、尸体这 3 类来源的逻辑和展示要能区分。
4. 后续玩家尸体和怪物尸体最好还能继续细分表现，但不希望把代码结构做得越来越乱。

## 3. 当前现状

### 3.1 当前 `SearchPanel` 的问题

当前 `SearchPanel` 逻辑是写死的：

1. 一打开就按“左边容器，右边背包”渲染。
2. 刷新时固定执行 `RenderContainer` 和 `RenderBag`。
3. 组件里没有“当前打开模式”“当前来源类型”“当前样式类型”这些抽象字段。

这意味着：

1. 如果直接在现有代码里加很多 `if else`，很快会变成难维护的面板。
2. 如果直接拆成 3 个完全独立 Panel，又会复制大量格子、拖拽、渲染、拿取逻辑。

### 3.2 当前入口现状

目前至少已经确认有两条相关入口：

1. 容器交互通过 `OpenContainerUI` 链路打开 `SearchPanel`。
2. 主界面背包按钮也是直接打开 `SearchPanel`。

也就是说，`SearchPanel` 已经天然承担了“多来源打开”的角色，只是现在没有模式抽象。

### 3.3 当前尸体链路的一个实际缺口

普通容器的 ECA 资产里，`OpenContainerUI` 节点已经配置了 `ui_key = SearchPanelComponent`。

但当前玩家尸体的服务器流程里，虽然也创建了 `OpenContainerUI` 节点，却没有带 `ui_key`。

客户端这边如果 `ui_key` 为空，会直接跳过打开 UI。

所以尸体要稳定复用 `SearchPanel`，至少还要把尸体打开链路的 `ui_key` 补上。

## 4. 推荐方案

### 4.1 总体方案

推荐做法：

**保留 1 个 `SearchPanel`，增加“打开模式”和“尸体子类型”抽象，用同一套格子与拖拽逻辑复用数据交互能力，再通过模式切换界面结构和视觉样式。**

同时，UI 结构不建议一开始就拆成 3 套完全独立布局。更合适的是：

1. 容器搜索和尸体搜索共用一套双栏布局。
2. 背包查看单独使用一套单栏布局。
3. 普通容器、尸体、地面掉落等差异，优先通过标题、背景、图标、装饰样式切换实现。

不推荐的做法：

1. 不推荐拆成 3 个完全独立的 Panel。
2. 不推荐继续在当前面板里直接堆大量分散的 `if else`。
3. 不推荐把 `ui_key` 同时拿来做“打开哪个面板”和“面板内部模式传参”两件事。

### 4.2 模式设计

推荐定义 3 个主模式：

1. `ContainerSearch`
2. `BackpackInspect`
3. `CorpseLoot`

尸体模式再增加子类型：

1. `Unknown`
2. `Player`
3. `Monster`
4. `Boss`
5. `Npc`

一期实际只用到 `Player` 和 `Monster`，但枚举值建议预留，后续不用再推翻设计。

另外需要明确：

1. 左右区域内容由 `OpenMode` 推导，不单独存 `LeftPanelKind` / `RightPanelKind`。
2. 容器和地面掉落的差异，优先复用现有运行时的 `ContainerOutputMode`，不额外新增一套重复的容器子类型。

这样做的好处是：

1. 主模式数量稳定，不会模式爆炸。
2. 玩家尸体和怪物尸体可以做不同标题、图标、边框色、文案。
3. GroundDrop 这类容器差异可以沿用现有运行时字段，不增加无谓概念。
4. 代码层仍然保持“同一类界面逻辑”的抽象。

## 5. 方案拆解

### 5.1 数据层改法

建议在 `SearchPanelComponent` 中增加纯数据字段，不要在 Entity 里写逻辑方法。

建议增加：

1. `OpenMode`
2. `CorpseSubType`
3. `CurrentPointId`
4. `TitleText`
5. `SubTitleText`

用途如下：

1. `OpenMode`：决定当前是容器、背包还是尸体模式。
2. `CorpseSubType`：决定当前尸体是玩家、怪物还是后续扩展类型。
3. `CurrentPointId`：记录当前容器或尸体对应的交互点。
4. `TitleText`：供 UI 主标题直接使用。
5. `SubTitleText`：供 UI 副标题或来源标记使用。

不建议增加：

1. `LeftPanelKind`
2. `RightPanelKind`

因为三种模式下左右区域内容是确定的，单独保存只会形成冗余状态和不一致风险。

### 5.2 打开参数传递方式

这一点必须在方案里先定死，否则真正实现时第一步就会卡住。

推荐做法：

1. `ui_key` 只负责决定打开哪个面板，继续保持 `SearchPanelComponent`。
2. 新增一个场景级的打开上下文组件，例如 `SearchPanelOpenContextComponent`，只存“这次准备怎么打开”的纯数据。
3. 所有入口先写入这个上下文，再统一打开 `SearchPanel`。
4. `SearchPanel` 在 `YIUIOpen` 时读取并消费上下文，确定当前模式和样式。

推荐的来源写入方式如下：

1. 背包按钮：点击背包时直接写入 `BackpackInspect`，然后打开 `SearchPanel`。
2. 普通容器：在容器打开消息到客户端后，写入 `ContainerSearch`。
3. 尸体容器：在容器打开消息到客户端后，写入 `CorpseLoot`，并附带 `CorpseSubType`。

关于尸体来源识别，推荐优先级如下：

1. 最稳妥方案：协议或运行时显式下发来源类型。
2. 过渡方案：临时根据 `pointId` 规则，例如 `corpse_` 前缀识别。

需要额外注意：

1. 当前尸体链路还缺少 `ui_key`，必须补成 `SearchPanelComponent`，否则客户端不会打开 UI。

### 5.3 逻辑层改法

建议把当前 `TryRefreshView()` 拆成“上下文解析 + 模式调度 + 区域渲染 + 样式应用”四层。

推荐拆分为：

1. `ResolveOpenContext()`
2. `RefreshViewByMode()`
3. `ApplyModeStyle()`
4. `RenderLeftAreaByMode()`
5. `RenderRightAreaByMode()`

职责建议如下：

1. `ResolveOpenContext()`：读取这次打开模式、尸体子类型和标题来源。
2. `RefreshViewByMode()`：根据模式决定这次界面整体怎么刷新。
3. `ApplyModeStyle()`：只处理标题、背景、显隐、按钮样式，不处理物品业务。
4. `RenderLeftAreaByMode()`：根据 `OpenMode` 决定左边是容器、尸体内容，还是隐藏。
5. `RenderRightAreaByMode()`：根据 `OpenMode` 决定右边是背包还是隐藏。

另外还要同步处理两个容易漏掉的逻辑点：

1. 背包单栏模式下，不应该继续让隐藏的容器区域参与拖拽落点计算。
2. 退出逻辑不能再只看“有没有 `OpenContainerPointId`”，而要看当前 `OpenMode` 是不是容器类模式。

### 5.4 UI 层改法

推荐保留一个 `SearchPanel.prefab`，但不要一开始就做 3 套完整根节点。

更合适的是做 2 套根节点：

1. `ModeRoot_DualPane`
2. `ModeRoot_BagOnly`

其中：

1. `ModeRoot_DualPane`：给容器搜索和尸体搜索共用。
2. `ModeRoot_BagOnly`：给背包查看单独使用。

在 `ModeRoot_DualPane` 下，通过样式切换实现：

1. 普通容器风格
2. 尸体风格
3. GroundDrop 风格预留

建议预制体内预留这些公共节点：

1. 主标题
2. 副标题
3. 来源图标
4. 背景图
5. 左区域标题
6. 右区域标题
7. 双栏快捷按钮区

这样做的好处是：

1. UI 改 prefab 更直观。
2. 程序只负责切显隐和填数据，不需要大量改坐标和锚点。
3. 背包查看布局和双栏布局拆开后，代码复杂度不会失控。
4. 如果以后尸体真的需要完全不同的布局，再补第三套根节点也不晚。

### 5.5 关闭时机与关闭来源

三种模式的关闭条件不完全一样，必须在方案里明确：

#### 容器搜索 `ContainerSearch`

关闭条件：

1. 玩家手动点击关闭。
2. 玩家离开交互范围，客户端收到离开范围事件后自动关闭。
3. 容器主动关闭或失效时强制关闭。

#### 背包查看 `BackpackInspect`

关闭条件：

1. 只允许手动关闭。
2. 不走 `CloseContainer` 链路。
3. 不依赖交互范围和容器运行时。

#### 尸体搜索 `CorpseLoot`

关闭条件：

1. 玩家手动点击关闭。
2. 玩家离开交互范围自动关闭。
3. 尸体对应交互点被销毁、尸体消失或服务端强制关闭时自动关闭。

### 5.6 三种模式的具体表现建议

#### 容器搜索 `ContainerSearch`

建议表现：

1. 左侧显示容器内容。
2. 右侧显示玩家背包。
3. 保留快捷筛选、快速拾取等搜索相关功能。
4. 标题和背景走“普通搜索容器”风格。
5. 如果 `ContainerOutputMode` 是 `GroundDrop`，仍然归入该模式，只切地面掉落对应的标题和图标。

#### 背包查看 `BackpackInspect`

建议表现：

1. 只显示背包区域。
2. 背包区居中或放大显示。
3. 隐藏左侧容器区。
4. 隐藏箭头、快速拾取、容器标题等仅在搜索场景下有意义的节点。

这样用户感知会更明确：这是“看自己的包”，不是“搜东西”。

#### 尸体搜索 `CorpseLoot`

建议表现：

1. 左侧显示尸体容器内容。
2. 右侧显示玩家背包。
3. 整体仍然是双栏，但标题、图标、底图、边框风格与普通容器不同。
4. 玩家尸体和怪物尸体在同一个模式下，通过副标题、图标或边框色继续区分。

例如：

1. 玩家尸体：偏“战利品/身份来源”风格。
2. 怪物尸体：偏“搜刮/掉落物”风格。

## 6. 为什么这是更合适的方案

### 6.1 比拆 3 个 Panel 更合适

因为三种界面的底层能力其实高度相同：

1. 格子布局
2. 物品渲染
3. 拖拽移动
4. 背包显示
5. 容器显示

如果拆 3 个 Panel，这些逻辑会重复，后续改一个 bug 往往要改 3 处。

### 6.2 比直接在现有代码里乱加判断更合适

如果只是在当前 `SearchPanel` 里继续硬塞判断：

1. 逻辑会分散在刷新、拖拽、点击、退出等多个地方。
2. UI 显隐会越来越难追踪。
3. 后面再加第 4 种表现时，很容易继续膨胀。

而“单面板 + 3 个打开模式 + 2 套布局根节点”的方式，结构会清楚很多。

## 7. 实施建议顺序

推荐按下面顺序推进，返工最少：

1. 先补 `SearchPanelOpenMode`、`CorpseSubType` 和场景级打开上下文组件。
2. 再补背包入口、容器入口、尸体入口对上下文的写入。
3. 再补尸体链路的 `ui_key`，并补来源类型的稳定识别方式。
4. 然后拆 `SearchPanel` 的模式调度、关闭逻辑和刷新逻辑。
5. 最后改 `SearchPanel.prefab`，增加双栏根节点、单栏根节点和对应样式绑定。

## 8. 具体落地建议

如果后续要正式开工，建议按下面规则执行：

1. `Entity` 只存模式和状态数据。
2. `System` 负责模式切换、视图刷新、样式应用。
3. `ui_key` 只做面板路由，不做内部模式传参。
4. 格子和拖拽逻辑尽量复用，不要为每个模式复制一套。
5. GroundDrop 这类容器差异优先复用现有 `ContainerOutputMode`。
6. 尸体子类型建议用预留值的 enum，不建议直接退化成裸 `int`。
7. 如果一期赶时间，尸体来源可以先按 `pointId` 规则识别，二期再补稳定协议字段。

## 9. 最终结论

本需求最合适的实现方式是：

**保留一个 `SearchPanel`，把它升级为“支持多打开模式的统一搜索面板”，用模式枚举区分容器搜索、背包查看、尸体搜索；容器搜索和尸体搜索共用双栏布局，背包查看单独使用单栏布局；`ui_key` 只负责打开 `SearchPanelComponent`，真正的模式和尸体子类型通过独立上下文传递。**

这样做的优势是：

1. 结构清晰。
2. 复用度高。
3. UI 可维护性更好。
4. 参数职责明确，不会把面板路由和内部状态搅在一起。
5. 后续继续扩展风险更低。
