# 范围遮蔽可见性架构说明

## 目标

把“草丛隐藏”从具体业务语义抽象为通用的“范围遮蔽可见性”能力，避免后续烟雾、隐身类技能继续复用 `Bush` 命名或在 `map` 包里堆业务特化代码。

## 设计原则

1. `ecanode` 负责业务入口。
草丛、范围交互点等场景玩法，仍然通过 ECA Flow 的 `ApplyStealth` / `RemoveStealth` 触发。

2. `map` 负责权威可见性底层。
服务端最终是否给客户端发创建、移除、同步消息，统一在 `map` 层做权威过滤。

3. `aoi` 不承载业务语义。
本次没有把草丛、烟雾、隐身之类业务规则直接塞进 `cn.etetet.aoi`。

4. 客户端本地显示只做表现。
“自己看自己半隐身”由客户端根据导出的 ECA 配置本地判断，不影响服务端权威可见性。

## 当前分层

### 业务层

- 草丛仍然是一个 `RangeTrigger + FlowGraph` 方案
- 示例资源：`GrassBushFlow.asset`
- 触发链路：
  - `OnPlayerEnterRange -> ApplyStealth`
  - `OnPlayerLeaveRange -> RemoveStealth`

### 通用底层

服务端通用遮蔽能力位于：

- `Packages/cn.etetet.map/Scripts/Model/Server/ExtraUnitVisibilityComponent.cs`
- `Packages/cn.etetet.map/Scripts/Hotfix/Server/ExtraUnitVisibilityComponentSystem.cs`

核心数据结构：

- `ConcealmentSourceToPlayers`
  - 某个遮蔽来源当前覆盖了哪些玩家
- `PlayerToConcealmentSources`
  - 某个玩家当前处于哪些遮蔽来源中
- `ViewerToConcealedTargets`
  - 某个观察者当前被隐藏了哪些目标

核心接口：

- `SetPlayerConcealmentState`
- `ShouldConcealTargetFromViewer`
- `IsTargetConcealed`
- `MarkTargetConcealed`

## 权威同步位置

服务端与 AOI 的耦合只发生在“消息出口层”，不发生在 AOI 核心算法层。

### 进入视野时

文件：

- `Packages/cn.etetet.map/Scripts/Hotfix/Server/Unit/UnitEnterSightRange_NotifyClient.cs`

行为：

- AOI 触发进入视野事件
- `map` 层判断该目标是否应该被遮蔽
- 如果应遮蔽，则不发送 `NoticeUnitAdd`

### 广播消息时

文件：

- `Packages/cn.etetet.map/Scripts/Hotfix/Server/MapMessageHelper.cs`

行为：

- 广播给观察者前再次检查 `IsTargetConcealed`
- 避免出现“对象没创建，但后续消息还在发”的异常状态

### 判断 AOI 原本是否可见

文件：

- `Packages/cn.etetet.map/Scripts/Hotfix/Server/ExtraUnitVisibilityComponentSystem.cs`

行为：

- 使用 `AOIEntity.GetSeeUnits()` 判断该目标是否属于 AOI 原生可见
- 遮蔽解除时，只在 AOI 原本可见的前提下补发创建消息

## 客户端表现

客户端本地遮蔽表现位于：

- `Packages/cn.etetet.map/Scripts/Model/Client/ECAInteractClientComponent.cs`
- `Packages/cn.etetet.map/Scripts/Hotfix/Client/ECAInteractClientComponentSystem.cs`
- `Packages/cn.etetet.map/Scripts/HotfixView/Client/Unit/GameObjectComponentSystem.cs`

核心思路：

1. 读取 `Packages/cn.etetet.map/Bundles/ECA/{MapName}.txt`
2. 扫描带 `ApplyStealth` 的 `RangeTrigger`
3. 本地构建 `LocalConcealmentArea`
4. 仅对“自己”的角色应用半透明材质

这层只负责表现，不参与服务端可见性裁决。

## 为什么这次要去掉 Bush 语义

如果底层保留 `Bush` 语义，后面做这些玩法时会越来越乱：

- 烟雾弹
- 角色主动隐身
- 临时遮蔽结界
- 侦测技能反隐

这些玩法业务上不是草丛，但底层本质上都在处理“谁对谁隐藏”。因此底层必须是通用遮蔽能力，而不是草丛专用实现。

## 后续扩展建议

### 草丛

继续走 `RangeTrigger + ApplyStealth/RemoveStealth` 即可，不需要额外改底层。

### 烟雾

不要复用草丛业务命名。
建议由技能或状态系统在运行时调用通用遮蔽接口，把受影响玩家加入某个动态 `sourceId`。

### 主动隐身

建议也走同一套通用遮蔽底层，但 `sourceId` 不再来自场景点，而来自技能实例、Buff 实例或状态实例。

### 反隐/侦测

如果后续需要“我本来被遮蔽，但某些观察者仍然能看见”，建议在当前通用底层上继续扩展优先级规则或额外显形规则，而不是再复制一套新的隐藏系统。

## 当前收益

1. `ECANode` 仍然负责业务入口，没有把业务触发散到别的包。
2. `map` 只保留通用可见性能力，不再把“草丛”作为底层概念固化。
3. 后续烟雾、隐身技能可以复用同一套权威可见性底层。
4. AOI 耦合被限制在消息出口层，风险可控。

## 已验证内容

- `dotnet build ET.sln` 通过
- 定向测试 `Ecanode_ConcealmentVisibility_Test` 通过

该测试覆盖了：

- 单人进入遮蔽区后，对外隐藏
- 双人共享同一遮蔽来源时，互相可见
- 一方离开后，重新形成单向遮蔽
- 双方都离开后，遮蔽关系被清理
