# 肉鸽效果修复计划

## 1. 文档目的

本文档用于把当前局内肉鸽效果的修复工作整理成一份可执行计划，目标是：

1. 先修正“卡面描述与实际实现不一致”的高风险问题。
2. 再补齐缺失的事件链路、运行时状态和清理逻辑。
3. 最后补测试，避免后续继续出现“测试全绿但效果语义错误”。

本文档不重新展开肉鸽整体设计，只聚焦修复实施。

## 2. 当前结论

当前肉鸽系统的基础链路是通的：

1. 击杀获得经验。
2. 升级后触发发牌。
3. 选牌后挂 Buff 或写入运行时。
4. 一部分持续类效果已经能正常生效。

但当前至少存在三类问题：

1. 多张卡牌的实现与卡面描述不一致。
2. 一些效果已经写入运行时，但没有真正消费方。
3. 现有测试覆盖了主链路，但没有覆盖若干条件触发类语义。
4. 当前基线编译已验证可通过，不再把“编译阻塞”当作默认前置项。

### 2.1 已确认设计口径

1. `1021` 在任务完成后额外挂奖励 Buff，不走同组后续条目激活。
2. `1064` 在概率语义拆分后，继续影响秒杀等通用概率触发。
3. `1054` 保留卡面描述，补“体型差增伤”公式，并对所有攻击目标生效。
4. `1045` 改为真召唤物实现，后续与召唤物角色体系对齐。

## 3. 修复目标

本轮修复只覆盖以下目标：

1. 让高优先级问题卡牌的行为与当前卡面描述一致。
2. 让“条件触发型效果”从静态常驻改为事件驱动。
3. 让“临时资源型效果”具备完整的创建、持有、清理链路。
4. 让“概率类效果”具备明确的作用域，不再复用同一个倍率语义。
5. 补足自动化测试，覆盖修复后的关键语义。

本轮不做以下事情：

1. 不拆新包，继续落在 `cn.etetet.statesync` 与相关现有包内。
2. 不重构整套肉鸽框架。
3. 不在没有明确设计确认前扩展新卡牌。

## 4. 实施原则

1. 遵守 ET ECS 规范，Entity 只存数据，逻辑放 System 或 Helper。
2. 条件触发类效果优先通过现有事件链路挂接，不做硬编码轮询。
3. 新增状态优先挂在玩家或 BuffData 下，避免散落在 Helper 静态缓存里。
4. 能复用现有 `RogueBuffPassiveRuntimeComponent`、`RogueEffectRuntimeComponent`、`RogueProgressComponent` 的，优先复用。
5. 每修一批效果，就补对应测试，不接受只改逻辑不补验证。

## 5. 修复范围与优先级

### 5.1 P0：必须先修

#### A. 任务奖励未闭环

卡牌：

1. `1021 猎手试炼`

问题：

1. 当前只注册了击杀任务。
2. 任务完成后没有真正发放“对怪伤害 +50%”奖励。

修复动作：

1. 给 `RogueObjectiveHelper.OnObjectiveCompleted` 增加奖励触发闭环。
2. 任务完成后额外挂“对怪伤害 +50%”奖励 Buff，不走 `EffectGroup` 后续条目激活。
3. 补测试：
   - 接任务前无增伤。
   - 完成任务后增伤生效。
   - 清理卡牌时奖励也能回滚。

#### B. 概率类效果语义混用

卡牌：

1. `1012 幸运搜索`
2. `1024 怪物磁铁`
3. `1064 幸运女神`

问题：

1. 三张卡目前都落成 `ProbabilityMultiplier`。
2. 当前唯一明确消费方是秒杀概率。
3. 宝箱概率、怪物概率、通用概率没有独立消费方。

修复动作：

1. 把概率效果按作用域拆开：
   - 容器结果概率倍率
   - 搜索区域怪物概率倍率
   - 通用触发概率倍率
2. 保留 `1064` 作为“通用触发概率倍率”，并继续影响 `1063` 秒杀概率这类允许被放大的通用概率触发。
3. `1012` 和 `1024` 改为各自独立效果节点或独立查询接口。
4. 在容器产出逻辑和搜索结果逻辑中接入真实消费方。
5. 补测试：
   - `1012` 只影响宝箱相关概率。
   - `1024` 只影响怪物相关概率。
   - `1064` 影响 `1063` 秒杀等通用概率触发，但不串到容器专属或怪物专属概率接口。

#### C. 条件触发效果被做成常驻

卡牌：

1. `1033 精准打击`
2. `1036 首发强化`

问题：

1. `1033` 现在拿到卡后直接常驻暴击率。
2. `1036` 现在拿到卡后直接常驻伤害和穿透。
3. 都没有体现“命中英雄后获得”和“换弹后前 3 发”的条件语义。

修复动作：

1. 为 `1033` 增加“命中敌方英雄”事件消费链路。
2. 为 `1033` 增加可叠加的临时或本局永久暴击累积状态。
3. 先在 `WeaponReloadHelper.TryCompleteReload()` 返回 `true` 的位置增加换弹完成事件或回调挂点。
4. 为 `1036` 增加“换弹完成后激活强化”状态。
5. 为 `1036` 增加“剩余强化发数”计数，并在开火或命中后递减。
6. 补测试：
   - `1033` 命中非英雄不触发。
   - `1033` 命中英雄后按预期增加暴击。
   - `1036` 换弹后前 3 发强化。
   - `1036` 第 4 发恢复正常。

#### D. 错误占位导致效果跑偏

卡牌：

1. `1005 废品回收`

问题：

1. 设计语义是“开物资箱未出高品质时额外金币”。
2. 当前实际实现更接近“击杀怪额外金币”。

修复动作：

1. 先定位容器开箱链路入口，确认搜索完成、首次打开和物品拿取的实际结算点。
2. 明确高品质判定标准，优先基于 `ItemConfig.Quality` 统一到 Helper。
3. 在容器开启结果结算阶段增加奖励判定。
4. 删除当前 `AddKillGold` 占位语义。
5. 补测试：
   - 开箱未出高品质时给金币。
   - 开箱出高品质时不给金币。
   - 击杀怪不会误触发该卡。

#### E. 临时资源没有生命周期

卡牌：

1. `1013 紫色钥匙`

问题：

1. 当前 `BuffConfig` 已能立即发 1 把钥匙，但 `EffectGroup` 仍保留 `AddGold(value1=0)` 旧占位，配置层存在不一致。
2. “临时”语义没有实现。
3. 跑局结束、卡牌移除、钥匙消耗后的清理规则不明确。

修复动作：

1. 先统一 `EffectGroup` 与 `BuffConfig` 的表达，删除 `AddGold(value1=0)` 旧占位，明确 1013 走背包发物品链路。
2. 明确临时钥匙生命周期：
   - 跑局结束清理
   - 卡牌被移除时清理
   - 使用后消耗
3. 把钥匙来源记录到 `RogueProgress` 或单独 runtime 中。
4. 增加统一清理入口，接入 `ClearRogueRuntime`。
5. 补测试：
   - 获得卡后有钥匙。
   - 清局或移除卡后钥匙被清理。
   - 使用后数量正确减少。

#### F. 数据已记录但没有系统消费

卡牌：

1. `1044 时间延长`

问题：

1. “每 30 秒生命上限 +3%”已实现。
2. “游戏延长 5 分钟”目前只是被动数据，没有接入局内倒计时。

修复动作：

1. 找到局内计时或结算控制点。
2. 在开始局内计时或刷新剩余时间时，叠加 `ExtendGameTime`。
3. 明确是即时延长一次，还是动态读取总时长。
4. 补测试：
   - 获得卡后总时长增加。
   - 清局或移除卡后的行为符合设计。

### 5.2 P1：高优先但可以排在 P0 后

#### A. 体型效果未完整落地

卡牌：

1. `1041 巨人体型`
2. `1054 灵巧身形`

问题：

1. 当前主要只改了生命相关数值。
2. 实际模型缩放没有可靠落地链路。
3. `1054` 卡面里的移速和体型差增伤也没有完整实现。

修复动作：

1. 体型变化按客户端可见处理，补单位缩放同步与表现层更新。
2. 为 `1054` 增加移速加成，按 `NumericType.SpeedFinalPct +30%` 落地。
3. 为 `1054` 增加“体型差增伤”公式，并接入真实伤害计算入口：
   - 读取攻击者与受击目标的总缩放千分比。
   - 取二者差值的绝对值作为体型差。
   - 体型差增伤千分比 = `min(abs(attackerScalePermille - targetScalePermille), 500)`。
   - 按最终伤害增伤结算，即每 100 点体型差提供 `+10%` 最终伤害，最高 `+50%`。
4. 体型差增伤只属于 `1054` 持有者作为攻击方时的专属特性，但目标可以是任意攻击目标。
5. `1041` 只提供体型变大与生命提升，不额外获得该伤害公式。

#### B. `1045 绿树精灵` 与描述不一致

问题：

1. 当前实现是周期回血。
2. 卡面描述写的是“召唤一个绿树精灵为你恢复生命”。
3. 测试已经把该效果固化成“回血”语义。

修复动作：

1. 改为真召唤物实现，补召唤单位、治疗行为、存续与清理链路。
2. 尽量复用后续召唤物角色体系，不把该效果继续固化为纯 Tick 回血。
3. 按召唤语义补代码和测试。

### 5.3 P2：清理与一致性收口

范围：

1. 清理旧的占位注释与过期实现说明。
2. 补全日志命名，避免调试时难以区分卡牌来源。
3. 统一 `EffectGroup`、`BuffConfig`、卡面描述之间的映射检查。
4. 补一份“效果卡牌 -> 事件入口 -> 运行时状态 -> 清理路径”的开发表。

## 6. 建议实施顺序

建议按下面顺序做，避免重复返工：

1. 先跑一次基线编译，确认 `dotnet build ET.sln` 仍可用。
2. 处理 `1021`，先把“任务完成奖励闭环”机制搭起来。
3. 处理 `1033` 和 `1036`，补条件触发状态机。
4. 处理 `1005` 和 `1013`，补容器结算与临时资源清理。
5. 处理 `1012/1024/1064`，拆概率语义并接入真实消费方。
6. 处理 `1044`，接入局内时间系统。
7. 处理 `1041/1054/1045`，做体型公式、缩放表现与召唤物收口。
8. 最后统一补测试、跑全量肉鸽测试、再跑一次整体回归。

## 9. 风险与依赖

### 9.1 主要风险

1. 概率类效果可能分散在容器、地图点、掉落、伤害多个系统，拆分时容易漏接。
2. `1036` 需要接换弹完成与开火扣次数，若事件边界定义不清，容易出现多扣或不扣。
3. `1005` 依赖容器搜索完成与开箱结果的真实结算点，若挂错阶段会导致奖励重复或漏发。
4. `1013` 的临时物品清理如果直接操作背包，容易误删其他来源同类物品。
5. 体型效果与召唤物都涉及表现层和运行时状态，容易牵涉同步消息、单位创建和销毁刷新。

### 9.2 外部依赖

1. `1045` 需要复用现有单位创建、存续和清理链路，避免单独造一套召唤物生命周期。
2. `1054` 体型差增伤按“攻击者与目标缩放差 -> 最终伤害加成”的固定公式实现，后续如要调数值只改配置或常量。
3. `1012/1024/1064` 仍需统一各系统消费口径，尤其要覆盖 `1063` 秒杀概率。

## 10. 验收标准

满足以下条件才算本轮修复完成：

1. `dotnet build ET.sln` 可通过。
2. `Test --Name=Rogue.*` 通过。
3. 本文档中列出的 P0 项全部有代码落地和测试覆盖。
4. 卡面描述与实际实现不再出现明显冲突。
5. 清理跑局或移除卡牌后，不残留错误状态、物品或 Buff。

## 11. 推荐排期

如果由一名熟悉当前项目的开发连续处理，建议按下面排期：

1. 第 1 天：跑基线编译，做 `1021`、`1033`、`1036`
2. 第 2 天：做 `1005`、`1013`、`1012/1024/1064`
3. 第 3 天：做 `1044`、`1041/1054`、`1045` 实现收口
4. 第 4 天：补测试、跑回归、清理注释与文档

当前 4 个主要设计口径已确认，后续优先保证 P0 全部落地，再推进 P1。
