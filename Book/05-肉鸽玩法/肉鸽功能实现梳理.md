# 肉鸽功能实现梳理

## 1. 结论摘要

当前仓库中的肉鸽功能已经形成一条完整闭环：

1. 玩家进入 `Map` 场景后挂载肉鸽进度组件。
2. 玩家击杀目标后按配置获得经验。
3. 达到升级阈值后提升等级，并附加对应数值增益。
4. 如果该等级配置要求发牌，则弹出肉鸽选牌面板。
5. 玩家选中选项后，服务端给玩家挂对应 Buff。
6. 客户端 `MainPanel` 会实时显示当前等级和经验条。

但当前实现有几个非常重要的现实约束：

1. `BTConfig` 格式为 `buff:xxxx`，解析为 `BuffConfigId` 挂 Buff，不执行行为树——这是既定设计。
2. `Reroll` 按钮已实现重抽逻辑。
3. 肉鸽牌功能不是在 `Home` 图测试，而是在正式 `Map` 场景里测试。
4. 客户端等级经验条现在是 `LateUpdate` 轮询 `RogueClientComponent`，不是事件驱动刷新。

如果你要改功能，优先先明确你要改的是哪一层：

1. 改经验和升级规则：看配置表和 `RogueRuntimeConfigCategory`
2. 改发牌逻辑：看 `RogueProgressHelper.TryOpenChoice` / `RollOptions`
3. 改选牌生效逻辑：看 `RogueProgressHelper.ChooseOption`
4. 改 UI 表现：看 `RoguePanel*`、`RogueOption*`、`MainPanelComponentSystem`
5. 改成真正"走 BT"：重点改 `RogueOptionConfig.TryGetEffectBuffConfigId` 和选牌生效链路

## 2. 实现总览

### 2.1 功能分层

肉鸽功能主要分成 5 层：

1. 配置层：肉鸽卡牌、等级曲线、升级数值、击杀经验、全局参数
2. 服务端状态层：玩家身上的肉鸽进度、待选牌状态、已应用 Buff/数值
3. 服务端逻辑层：击杀加经验、升级、发牌、选牌应用效果、跨图清理
4. 客户端状态层：客户端缓存当前等级/经验/待选项
5. 客户端 UI 层：选牌面板、卡牌项、主界面经验条

### 2.2 关键入口

肉鸽进度不是登录就有，而是在玩家进入正式 `Map` 场景时初始化。

挂载入口：

- [`M2M_UnitTransferRequestHandler.cs`](/D:/05ET/MatchTest/ETGame/Packages/cn.etetet.map/Scripts/Hotfix/Server/Map/M2M_UnitTransferRequestHandler.cs)

关键代码：

- 玩家单位进入 `Map` 后执行 `RogueProgressHelper.EnsureProgress(unit, true);`

这意味着：

1. `Home` 不是主要测试场景
2. 只有玩家单位有肉鸽进度
3. 首次挂载时会同步一份初始等级/经验到客户端

## 3.4 BTConfig 当前真实语义

这一点非常重要。

在 [`RogueRuntimeConfig.cs`](/D:/05ET/MatchTest/ETGame/Packages/cn.etetet.statesync/Scripts/Model/Share/RogueRuntimeConfig.cs) 里，`RogueOptionConfig.TryGetEffectBuffConfigId` 的逻辑是：

1. 读取 `BTConfig`
2. 去掉可选前缀 `buff:`
3. 把字符串解析成整数
4. 当成 `BuffConfigId` 使用

也就是说当前的 `BTConfig` 实际语义是：

1. 可以直接写 `200111`
2. 也可以写 `buff:200111`
3. 最终都不是执行 BT，而是拿来查 Buff 配置

所以目前肉鸽牌"走 BT"这件事，代码层并没有真正实现。

## 5.5 升级逻辑

核心文件：

- [`RogueProgressHelper.cs`](/D:/05ET/MatchTest/ETGame/Packages/cn.etetet.statesync/Scripts/Hotfix/Server/RogueProgressHelper.cs)

`AddExp` 的主要逻辑：

1. 累加 `CurrentExp`
2. 进入 `while (CurrentExp >= NeedExp)` 循环
3. 取下一级配置
4. 扣除当前等级所需经验
5. 升级并更新新的 `NeedExp`
6. 应用该级的数值增益
7. 发送 `M2C_RogueLevelUp`
8. 若该级需要发牌，则触发发牌
9. 循环结束后发送 `M2C_RogueExpSync`

这意味着它支持一次性获得大量经验并连续升级。

## 5.6 升级数值增益

逻辑在 `ApplyLevelNumerics`

行为：

1. 遍历本级的 `NumericDeltas`
2. 直接对玩家 `NumericComponent` 执行 `numeric.Set(old + delta)`
3. 同时累计到 `AppliedLevelNumericTotals`
4. 生成 `RogueNumericDelta` 列表，附带在升级消息里发给客户端

这部分是"等级成长"的核心。

如果你要改为：

1. 不是永久加成
2. 只在本局某阶段生效
3. 改成 Buff 化

那就应该从这里下手。

## 5.7 发牌逻辑

逻辑在：

- `TryOpenChoice`
- `RollOptions`
- `RollOptionIndexByWeight`

发牌流程：

1. 先拿到全部可用选项
2. 过滤出能解析出 `BuffConfigId` 且 Buff 配置存在的候选
3. 按权重随机抽取 `ChoiceOptionCount` 张
4. 写入 `PendingOptionIds`
5. `ChoiceSerial += 1`
6. 发送 `M2C_RogueChoicePopup`

当前抽卡规则特点：

1. 同一轮不会重复抽到同一 `OptionId`
2. 不会排除"已经选过的牌"
3. 不会做牌池稀有度、职业、前置依赖之类的限制
4. 权重只来自 `RogueCardConfig.Weight`

如果你要加：

1. 去重
2. 同系牌池
3. 稀有度
4. 前置牌
5. 职业专属

主要改这里。

## 5.8 选牌生效

服务端入口：

- [`C2M_RogueChooseOptionHandler.cs`](/D:/05ET/MatchTest/ETGame/Packages/cn.etetet.statesync/Scripts/Hotfix/Server/C2M_RogueChooseOptionHandler.cs)

核心逻辑：

1. 校验 `ChoicePending`
2. 校验 `ChoiceSerial`
3. 校验 `OptionId` 是否属于当前待选列表
4. 解析出目标 `BuffConfigId`
5. 调用 `BuffHelper.CreateBuff`
6. 记录 `AppliedBuffIds`
7. 清理当前待选状态
8. 如果 `PendingChoiceLevels` 还有排队等级，则立即补发下一轮牌

这里目前的实际效果是：

1. 选中一张牌
2. 给角色挂一个 Buff

## 9. 当前设计限制与潜在问题

## 9.1 `BTConfig` 设计说明（已确认）

`BTConfig` 字段名带 "BT"，但当前既定设计是：**解析为 BuffConfigId，挂 Buff 生效**，不执行行为树。格式固定为 `buff:xxxx`。这是有意为之的设计选择，不是问题。

## 9.2 `Reroll` 已实现（2026-03-26 更新）

Reroll 重抽功能已实现。

## 9.3 击杀经验维度比较粗

当前是按 `UnitType` 给经验，不是按：

1. `UnitConfigId`
2. 怪物模板 ID
3. 稀有度
4. 波次/Boss

如果你要做更细的肉鸽成长节奏，这里很可能不够。

## 9.4 选项池没有去重和前置限制

当前不会处理：

1. 已选牌去重
2. 同系牌限制
3. 前置牌树
4. 稀有度层级
5. 职业/武器前提

## 9.5 客户端经验条是轮询刷新

当前不是：

1. 收到经验消息后立刻事件刷新 UI

而是：

1. `MainPanel` 每帧读 `RogueClientComponent`

优点：

1. 改动小
2. 对现有 UI 侵入低

缺点：

1. 不是最干净的 UI 架构
2. 后面如果 UI 越来越多，建议改成事件驱动

## 11. 建议的改造顺序

如果你准备动这个功能，我建议按下面顺序，不容易把链路改断：

1. 先决定肉鸽牌的"真实生效模型"是 Buff、BT、技能，还是混合
2. 再决定经验维度是按 `UnitType` 还是按怪物模板
3. 再决定卡池规则是否要加稀有度、去重、前置
4. 最后再调 UI 交互和表现

如果第一步没定，后面配置和协议都容易白改。
