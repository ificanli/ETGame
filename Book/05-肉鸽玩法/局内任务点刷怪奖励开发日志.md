## 决策记录

### 2026-04-13 - 不接 quest 包
- **背景**：现有需求只是局内单点一次性刷怪奖励闭环，不需要完整任务系统。
- **方案**：逻辑直接落在 `cn.etetet.statesync`，通过 ECA 点位参数和运行时组件完成闭环。
- **原因**：当前 `quest` 包与本需求的边界不匹配，引入后会扩大改动面，也会把简单闭环做成重系统接入。
- **替代方案**：复用 `quest` 包。放弃原因是依赖和状态模型都偏重，不符合当前“用配置做、同局一次”的需求范围。

### 2026-04-13 - 接受任务弹窗走客户端动态 UI
- **背景**：需求需要一个轻量级接受任务 UI，但没有要求新建完整 YIUI 面板资源。
- **方案**：参考现有运行时 UI 构造方式，在客户端当前场景动态创建一个最小弹窗。
- **原因**：改动收敛、交互链路清晰，且不会额外引入 prefab 和 YIUI 资源依赖。
- **替代方案**：新建完整 YIUI 面板。放弃原因是对当前需求来说过重，制作和接线成本更高。

### 2026-04-13 - StartTask 动作在 statesync 侧增量注册
- **背景**：`ECAFlowActionKey` 已预留 `StartTask`，但 `ecanode` 当前没有实现，且不能让低层包反向依赖高层玩法。
- **方案**：由 `statesync` 在地图场景进入任务点时确保向 `ECAFlowActionRegistry` 注册 `StartTask` 处理器。
- **原因**：保留 `ecanode` 的基础框架职责，同时把玩法闭环收在高层包，满足依赖方向要求。
- **替代方案**：直接改 `ecanode` 实现任务逻辑。放弃原因是会把高层玩法依赖倒灌进 ECA 扩展包。

### 2026-04-13 - FlowAction 注册改为按 Key 保底补齐
- **背景**：`statesync` 先注册 `StartTask` 后，`ECAFlowActionInvokeHandler` 原有“只要 registry 非空就不再注册默认动作”的逻辑会让 `ecanode` 内建动作被整体短路。
- **方案**：把默认动作注册改为按 key 检查缺失项再补齐，而不是按 registry 总量短路。
- **原因**：这样高层玩法可以增量注册自己的动作，同时不破坏低层包已有动作集合。
- **替代方案**：延后 `StartTask` 注册时机。放弃原因是仍依赖初始化顺序，稳定性差。

### 2026-04-16 - 任务点参数模板改为随 FlowGraph 自动补齐
- **背景**：当前任务点参数都挂在 `ECAPointMarker.Params` 上，场景摆点时需要手动输入 6 个 `mission_task_*` key，容易输错，也不利于交接。
- **方案**：在 `ECAPointMarker` 中增加“FlowGraph 参数模板”能力；当挂载的 FlowGraph 包含 `StartTask` 动作时，从节点参数里读取 `point_param_template__*` 模板，并自动补到点位 `Params`；`RogueMissionTaskFlow` 同步写入默认模板值。
- **原因**：这样配置入口仍然是点位 `Params`，不改运行时读取逻辑；同时避免 `cn.etetet.eca` 反向依赖 `statesync`。
- **替代方案**：直接在 `ECAPointMarker` 里 hard code 任务点 key。放弃原因是不利于后续复用，也违反包分层和可维护性要求。

### 2026-04-16 - 任务点刷怪随机范围直接调大
- **背景**：用户回归认为任务刷新的怪物位置不够随机、范围太小，并明确要求“只改参数，改成 `10 -10`”。
- **方案**：继续沿用 `SpawnMonstersHelper.SpawnAtPoint()` 的硬编码散布逻辑，把 `offsetX/offsetZ` 从 `[-2,2]` 直接改为 `[-10,10]`。
- **原因**：这是当前改动面最小、能立即生效的做法，符合用户“只改参数”的要求，也不引入新的点位配置成本。
- **替代方案**：给任务点新增“刷怪半径”参数 key。放弃原因是会扩大配置面和文档/运行时解析范围，不符合本轮目标。

## 问题日志

### 2026-04-13 - 当前仓库存在并行脏改动
- **现象**：`git status` 显示多个模块和资源目录已被其他并行工作改动。
- **原因**：仓库当前不是干净工作树，且用户已明确“不要管其他模块的编译问题”。
- **解决**：本次改动只落在任务点相关文档和目标代码文件，不回退、不整理其他模块改动。

### 2026-04-13 - 增量注册 `StartTask` 时内建动作被短路
- **现象**：任务点进入场景后能触发高层 `StartTask` 注册，但 `ecanode` 默认动作注册因为 registry 已非空被整体跳过，存在把其他点位动作也带挂的风险。
- **原因**：`ECAFlowActionInvokeHandler` 以“registry 是否已有任意项”作为默认动作注册条件，无法兼容高层包的增量注册。
- **解决**：把默认动作注册改为按 key 保底补齐，仅补缺失项，不覆盖已注册动作。

### 2026-04-13 - 新测试未被测试控制台发现
- **现象**：执行 `"Test --Name=MissionTaskReward" | dotnet .\\Bin\\ET.App.dll --SceneName=Test --Console=1` 返回 `not found test!`。
- **原因**：`dotnet build ET.sln` 仍被既有旧错误 `Packages/cn.etetet.test/Scripts/Hotfix/Test/Test_PlayerCorpseLoot_Insurance_Test.cs(423,73)` 阻塞，导致运行态 `Bin/ET.Hotfix.dll` 没有刷新到本次源码；二进制字符串检查显示其中已有 `Test_CreateRobot_Test`、`Test_Loadout_WeaponConfigConsistency_Test`，但没有 `Test_Rogue_MissionTaskReward_Test`。
- **解决**：确认测试分发机制本身无异常，当前将阻塞写入文档；待外部旧错误解除并重新执行 `dotnet build ET.sln` 后，再跑任务点定向测试和局内回归。

### 2026-04-16 - 任务点参数不知道该填在哪
- **现象**：使用方确认了 `mission_task_*` 这 6 个参数必填/可选，但在 Unity Inspector 里不清楚应该填到哪，也不希望每次手动敲 key。
- **原因**：初版实现只在文档里说明“填到点位 `Params`”，但没有把参数模板直接体现在任务点 FlowGraph 的摆点体验里。
- **解决**：改为 `RogueMissionTaskFlow` 自带点位参数模板，`ECAPointMarker` 会在挂上含 `StartTask` 的 FlowGraph 后自动把模板同步到 `Params`。
