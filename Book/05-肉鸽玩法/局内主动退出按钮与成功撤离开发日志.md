## 决策记录

### 2026-04-16 - 主动退出不复用撤离点倒计时链前半段
- **背景**：现有成功撤离入口绑定在撤离点 ECA 交互上，要求玩家站点内停留一段时间。
- **方案**：只复用 `EvacuationSettlementHelper` 和成功结算页，不复用撤离点范围检测与倒计时。
- **原因**：用户要求的是“局内任意时刻点击按钮立即成功撤离”，语义和撤离点局部交互已经不同。
- **替代方案**：伪造一个隐藏撤离点并强行走 `PlayerEvacuationComponent`。放弃原因是会把 UI 按钮错误耦合到场景点位语义，链路更脆。

### 2026-04-16 - 退出按钮优先落 MainPanel prefab
- **背景**：用户明确要求后续所有涉及 UI 的修改优先考虑 prefab，不要运行时创建。
- **方案**：直接在 `MainPanel.prefab` 补静态退出按钮，再由手写层接入点击。
- **原因**：按钮属于局内主界面的稳定常驻区块，资源层表达更直观，也方便你直接进游戏验证。
- **替代方案**：运行时代码创建按钮。放弃原因是违反当前明确约束。

### 2026-04-16 - 主动退出 handler 维持“响应先回，后台协程结算+切图”口径
- **背景**：主动退出请求在语义上是“接受一个成功撤离指令”，真正的结算与回大厅仍应继续走现有权威链。
- **方案**：`C2M_QuickExitExtractionHandler` 先同步返回“请求接受成功”，再在后台协程里执行 `EvacuationSettlementHelper.Settle(unit)` 与 `TransferHelper.TransferAtFrameFinish(...)`。
- **原因**：这样更贴近现有成功撤离链的执行形态，客户端只负责发起请求，不直接驱动结算页和切图。
- **替代方案**：把结算页或回大厅逻辑下沉到客户端直接处理。放弃原因是会绕开现有权威消息链，风险更高。

### 2026-04-17 - 定向测试 waiter 必须显式预启动
- **背景**：服务端实际已经发送 `M2C_EvacuationSettlement`、`M2C_StartSceneChange` 等消息，但 `Test_QuickExitExtraction_SettlementFlow_Test` 仍表现为一直等不到通知。
- **方案**：把 `Wait<Wait_M2C_EvacuationSettlement>()` 和 `Wait<Wait_SceneChangeFinish>()` 改为先 `.NewContext(null)` 预启动，再等待返回结果。
- **原因**：`ObjectWait.Wait<T>()` 内部会先取异步上下文；如果只是把它存成 `ETTask` 而不 `await` / `.NewContext(...)`，waiter 根本不会注册到 `ObjectWait.tcss`，后续 `Notify` 到了也没人接。
- **替代方案**：继续修改主动退出业务链或场景切图链。放弃原因是根因不在业务实现，而在测试自身的 waiter 启动方式。

### 2026-04-17 - 主动退出定向测试 waiter 未预启动
- **现象**：服务端主动退出后，客户端运行时其实已经收到结算与切图消息，但测试仍卡在等待 `Wait_M2C_EvacuationSettlement` / `Wait_SceneChangeFinish`。
- **原因**：测试把 `ObjectWait.Wait<T>()` 先存成了未启动的 `ETTask`，导致 waiter 没注册；同时旧掉落物品 `10001` 在当前仓会被正规化到 `22001`，原断言也存在旧 ID 假设。
- **解决**：把两个 waiter 改为 `.NewContext(null)` 预启动，并把结算物品断言改为按 `LegacyItemConfigIdHelper.NormalizeConfigId(10001)` / `MatchesConfigId(...)` 校验。
