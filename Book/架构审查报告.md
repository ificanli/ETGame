# 架构审查报告

> 审查时间：2026-03-26  
> 覆盖范围：`cn.etetet.statesync` 为核心，兼顾 `cn.etetet.spell`、`cn.etetet.item`、`cn.etetet.equipment`、`cn.etetet.proto` 及 YIUI 框架层  
> 审查方法：全量代码阅读，逐系统梳理，按严重程度分级

---

## 一、总体架构概况

项目采用 ET10 框架，按照 **Model / ModelView / Hotfix / HotfixView** 四层分包，客户端/服务端/共享三向编译隔离，热更新通过 HybridCLR 实现。主业务包 `cn.etetet.statesync` 承载了战斗、肉鸽、搜索、移动等全部核心玩法，文件数量达 6300+，是整个项目的"重心"。

整体架构设计是清晰且现代的——ECS + 事件总线 + Helper 静态类 + 行为树 BT，各层职责相对明确。以下报告聚焦**可以改进**的部分，从高到低排列。

## 二、P0 级问题（有已知 Bug 或会产生运行时错误）

### P0-1：HPViewComponent/HPView3DComponent Destroy 方法体为空（BUG-006）

**位置**：`HPViewComponentSystem.cs:42`、`HPView3DComponentSystem.cs`  
**现象**：怪物死亡后血条 UI 残留在屏幕上，尸体搜索阶段依然可见血条。  
**根因**：Entity Dispose 时 Destroy 不主动回收 UIBase，LateUpdate 不再触发所以无法自动隐藏。  
**修复**（已写入 BUG 追踪）：

```csharp
// HPViewComponentSystem.cs
private static void Destroy(this HPViewComponent self)
{
    if (self.UIBase?.OwnerRectTransform == null) return;
    var mgr = self.YIUIMgr();
    if (mgr?.UICache == null) return;
    if (self.UIBase.OwnerRectTransform.parent != mgr.UICache)
        self.UIBase.OwnerRectTransform.SetParent(mgr.UICache);
}

// HPView3DComponentSystem.cs
private static void Destroy(this HPView3DComponent self)
{
    self.u_DataShow?.SetValue(false);
}
```

### P0-2：SpawnMonstersHelper.SpawnAtPoint groupId 用法有误

**位置**：`SpawnMonstersHelper.cs:31`  
**现象**：`groupId` 直接被 `int.TryParse` 当作 `unitConfigId` 使用，而 groupId 语义上是"刷怪组ID"（字符串），未来会直接导致刷怪失败。  
**代码**：
```csharp
// TODO: 这里需要根据 groupId 从配置中读取怪物配置
// 目前使用简单的逻辑：groupId 直接作为 UnitConfigId
if (!int.TryParse(groupId, out int unitConfigId))
{
    Log.Warning($"[SpawnMonsters] Invalid groupId format: {groupId}");
    return 0;
}
```
**改进建议**：设计 `MonsterGroupConfig` 表，groupId → List\<MonsterEntry\>，支持多种怪物混合刷新和数量概率权重，消除当前的 TODO 注释和临时绑定。

### P0-3：DamageContext.UnitDie 事件在 attacker 无效时直接 return，目标 Unit 不会被正确清理

**位置**：`DamageContextHelper.cs:96-99`  
```csharp
if (attacker == null || attacker.IsDisposed || attacker.InstanceId == 0)
{
    return;  // ← 直接 return，UnitDie 不会被发布！
}
```
**现象**：若 attacker 在伤害结算完成到 UnitDie 发布之间被 Dispose（例如被其他逻辑提前清理），目标 HP 已扣到 0，但 `UnitDie` 不发布，导致：
- 怪物不会创建尸体盒
- 经验/金币不会结算
- 任务计数不会推进

**改进建议**：把 `UnitDie` 的发布路径从 attacker 有效性中解耦。如果 attacker 已销毁，仍然发布 `UnitDie`，只是 `Unit = null`，让各事件监听者自己做 null 判断即可：

```csharp
UnitDie unitDie = new UnitDie
{
    TargetId = targetId,
    TargetUnitType = targetUnitType,
};
// attacker 可能已销毁，不做强制依赖
if (attacker != null && !attacker.IsDisposed && attacker.InstanceId != 0)
{
    try { unitDie.Unit = attacker; } catch { }
}
// ...
EventSystem.Instance.Publish(scene, unitDie);
```

## 三、P1 级问题（设计缺陷，会在迭代中放大为 Bug 或维护债）

### P1-1：WeaponComponent 字段全部展开，无法扩展到 3 槽以上

**位置**：`WeaponComponent.cs`  
**现象**：`Slot1WeaponId`、`Slot2WeaponId`、`Slot1Ammo`、`Slot2Ammo`... 共 20+ 个字段全部以 `Slot1`/`Slot2` 前缀区分，`WeaponComponentSystem` 中所有方法都是 `if slot==1 ... else if slot==2` 分支。  
**风险**：如果需要加第三把武器（手雷、匕首），需要改 Component + 全部方法的 if-else + 协议 + 同步逻辑 + UI，改动面极大。  
**改进建议**：将武器槽抽象为数组/列表结构，或提取 `WeaponSlotData` 结构体：

```csharp
public class WeaponComponent : Entity, IAwake, IDestroy
{
    // 替换为按槽索引访问
    public WeaponSlotData[] Slots = new WeaponSlotData[2];
    public int CurrentSlot;
}

[Serializable]
public struct WeaponSlotData
{
    public int WeaponId;
    public int Ammo;
    public bool Reloading;
    public long LastFireTime;
    public long ReloadFinishTime;
    // effective stats...
}
```

这样 `GetAmmo(slotIndex)` → `Slots[slotIndex-1].Ammo`，逻辑清晰，扩展到 N 槽无需改接口。

### P1-2：M2C_WeaponAmmoState 每次射击/换弹都全量同步双槽状态

**位置**：`WeaponReloadHelper.SyncAmmoState`，`WeaponRuntimeStatsHelper.RefreshUnitWeaponRuntimeStats`  
**现象**：`M2C_WeaponAmmoState` 包含双槽弹药量、换弹状态、弹匣容量、射程，共 9 个字段，每次任何一个槽发生变化都全量下发。  
**风险**：高频战斗时（多人同屏、连续射击），这个包的频率直接等于射击频率，带宽和处理开销浪费约 50%。  
**改进建议**：
1. 拆分为 `M2C_WeaponSlotAmmoChanged { UnitId, SlotIndex, Ammo, Reloading }` 增量消息。
2. 静态属性（弹匣容量、射程）只在武器装备/肉鸽Buff改变时下发一次，不混入高频消息。

### P1-3：RogueProgressHelper.TryOpenChoice 方法过长，决策树可读性差

**位置**：`RogueProgressHelper.cs:568-731`（约 160 行）  
**现象**：`TryOpenChoice` 方法包含了品质抽取 → 第一次尝试 → 品质降级循环 → 忽略Tag二次循环 → 品质降级再循环，4 层嵌套 for 循环，逻辑复杂。  
**风险**：新增抽卡规则（如保底机制）需要在此方法中再加分支，容易引入逻辑冲突。  
**改进建议**：提取专门的 `RogueOptionRollPipeline`，用职责链或策略模式封装抽卡步骤，每个步骤独立可测试：

```csharp
// 示例结构
public class RogueOptionRollPipeline
{
    public List<int> Execute(Unit unit, int preferQuality, int needCount)
    {
        // 步骤1: 正常品质抽取（含Tag过滤）
        // 步骤2: 降级品质补充
        // 步骤3: 忽略Tag补充
        // 步骤4: 全品质忽略Tag兜底
        // 步骤5: 保底逻辑（扩展点）
    }
}
```

### P1-4：HPViewComponentSystem.LateUpdate 中每帧调用 UnitHelper.GetMyUnitFromCurrentScene

**位置**：`HPViewComponentSystem.cs:68-81`  
```csharp
if (self.Player == null)
{
    var player = UnitHelper.GetMyUnitFromCurrentScene(self.Scene());
    // ...
}
```
**现象**：Player 引用每帧都做 null 检查，如果 null 就调用 `GetMyUnitFromCurrentScene`（内部有查找开销）。当同屏有 20 个怪物，每个 LateUpdate 都跑这段逻辑。  
**风险**：当前场景中玩家掉线重连或 Unit 重建时 `self.m_Player` 不会主动失效，可能持有过期 EntityRef。  
**改进建议**：将 Player 引用改为 `EntityRef<Unit>`，在 HPViewComponent 的 Destroy 或场景切换事件中主动清空，LateUpdate 中只做 EntityRef 解引用而非重新查找。

### P1-5：MonsterCorpseLootHelper 中 FlowGraph 硬编码构建，容器交互逻辑不可配置

**位置**：`MonsterCorpseLootHelper.cs:271-337`  
**现象**：`CreateOpenContainerFlowGraph` 方法直接用代码构造了含 6 个节点的 FlowGraph，其中包括交互按钮文字 ID、触发事件类型、OpenContainerUI 参数等。这些逻辑对于所有尸体盒是完全一样的，但无法被策划配置。  
**风险**：如果要做"精英怪有不同交互音效"或"特殊尸体需要 2 步交互"，必须改代码。  
**改进建议**：在 `ExtractionInventoryConfig` 或 `MonsterCorpseLootConfig` 中增加 `CorpseFlowGraphTemplateId` 字段，FlowGraph 从配置读取预设模板，代码只负责参数注入，不包含结构。

---

### P1-6：RogueEffectHelper.ShouldKeepBuff 判断逻辑复杂且维护成本高

**位置**：`RogueEffectHelper.cs:505-543`  
**现象**：`ShouldKeepBuff` 需要通过分析 `buffConfig.Effects` 的内容来决定是否保留 Buff 实例（比如 Effects 列表中只有 `EffectServerBuffAdd` 且其子节点全是瞬发操作时才不保留）。这是一种反向推断，容易随新 Effect 类型的增加而失效。  
**改进建议**：在 `BuffConfig` 中直接添加 `KeepInstance` 字段（bool 或 enum），由策划在配置中明确标记，消除代码侧的反向推断。

---

### P1-7：BulletDamageRequest_ApplyDamage 事件 handler 使用了不必要的 async

**位置**：`BulletDamageRequest_ApplyDamage.cs`  
```csharp
protected override async ETTask Run(Scene scene, BulletDamageRequest a)
{
    // ...全部是同步代码...
    DamageContextHelper.ApplyDamage(...);
    await ETTask.CompletedTask;  // ← 完全没有异步操作
}
```
**风险**：`async` + `await ETTask.CompletedTask` 会在每次子弹命中时分配 ETTask 状态机对象（即使 HybridCLR 优化过，仍有额外开销）。高频战斗中（100发/秒）这是可避免的 GC 压力。  
**改进建议**：将此 Handler 改为 `IEvent` 同步接口（如果 ET 框架支持），或至少改为非 async 的同步 override（需确认 ET 基类是否支持）。

## 四、P2 级问题（代码质量/可读性/可扩展性）

### P2-1：ResolveHealSpiritConfigId 用全量遍历寻找 Pet 类型 Unit 配置

**位置**：`RogueBuffActionHandlers.cs:1122-1145`  
```csharp
foreach (UnitConfig config in configCategory.DataList)
{
    if (config != null && config.UnitType == UnitType.Pet)
        return config.Id;
}
```
**问题**：每次召唤治愈精灵都遍历全部 UnitConfig，实际配置数量不多但这是不良实践。  
**改进建议**：在 `ExtractionInventoryConfig` 或单独的 `RogueRuntimeConfig` 中直接配置 `HealSpiritConfigId`，消除动态查找。

### P2-2：JoystickMoveComponentSystem 中每帧广播同时创建两个相同消息体

**位置**：`JoystickMoveComponentSystem.cs:249-253`  
```csharp
M2C_JoystickMove selfMsg = CreateMoveMessage(...);
MapMessageHelper.NoticeClient(unit, selfMsg, NoticeType.Self);

M2C_JoystickMove broadcastMsg = CreateMoveMessage(...);
MapMessageHelper.NoticeClient(unit, broadcastMsg, NoticeType.BroadcastWithoutSelf);
```
**问题**：16ms 一帧，每帧创建 2 个内容完全相同的消息对象。如果 `NoticeType.Broadcast` 支持"含自己"广播，只需一次 Create 即可。  
**改进建议**：检查 `MapMessageHelper` 是否支持 `NoticeType.Broadcast`（含自己），若支持则合并为一次调用；若框架要求分开发，则先 Self 后用同一个消息对象再发 BroadcastWithoutSelf，避免二次构造（需确认对象池安全性）。

### P2-3：WeaponCanFire 中 CanFire 检查射击间隔时有"配置兜底"逻辑

**位置**：`WeaponComponentSystem.cs:149-153`  
```csharp
if (effectiveAttackIntervalMs <= 0)
{
    WeaponConfig config = WeaponConfigCategory.Instance.Get(weaponId);
    effectiveAttackIntervalMs = config?.AttackIntervalMs ?? 0;
}
```
**问题**：`effectiveAttackIntervalMs` 在 `Awake` 和每次 `RefreshUnitWeaponRuntimeStats` 时应当已经被正确赋值。在高频 `CanFire` 路径中再做"万一没设对就从配置读"的兜底，说明对 EffectiveStats 的初始化时机缺乏信心。  
**改进建议**：在 `Awake` 和 `RefreshUnitWeaponRuntimeStats` 完成后，确保 EffectiveStats 永远 > 0（有武器的情况下）。去掉 `CanFire` 中的兜底，加断言 `Assert(effectiveAttackIntervalMs > 0)` 方便排查问题。

### P2-4：RogueBuffConfigLoader.EnsureRegistered 在每次 ApplySelectedOption 时调用

**位置**：`RogueEffectHelper.cs:15`  
```csharp
public static int ApplySelectedOption(...)
{
    RogueBuffConfigLoader.EnsureRegistered();
    // ...
```

**问题**：`EnsureRegistered` 在每次选牌时调用，内部应该有幂等保护，但每次都要进入方法执行检查。如果选牌很频繁（GrantRandomCard 链式调用），这是不必要的重复调用。

### P2-5：RogueProgressHelper 文件体量过大（1065 行）

**位置**：`RogueProgressHelper.cs`  
**问题**：一个文件承载了经验计算、升级、选牌弹窗、Reroll、定时弹窗重发、AutoChoose（机器人）等多个职责，行数达 1065 行。

### P2-6：FindLootConfig 使用 foreach 线性扫描配置表

**位置**：`MonsterCorpseLootHelper.cs:145-178`

### P2-7：WeaponSyncHelper 每次仅视野进入就同步全量武器状态，无差量对比

**位置**：`WeaponSyncHelper.cs`

## 五、架构层面的中长期建议

### 架构建议 A：建立"子系统职责矩阵"防止 statesync 包过度膨胀

`cn.etetet.statesync` 已积累 420 个 CS 文件，其中肉鸽、战斗、地图、搜索、武器、玩家显示等全部堆在一个包内。这在早期快速迭代时合理，但随着版本推进，建议将独立性较高的子系统拆包：

| 候选拆包 | 当前位置 | 建议新包 |
|---------|---------|---------|
| 肉鸽进度/效果/选牌 | statesync/Hotfix/Server/Rogue* | cn.etetet.roguelite |
| 怪物尸体/容器搜索 | statesync/Hotfix/Server/*Corpse*Loot* | cn.etetet.loot |
| 武器组件/换弹/Buff | statesync/Hotfix/Share/Weapon* | cn.etetet.weapon |

---

### 架构建议 B：协议号段管理规范化

当前协议号在 `StateSync_C_10700.cs` 中定义，但武器协议（10711~10715）、肉鸽协议（10716~10724）混在同一个文件，没有明确的模块段划分注释。随着功能增加，协议号维护会越来越混乱。  
**建议**：
- 每个模块预留固定号段，如：武器 10710-10729、肉鸽 10730-10769，写在文件头注释中
- 考虑将协议定义拆分到各业务包的子文件中，不全集中在 `cn.etetet.proto`

## 六、已有优点（维持不变）

以下设计是值得肯定的，不需要改动：

1. **伤害管线事件化**：`BeforeDamageApply → Apply → AfterDamageApply` 三段式事件发布，扩展不改核心。
2. **武器运行时属性 EffectiveStats 缓存**：肉鸽 Buff 改变时统一刷新，CanFire 路径只读缓存，避免每次查配置。
3. **换弹定时器独立调度**（`WeaponReloadSchedulerHelper`）：换弹不依赖 BT Tick，脱离视野也能正确完成。
4. **CoroutineLock 在 ChooseOption/RerollOption 上加锁**：防止同一玩家并发选牌导致双重选择。
5. **虚拟 Unit（Virtual）作为尸体盒容器**：与 ECA 交互框架无缝兼容，不需要单独创建容器实体类型。
6. **EntityRef\<Unit\> 弱引用防止异步协程死持 Unit**：在 `TryInitializeChoicePopupAfterEnter` 等异步路径中正确使用。
