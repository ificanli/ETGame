# 肉鸽效果与机制实现评估方案

## 1. 结论先行

基于当前仓库，肉鸽系统已经具备一条“击杀经验 -> 升级 -> 发牌 -> 挂 Buff”的最小闭环，但距离 `D:\05ET\Book\肉鸽效果设计.txt` 里的“全量肉鸽效果和机制”还有明显差距。

核心结论有 6 条：

1. 现有 `Buff + BT` 体系只能直接覆盖一部分效果，主要是“持续生效、周期 Tick、受击触发、加减数值、加减 Buff、召唤物”。
2. 设计稿里大量效果属于“流程型/事件型/局内经济型”能力，不能直接塞进 `BuffConfig` 解决，必须补一层 `RogueRuntime` 事件与状态系统。
3. 当前 `RogueCard.BTConfig` 并没有执行行为树，它只是被解析成 `BuffConfigId`，这个字段语义必须重做。
4. 当前 `RogueLevelEntry.xlsx` 的实际触发等级不是旧文档里的 `2/4/6/9`，而是 `1/3/5/8`。
5. 按当前设计语义，`HideTags` 是“对玩家隐藏但依然生效的 tag”，不是“排除标签”。现有实现没有按这个语义完整接入：隐藏 tag 会参与候选筛选，但不会参与 2/3 张流派统计。
6. 推荐短期继续以 `cn.etetet.statesync` 为主落点，不新开包；等机制稳定后，再考虑是否抽出独立 `cn.etetet.rogue` 包。

我的建议不是“所有效果都做成 Buff”，而是拆成三层：

1. `RogueCard` 负责抽卡、显示、标签、池子、前置条件。
2. `RogueRuntime` 负责局内金币、计数器、任务、事件订阅、卡牌替换、死亡复活、商人激活、区域发现等流程能力。
3. `Buff + BT` 负责真正挂在单位身上的持续状态和可复用战斗行为。

## 2. 现状核对

### 2.1 当前已经存在的能力

当前仓库已经存在以下可复用基础：

1. `RogueProgressHelper` 已经实现经验、升级、发牌、选牌、挂 Buff、离图清理。
2. `RogueChoiceQualityHelper` 已有按品质抽牌的序列逻辑。
3. `Tags.xlsx + RogueProgressHelper.RefreshCommonShowTagBuffs` 已经支持“同类标签达到阈值后自动挂展示/效果 Buff”的机制雏形，但当前样例表只填了一档 `ShowTagsBuffId`，所以 2 张和 3 张会落到同一个 Buff。
4. `spell` 包里的 `BuffConfig` 支持：
   - Add
   - Tick
   - Hitted
   - Remove
   - 数值修改回滚
   - 子 Buff
   - 召唤物绑定
5. `ecanode` 已经有容器搜索、多人并发搜索、打开容器、生成战利品、拖拽/一键拾取链路。
6. `eca` 已经有 `OnPlayerEnterRange`、`OnPlayerLeaveRange`、`OnPlayerInteract`、`OnMapLoaded` 等流程事件；`OnTargetKilled` 目前只有常量和编辑器支持，生产代码尚未接通。

### 2.2 当前明确不够用的地方

当前仓库还缺这些“肉鸽重度效果”所需能力：

1. 局内金币系统。
2. 统一伤害上下文系统。
3. 致命伤害拦截。
4. 死亡后复活与物品保留规则。
5. 区域首次发现记录。
6. 商人激活/刷出/购买流程。
7. 武器局内附魔系统。
8. 概率触发全局倍率系统。
9. 助攻参与击杀统计。
10. 真实的 reroll / reset / random card grant。

### 2.3 当前代码里几个必须正视的事实

#### 事实 A：`BTConfig` 当前不是 BT

`RogueOptionConfig.TryGetEffectBuffConfigId` 的真实逻辑是：

1. 读取 `BTConfig`
2. 去掉可选前缀 `buff:`
3. 解析成整数
4. 当成 `BuffConfigId`

所以现在配置里写 `BTConfig=200111`，本质上等于“选中后直接挂 200111 号 Buff”，不是“运行某棵 BT”。

#### 事实 B：当前发牌等级和旧文档不一致

`RogueLevelEntry.xlsx` 当前实际配置为：

1. `Level=1` 触发发牌
2. `Level=3` 触发发牌
3. `Level=5` 触发发牌
4. `Level=8` 触发发牌

不是旧文档里提到的 `2/4/6/9`。

#### 事实 C：当前 `HideTags` 没有按“隐藏 tag”语义完整接通

按当前设计语义，`HideTags` 应表示“这张卡实际带有这些 tag，但不对玩家展示”。

现有代码里有两个现象：

1. `RogueProgressHelper.MatchOptionByTags` 会把 `ShowTags` 和 `HideTags` 一起送进 `CollectFilterTags`，所以隐藏 tag 会参与英雄/武器候选筛选。
2. `BuildCommonShowTagCounts` 只统计 `ShowTags`，不会统计 `HideTags`，所以隐藏流派 tag 不会参与 2/3 张效果结算。

这意味着当前真正的问题不是“排除逻辑错误”，而是：

1. 显示标签和逻辑标签还没彻底拆清。
2. 隐藏 tag 会影响抽卡筛选，但不会影响流派成型统计。
3. 如果后续要做“暗 tag”“隐藏流派”“不告诉玩家真实归属”，必须先统一它的运行时语义。

#### 事实 D：当前品质序列是场景共享，不是玩家独立

`RogueChoiceQualityComponent` 挂在 `Scene` 上，`ChoiceQualities` 是整张地图共用的序列。

如果设计想要：

1. 每个玩家独立 pity
2. 每个玩家独立品质推进

那么这个组件必须从 `Scene` 下沉到玩家局内运行态。

#### 事实 E：当前伤害链路并不统一

现在至少有两条扣血路径：

1. `spell` 包里的 `DamageHelper.Damage`
2. `statesync` 里的 `BulletComponentSystem.OnHit`

其中子弹命中逻辑会直接扣 `HP`，不会走 `DamageHelper`。

这会直接影响：

1. 吸血
2. 固定减伤
3. 对怪增伤
4. 致命免死
5. 低血斩杀
6. 命中触发弹射/冰冻/秒杀

如果不统一成一套 `DamageContext`，后续效果会出现“一部分生效、一部分对子弹不生效”的问题。

另外当前两条路径的数值类型也不一致：

1. `DamageHelper.Damage` 主要按整数伤害结算。
2. `BulletComponentSystem.OnHit` 先按 `float` 计算，再写回 `long`。

这一点在做统一前必须先拍板。

## 3. 推荐总体架构

## 3.1 包落点建议

推荐先不新开包，继续按下面方式落：

1. `cn.etetet.statesync`
   - 肉鸽运行时组件
   - 卡池/选牌/金币/局内任务/区域发现/死亡复活/武器附魔
   - 客户端 HUD、发牌 UI、金币 UI、标记 UI
2. `cn.etetet.spell`
   - 继续承载 Buff 生命周期
   - 不承载肉鸽卡池和局内流程
3. `cn.etetet.btnode`
   - 扩展肉鸽专用 BT 节点
4. `cn.etetet.ecanode`
   - 搜索完成、容器产出、商人点位激活等交互入口
5. `cn.etetet.map`
   - 单位进图/离图初始化与清理
6. `cn.etetet.battle`
   - 对局剩余时间延长、结算财富统计

原因很简单：

1. 现有 Rogue 代码已经在 `statesync`。
2. `statesync` 已经依赖 `spell`、`eca`、`ecanode`、`item`、`map`。
3. 先落在现有整合包，改造成本最低。
4. 等玩法固化后再抽包，风险更低。

## 3.2 推荐运行时组件拆分

当前 `RogueProgressComponent` 已经承担了太多职责，建议扩成 4 个组件。

### `RogueRunComponent` 挂在 `Unit`

负责本局玩家肉鸽运行态，只保留全局、稳定、跨效果共享的数据：

1. `Level`
2. `CurrentExp`
3. `NeedExp`
4. `CurrentGold`
5. `SelectedCardIds`
6. `ActiveModifierIds`
7. `AppliedBuffIds`
8. `TagCounts`
9. `VisitedAreaIds`
10. `ProbabilityScalePermille`

### `RogueChoiceComponent` 挂在 `Unit`

负责选牌态：

1. `ChoiceSerial`
2. `ChoicePending`
3. `PendingOptionIds`
4. `PendingChoiceQueue`
5. `RerollCount`
6. `LastRolledPoolId`

### `RogueObjectiveComponent` 挂在 `Unit`

这里建议明确分成“容器组件 + 多实例子 Entity”两层，而不是把它理解成一个可多挂的同类型组件。

推荐结构：

1. `RogueObjectiveComponent` 作为 `Unit` 上的任务容器，只负责索引和查找。
2. 每条任务实例使用一个 `RogueObjective` 子 Entity，挂在 `RogueObjectiveComponent` 下。
3. `RogueObjective` 里保存：
   - `ObjectiveId`
   - `Progress`
   - `Completed`
   - `RewardClaimed`

这样一个玩家同时有 2 条或更多任务时，不会违反 ET “同类型 Component 不能重复挂载”的约束。

### `RogueWeaponModifierComponent` 挂在 `Unit`

负责枪械局内改造：

1. `RangePct`
2. `AttackIntervalPct`
3. `MagazinePct`
4. `ReloadPct`
5. `BounceChance`
6. `NextShotBuffState`
7. `EnchantIds`

### `RogueEffectRuntimeComponent` 挂在 `Unit`

这里同样建议明确为“容器组件 + 多实例子 Entity”。

推荐结构：

1. `RogueEffectRuntimeComponent` 作为 `Unit` 上的效果运行时容器。
2. 每条已激活效果实例使用一个 `RogueEffectRuntime` 子 Entity，挂在 `RogueEffectRuntimeComponent` 下。
3. `RogueEffectRuntime` 里保存：
   - `EffectEntryId`
   - `SourceCardId`
   - `CooldownEndTime`
   - `TriggerCount`
   - `CustomValue1`
   - `CustomValue2`

这类运行态建议按“效果实例”拆开，而不是把所有 `Cooldowns/Counters` 塞进一个总组件。

这样做的好处是：

1. 经验升级逻辑和选牌逻辑分开。
2. 任务、金币、武器改造不必硬塞进一个组件。
3. 效果冷却和计数不落成上帝组件。
4. 后续写测试时更容易拆。

## 4. Buff 和 BT 应该怎么做

## 4.1 推荐原则

推荐采用一句话原则：

`Buff 负责挂身上的状态，BT 负责 Buff 的行为脚本，RogueRuntime 负责卡牌和事件流程。`

不要把三者混成一个概念。

## 4.2 哪些效果应该优先做成 Buff

下面这些效果适合直接做成 Buff：

1. 固定数值增伤/减伤/攻速/移速/血量/回血。
2. 周期触发效果。
3. 受击触发效果。
4. 持续隐身。
5. 护盾。
6. 命中后附加 Debuff。
7. 定时召唤单位或陷阱。
8. 2/3 张同流派效果。

原因：

1. 已有生命周期。
2. 已有 Tick。
3. 已有 Add/Hitted/Remove 树。
4. 已有数值回滚记录。

## 4.3 哪些效果不应该直接塞进 Buff

下面这些效果不要一开始就试图纯 Buff 化：

1. 直接给金币。
2. 击杀额外给金币。
3. 第一次进入区域给奖励。
4. 激活地图商人。
5. 任务“击杀 15 个怪”。
6. 随机获得紫卡/橙卡。
7. 命运重置。
8. 死亡后概率复活并随机保留装备/背包。
9. 修改容器开出怪物/宝箱概率。
10. 全局“概率类效果乘 1.5”。

这些都应该走 `RogueRuntime` 的事件订阅与流程处理，再由处理结果决定是否加 Buff。

## 4.4 BT 在肉鸽里应该承担的角色

BT 应该只做两类事：

1. Buff 内部执行逻辑。
2. 部分复杂战斗行为节点。

例如：

1. `BTHeal`
2. `BTApplyDetector`
3. `BTCreateWard`
4. `BTNumericChange`
5. 新增的 `BTGrantRogueGold`
6. 新增的 `BTSpawnRogueTrap`
7. 新增的 `BTApplyWeaponEnchant`

BT 不应该负责：

1. 卡池抽取。
2. 选牌去重。
3. reroll。
4. 任务进度。
5. 区域发现记录。
6. 死亡后复活判定。

## 4.5 推荐做法：废弃 `RogueCard.BTConfig` 的现语义

建议把 `RogueCard.xlsx` 里的 `BTConfig` 直接替换成 `EffectGroupId`。

原因是效果类型本来就应该由 `RogueEffectEntry.ExecuteType` 自描述，不需要再在卡表额外加一个 `ApplyMode` 做重复分流。

实际执行时：

1. 卡表只提供 `EffectGroupId`
2. `RogueEffectHelper.ApplyGroup` 读取组内所有 `RogueEffectEntry`
3. 再按每条 `ExecuteType` 分发为：
   - `AddBuff`
   - `RegisterObjective`
   - `GrantRandomCard`
   - `AddGold`
   - `ReplaceAllCards`
   - `ApplyWeaponEnchant`

这样比“字段叫 BTConfig，实际填 BuffId”更清晰，也避免卡表和效果表双重定义执行模式。

## 5.3 `Tags.xlsx` 应该怎么用

当前 `Tags.xlsx` 已经非常适合做 2/3 张流派效果。

推荐用法：

1. 7 个主流派：
   - 打金专家
   - 全能搜查
   - 首领猎手
   - 火力进化
   - 持久作战
   - 猎杀者
   - 掷骰狂人
2. 每张卡挂一个或多个流派 tag
3. `ShowTagsBuffId` 配置成“2 张效果 Buff”“3 张效果 Buff”
4. 继续沿用当前 `TagType=1` 的逻辑

这块现有代码已经能复用，但要注意三点：

1. `ShowTagsBuffId` 虽然类型是数组，当前样例只填了 1 个值，所以 2 张和 3 张目前会命中同一个 Buff。
2. 正式配置时应至少填 2 个值：
   - `ShowTagsBuffId[0] = 2 张效果`
   - `ShowTagsBuffId[1] = 3 张效果`
3. 如果 `HideTags` 表示隐藏但生效的 tag，那么流派统计必须把 `HideTags` 也纳入计数，而不是只统计 `ShowTags`。

## 6. 现有流程要改什么

## 6.1 Rogue 选牌应用链路

当前是：

1. `ChooseOption`
2. 解析 `BTConfig`
3. 直接 `BuffHelper.CreateBuff`

建议改成：

1. `RogueChoiceHelper.ChooseOption`
2. 从 `RogueCard` 取 `EffectGroupId`
3. `RogueEffectHelper.ApplyGroup`
4. 按 `ExecuteType` 分发：
   - 加 Buff
   - 注册修饰器
   - 立即加金币
   - 发随机牌
   - 重置已有牌

这样同一张卡就可以同时：

1. 挂 Buff
2. 注册事件监听
3. 立刻给金币

除了应用链路，还必须补一条对称的移除链路。

建议统一提供 `RogueEffectHelper.RemoveGroup(Unit unit, int effectGroupId, RogueRemoveReason reason)`，按效果组逐条反注册，至少覆盖下面几种场景：

1. `命运重置`
   - 遍历当前 `SelectedCardIds`
   - 找到每张卡对应的 `EffectGroupId`
   - 调用 `RemoveGroup`
   - 清理已挂 Buff、任务实例、效果运行时实例、武器附魔和事件订阅
   - 再重建新的卡牌状态
2. `局结束清理`
   - 遍历所有 `RogueEffectGroup`
   - 对 `RemoveOnRunEnd=true` 的组调用 `RemoveGroup`
   - 最后清空 `RogueRunComponent / RogueChoiceComponent / RogueObjectiveComponent / RogueEffectRuntimeComponent`
3. `单张卡被替换`
   - 仅移除旧卡对应组
   - 保留其他效果组运行态

`RemoveGroup` 的执行建议与 `ApplyGroup` 对称：

1. 反注册事件监听
2. 移除由该组创建的 `RogueObjective` 子 Entity
3. 移除由该组创建的 `RogueEffectRuntime` 子 Entity
4. 卸载该组挂上的 Buff
5. 回滚武器附魔和局内修饰器
6. 最后从 `SelectedCardIds / ActiveModifierIds / AppliedBuffIds` 等索引中删掉对应记录

## 6.2 伤害流程

这是最需要改的地方。

建议新增统一伤害上下文：

1. `DamageContext`
   - `SourceUnitId`
   - `TargetUnitId`
   - `WeaponId`
   - `IsBullet`
   - `IsBoss`
   - `BaseDamage`
   - `FinalDamage`
   - `CanDie`
   - `IsCritical`
   - `LifeStealPct`
2. 新增事件：
   - `RogueBeforeDamageApply`
   - `RogueAfterDamageApply`
   - `RogueDamageKilledTarget`

然后统一把：

1. `DamageHelper.Damage`
2. `BulletComponentSystem.OnHit`

都改成走同一套上下文。

这一步建议同时拍板服务端权威数值类型：

1. 服务端 HP 和最终伤害统一按 `long` 整数结算。
2. `BulletComponentSystem.OnHit` 不再直接用 `float` 做权威扣血。
3. 如果未来一定需要小数伤害，优先采用定点/缩放整数，不继续混用 `float` 和 `long`。

建议同时明确一条固定 pipeline，避免多个效果叠加时出现顺序歧义：

1. 计算 `BaseDamage`
2. 应用攻击方增伤、暴击、对怪/对 Boss 修正
3. 应用防御方减伤、固定减伤、护盾前置修正
4. 做致命判定和 `CanDie` 裁决
5. 写入最终扣血并结算死亡
6. 触发吸血、击杀后奖励、击杀任务、死亡后事件

像“致命免死”这类效果必须放在减伤之后、实际扣血之前处理，否则结果会不稳定。

否则这些效果没法稳定支持：

1. 致命伤害免疫
2. 固定减伤
3. 对怪增伤
4. 对低血增伤
5. 吸血
6. 秒杀非 Boss

## 6.3 搜索/容器流程

当前容器系统已经够成熟，但还需要补事件。

建议新增：

1. `RogueSearchStarted`
2. `RogueSearchCompleted`
3. `RogueContainerLootGenerated`
4. `RogueContainerLootTaken`

建议挂点：

1. `ContainerRuntimeHelper.MarkSearchStarted`
2. `ContainerRuntimeHelper.OpenContainerUI`
3. `ContainerRuntimeHelper.GenerateLoot`
4. `ContainerRuntimeHelper.TakeItem / TakeAll`

这样就能覆盖：

1. 搜索速度提升
2. 搜索完容器概率给移速 Buff
3. 未出高品质物品时给金币
4. 修改宝箱/怪物产出权重

如果后续希望让 ECA 流程图直接感知击杀事件，还需要补一件事：

1. 把现有 `BulletKillEvent / UnitDie` 链路桥接到 `ECAFlowEventType.OnTargetKilled`

否则 `OnTargetKilled` 依然只是一个“定义过但没生产触发”的事件名。

## 6.4 区域发现流程

“首次进入区域给奖励”不建议用硬编码位置判断。

建议做法：

1. 地图上放 `ECAPointType` 的区域/地标点
2. 利用 `OnPlayerEnterRange`
3. `RogueRunComponent.VisitedAreaIds` 记录是否已触发

这样就能实现：

1. 新区域首次奖励
2. 特定房间首次奖励
3. 商人/宝箱/怪物区域首次进入特殊逻辑

## 6.5 商人流程

商人不要做成“凭空弹一个 UI”，建议继续走地图点位。

推荐方案：

1. 地图预摆若干 `Merchant` 点位
2. 默认 `SetPointState=Disabled`
3. 肉鸽效果触发时，激活一个商人点位
4. 玩家靠近后走 `ECAInteract`
5. 打开商店 UI，用 `CurrentGold` 购买

这样可以复用：

1. 点位显示
2. 交互范围
3. 小地图表现
4. 玩家进入离开流程

## 6.6 武器改造流程

“攻击距离提高”“弹射”“换弹后强化前三发”“随机附魔”不适合全都做成纯 Numeric。

建议新增 `RogueWeaponModifierComponent`，并在下面入口挂逻辑：

1. `WeaponComponent.CanFire`
2. `WeaponReloadHelper.TryCompleteReload`
3. `BulletComponentSystem.OnHit`
4. `BTWeaponFireHandler`

至少要支持：

1. 命中计数
2. 子弹弹射
3. 下一发/下三发强化
4. 换弹完成事件
5. 武器局内词条

## 6.7 死亡与复活流程

“死亡后概率在复活点复活并随机保留物品”无法只靠 Buff 解决。

必须新增一套死亡裁决流程：

1. `BeforeUnitDie`
2. 判断是否有复活类修饰器
3. 成功则取消死亡
4. 传送到出生点
5. 执行背包/装备随机保留规则

这一块建议落在：

1. `statesync` 的玩家局内流程
2. 必要时借 `battle` 管理复活次数和结算统计

## 6.8 对局时间延长

“本局游戏时长延长 5 分钟”不应挂在玩家 Buff 上。

建议落到 `cn.etetet.battle`：

1. 战局组件记录 `RemainTimeMs`
2. 肉鸽效果触发时调用 `BattleTimeHelper.AddTime`
3. 客户端同步剩余时间

## 6.9 客户端同步方案

本方案不能只停留在服务端，以下效果需要明确客户端消息：

1. 金币
   - `M2C_RogueGoldSync`
2. 雷达扫描和未搜索箱子高亮
   - `M2C_RogueMinimapReveal`
3. 猎杀者地图标记
   - `M2C_RogueTrackedTargetSync`
4. 商人激活/关闭
   - `M2C_RogueMerchantState`
5. 武器临时附魔与枪械改造展示
   - `M2C_RogueWeaponAffixSync`
6. 关键效果提示
   - `M2C_RogueModifierToast`

如果后续做体型变化，还需要额外同步：

1. `M2C_RogueScaleSync`

## 6.10 体型变化流程

设计稿里有：

1. 体型变大，生命值增加
2. 体型变小，血量下降并换速度/伤害

当前仓库没有成熟的“单位体型”权威运行态。

这块必须补一个明确方案，二选一：

1. 走 `NumericType.Scale`，再由客户端视图层读取并改模型缩放
2. 新增专门的 `UnitScaleComponent + 同步消息`

不建议直接只在客户端改 `Transform.localScale`，那样服务端和客户端状态会脱节。

## 6.11 脱战状态流程

“脱战后进入隐身”需要独立的脱战判定。

当前仓库没有现成的 `InCombat / OutOfCombat` 状态组件或事件，建议新增：

1. `CombatStateComponent`
2. `LastDealDamageTime`
3. `LastTakeDamageTime`
4. `OutOfCombatDelayMs`
5. 事件：
   - `UnitEnterCombat`
   - `UnitLeaveCombat`

## 6.12 背包满度流程

“背包空间越满，临时生命增幅越高”不需要新底层，现有 `item` 包已经能取：

1. `GetUsedSlotCount()`
2. `Capacity`

这块需要补的不是数据源，而是：

1. 背包占用率换算规则
2. 刷新时机
3. 对应的临时生命 Buff 或 Numeric 修正

## 6.13 技能禁用流程

“你的技能无法使用，枪械攻速提高 50%”需要一个技能禁用态。

当前 `SpellHelper` 只有 CD/目标/消耗流程，没有统一的“禁止施法”判定。

建议新增：

1. `SkillDisabledComponent` 或 `Numeric/Buff` 标记
2. 在 `SpellHelper.Cast` 入口先检查禁用态
3. 客户端 ActionBar 同步灰显与点击拦截

## 11. 我给你的最终建议

如果这轮只是先定方案，我建议按下面结论拍板：

1. `statesync` 继续做肉鸽主包，不新开包。
2. `RogueCard.BTConfig` 本轮直接废弃，改 `EffectGroupId`。
3. `Buff` 不承担卡池和流程，只承担状态与战斗行为。
4. `BT` 不直接承载选牌逻辑，只承载 Buff 内部执行。
5. 新增 `RogueRuntime` 事件层，专门处理金币、任务、区域、商人、复活、重置牌组。
6. 先统一伤害链路，再做致命免死、吸血、秒杀、固定减伤。
7. 先修当前配置和代码的三个现实问题：
   - 发牌等级与文档不一致
   - `HideTags` 隐藏标签语义未完整接入
   - `ShowTagsBuffId` 当前只配了一档，2 张和 3 张会落同一个 Buff

如果你认可这个方向，下一步最合适的不是直接写所有效果代码，而是先做三件基础工程：

1. 改 `RogueCard` 配置模型
2. 新建 `RogueEffectGroup / RogueEffectEntry`
3. 抽出统一 `RogueEffectHelper + DamageContext`

这三件不先做，后面越写卡，返工越大。
