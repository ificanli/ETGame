# 服务端内网发布指南

## 1. 适用范围

本文档适用于当前工程在 **Windows 单机** 环境下进行 **内网服务端发布与联调**。

默认目标是：

- 服务端运行在一台 Windows 机器上
- 客户端与服务端处于同一局域网
- 先保证服务端可以稳定启动、客户端可以连通
- 不修改服务端业务代码，只调整配置和启动方式

本文档不覆盖以下场景：

- Linux 正式发布流程
- Docker 镜像构建与容器编排
- 多机分布式部署
- 资源热更新发布流程

## 2. 当前结论

针对本工程当前状态，**内网发布服务端不需要强制使用 Aspire，也不需要强制使用 Docker**。

推荐优先采用下面的方式：

- 使用 `dotnet build ET.sln` 编译整个工程
- 在项目根目录下直接启动多个 `ET.App.dll` 进程
- 通过 `Release` 启动配置指定服务端内网地址
- 通过 `GlobalConfig.asset` 指定客户端入口地址

这样做的原因是：

- 当前工程已经支持直接启动 `ET.App.dll`
- 当前仓库存在 Aspire 相关工程和脚本，但它更偏向进程编排与观测，不是当前内网联调的必需项
- 当前仓库没有现成的 `Dockerfile` 或 `docker-compose` 文件，直接上 Docker 反而会增加额外维护成本

## 3. 前置条件

开始之前请确认以下条件：

- 使用 **管理员权限** 打开 PowerShell
- 所有命令都在 **项目根目录** 执行，不要在 `Bin` 目录执行
- 统一使用 `PowerShell`
- 编译命令统一使用 `dotnet build ET.sln`
- 服务端机器和客户端机器在同一局域网
- Windows 防火墙允许服务端程序通信

项目根目录示例：

```powershell
Set-Location D:\05ET\MatchTest\ETGame
```

## 4. 先确认服务器内网 IP

在服务端机器上执行：

```powershell
Get-NetIPAddress -AddressFamily IPv4 |
  Where-Object { $_.IPAddress -notlike '127.*' -and $_.IPAddress -notlike '169.254.*' } |
  Select-Object InterfaceAlias, IPAddress, PrefixLength
```

如果只是快速查看，也可以执行：

```powershell
ipconfig
```

在当前项目联调场景中，优先使用：

- 客户端能够 `ping` 通的地址
- 不属于 `127.0.0.1`
- 不属于 `169.254.x.x`

当前服务器实际内网 IP：

```text
172.16.130.102
```

本文后续所有配置示例、验证命令和启动说明，默认都以 `172.16.130.102` 作为当前服务端内网地址编写。
如果后续服务器网卡地址发生变化，再统一替换本文中的该地址即可。

## 5. 需要修改的配置

### 5.1 服务端机器地址

编辑：

- `Packages/cn.etetet.startconfig/Bundles/Luban/Release/Server/Json/StartMachineConfigCategory.json`
- `Packages/cn.etetet.startconfig/Bundles/Luban/Release/ClientServer/Json/StartMachineConfigCategory.json`

把：

```json
[
  {
    "Id": 1,
    "InnerIP": "127.0.0.1",
    "OuterIP": "127.0.0.1"
  }
]
```

改成：

```json
[
  {
    "Id": 1,
    "InnerIP": "172.16.130.102",
    "OuterIP": "172.16.130.102"
  }
]
```

说明：

- 在当前“同一内网”场景下，`InnerIP` 和 `OuterIP` 通常先填同一个内网地址即可
- 不要保留为 `127.0.0.1`，否则客户端拿到的地址只会指向服务端机器自己

### 5.2 客户端入口地址

如果你使用 Unity 编辑器或本地客户端进行联调，编辑：

- `Packages/com.etetet.init/Resources/GlobalConfig.asset`

至少确认两项：

- `Address` 改成 `172.16.130.102:10101`
- `CodeMode` 使用客户端模式

示例：

```yaml
CodeMode: 1
SceneName: StateSync
Address: 172.16.130.102:10101
```

说明：

- `10101` 是当前 `Release` 配置中的 `RouterManager` HTTP 入口端口
- 客户端会先请求 `http://{Address}/get_router`

### 5.3 当前 Release 配置中的进程与入口

当前 `Release` 配置中，关键进程如下：

- `Process=1`：`ServiceDiscovery`
- `Process=2`：`RouterManager`
- `Process=3`：`Router`，`Num=4`
- `Process=14`：`Realm`
- `Process=15`：`Gate`，`Num=2`
- `Process=25`：`Location`
- `Process=26`：`MapManager`
- `Process=27`：`Match`

当前固定入口端口：

- `RouterManager`：`10101`

注意：

- 当前 `Router`、`Realm`、`Gate` 等大量场景端口仍为 `0`
- 这代表默认采用动态端口分配
- 第一次内网联调可以先接受这一点

## 6. 编译

统一使用以下命令：

```powershell
Set-Location D:\05ET\MatchTest\ETGame
dotnet build ET.sln
```

不要使用其它编译命令替代。

## 7. 防火墙放行

由于当前 `Release` 中有动态端口，第一版联调最省事的方式不是只放某几个端口，而是先允许 `dotnet` 在专用网络入站。

在管理员 PowerShell 中执行：

```powershell
$rule = Get-NetFirewallRule -DisplayName 'ET Server DotNet Inbound' -ErrorAction SilentlyContinue
if (-not $rule) {
    $dotnet = (Get-Command dotnet).Source
    New-NetFirewallRule -DisplayName 'ET Server DotNet Inbound' -Direction Inbound -Action Allow -Program $dotnet -Profile Private
}
```

如果你的安全要求较严格，后续可以改为固定端口策略；本文档先以“快速跑通内网联调”为目标。

## 8. 启动服务端

### 8.1 启动原则

- 必须在项目根目录启动
- 建议先删除旧日志目录
- 当前 `Release` 是多进程配置，需要启动多个实例
- 当前主包 `SceneName` 以 `StateSync` 为准

### 8.2 一键启动脚本

在管理员 PowerShell 中执行：

```powershell
$root = "D:\05ET\MatchTest\ETGame"
$scene = "StateSync"
$config = "Release"

$servers = @(
    @{ Name = "ServiceDiscovery"; Process = 1;  Replica = 1 }
    @{ Name = "RouterManager";    Process = 2;  Replica = 1 }
    @{ Name = "Router-1";         Process = 3;  Replica = 1 }
    @{ Name = "Router-2";         Process = 3;  Replica = 2 }
    @{ Name = "Router-3";         Process = 3;  Replica = 3 }
    @{ Name = "Router-4";         Process = 3;  Replica = 4 }
    @{ Name = "Realm";            Process = 14; Replica = 1 }
    @{ Name = "Gate-1";           Process = 15; Replica = 1 }
    @{ Name = "Gate-2";           Process = 15; Replica = 2 }
    @{ Name = "Location";         Process = 25; Replica = 1 }
    @{ Name = "MapManager";       Process = 26; Replica = 1 }
    @{ Name = "Match";            Process = 27; Replica = 1 }
)

Set-Location $root
Remove-Item .\Logs -Recurse -Force -ErrorAction SilentlyContinue

foreach ($s in $servers) {
    $args = "dotnet .\Bin\ET.App.dll --SceneName=$scene --StartConfig=$config --Process=$($s.Process) --ReplicaIndex=$($s.Replica) --Console=1"
    Start-Process powershell -WorkingDirectory $root -ArgumentList '-NoExit', '-Command', $args
    Start-Sleep -Seconds 1
}
```

### 8.3 单进程手动启动示例

如果你只想先验证某个进程能否起来，可以单独启动：

```powershell
dotnet .\Bin\ET.App.dll --SceneName=StateSync --StartConfig=Release --Process=2 --ReplicaIndex=1 --Console=1
```

上面这条命令对应 `RouterManager`。

## 9. 连通性验证

### 9.1 检查入口端口

在客户端机器或服务端机器执行：

```powershell
Test-NetConnection 172.16.130.102 -Port 10101
```

如果 `TcpTestSucceeded` 为 `True`，说明 `RouterManager` 的入口端口已经可达。

### 9.2 检查路由信息接口

执行：

```powershell
Invoke-WebRequest http://172.16.130.102:10101/get_router
```

如果返回成功，说明客户端拿路由信息这一步已经通了。

进一步检查返回内容时，重点看：

- `Realms` 是否存在
- `Routers` 是否存在
- 返回的地址是否还包含 `127.0.0.1`

如果返回内容里的地址还是 `127.0.0.1`，说明配置没有改对，或者服务端没有完全重启。

### 9.3 检查日志

查看：

- `Logs/`
- `Logs/All.log`

重点关注：

- `Error`
- `Bind`
- `get_router`
- 地址仍然指向 `127.0.0.1`

## 10. 是否需要 Aspire

当前结论：**不是必需品**。

适合考虑 Aspire 的场景：

- 你需要统一管理多个 ET 进程
- 你需要更方便地观察多进程状态
- 你准备进一步接入观测链路

当前不推荐把 Aspire 作为第一次内网发布的前置条件，原因是：

- 直接启动 `ET.App.dll` 已经足够完成当前内网联调
- 当前项目里的 Aspire 更偏向编排与观测，不是服务端运行的唯一入口
- 你先把基础网络、配置和多进程启动跑通，再引入 Aspire，会更稳定

## 11. 是否需要 Docker

当前结论：**不是必需品，也不建议作为第一步**。

原因：

- 当前仓库没有现成的 `Dockerfile`
- 当前仓库没有现成的 `docker-compose` 文件
- 当前 `Release` 默认使用多进程和动态端口，容器化之前需要先明确端口策略

如果后续要做 Docker 化，建议先完成这些前置工作：

- 梳理固定端口策略
- 明确每个进程如何拆容器
- 补齐镜像构建文件
- 补齐容器编排文件

## 12. 关于固定端口的说明

很多内网部署最终都会希望改成固定端口，但**当前工程不能简单把多副本场景直接改成同一个固定端口**。

原因：

- 当前 `Router` 有 `4` 个副本
- 当前 `Gate` 有 `2` 个副本
- 代码里没有看到基于 `ReplicaIndex` 自动为端口做偏移的逻辑

这意味着：

- 如果你把多副本场景直接改成同一个固定端口，多个副本大概率会发生端口冲突

因此当前推荐做法是：

- 第一阶段：保留动态端口，先通过程序级防火墙放行跑通内网联调
- 第二阶段：如果确实要固定端口，再单独设计“副本如何分端口”的方案

## 13. 常见问题

### 13.1 同一个 WiFi 就一定能连上吗

不一定。

还需要同时满足：

- 客户端能访问服务端内网 IP
- 服务端没有把地址配置成 `127.0.0.1`
- `10101` 对局域网开放
- 防火墙没有拦住
- WiFi 没有开启访客隔离或 AP 隔离

### 13.2 为什么客户端还在请求 `127.0.0.1:10101`

通常是以下原因之一：

- `GlobalConfig.asset` 里的 `Address` 没改
- 改的是错误的客户端配置
- 改完没有重启客户端

### 13.3 为什么 `/get_router` 通了，但登录还是失败

常见原因：

- `Realm` 或 `Gate` 返回的地址仍然错误
- 动态端口被防火墙拦截
- 不是所有服务进程都启动了

### 13.4 为什么必须从项目根目录启动

因为当前工程运行时会按相对路径读取：

- `Bin`
- `Packages/.../Bundles/...`
- `NLog.config`

如果你在错误目录启动，通常会出现配置、日志或资源读取失败。

## 14. 最小操作清单

如果你只想快速照着做，按这个顺序执行：

1. 查出服务端机器内网 IP
2. 把 `Release` 的 `StartMachineConfigCategory.json` 改成该内网 IP
3. 把客户端 `GlobalConfig.asset` 的 `Address` 改成 `服务器IP:10101`
4. 执行 `dotnet build ET.sln`
5. 允许 `dotnet` 通过 Windows 防火墙专用网络入站
6. 用本文档的一键脚本启动全部服务端进程
7. 执行 `Test-NetConnection 服务器IP -Port 10101`
8. 执行 `Invoke-WebRequest http://服务器IP:10101/get_router`
9. 确认返回内容里不再是 `127.0.0.1`
10. 启动客户端联调
