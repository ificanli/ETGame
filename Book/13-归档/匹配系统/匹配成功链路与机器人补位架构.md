# 匹配成功链路与机器人补位架构

## 目标

收敛匹配成功后的职责边界，解决三个问题：

1. Match 成功结果广播给所有 Gate，存在无效网络开销。
2. Gate 负责创建匹配机器人，职责越位。
3. 多个 Gate 各自申请 `MapId=0` 时，存在复用运行中副本的串房风险。

## 调整后的职责划分

### Match

- 负责排队、出 `MatchResult`。
- 负责统一创建本局唯一副本。
- 负责初始化 Map 侧对局上下文。
- 负责按 Gate 定向通知匹配成功结果。

### Gate

- 负责接收客户端匹配请求。
- 负责把本地玩家所属 Gate 标识传给 Match。
- 负责通知本地客户端匹配成功。
- 负责把本地真人玩家转发进目标副本。

Gate 不再创建机器人，不再决定哪个 Gate 负责补位。

### Map

- 负责记录本局匹配上下文。
- 负责跟踪真人玩家是否全部进入。
- 负责在真人到齐后本地创建机器人。
- 负责机器人出生点、阵营、AI Buff、武器与被动初始化。

## 当前链路

1. 客户端发送 `C2G_MatchRequest` 到 Gate。
2. Gate 在 `G2Match_MatchRequest.GateActorId` 中写入当前 Gate 的 FiberId。
3. Match 将玩家入队，并记录 `MatchRequest.GateActorId`。
4. 匹配成功后，Match 生成唯一 `MapId`，调用 `A2MapManager_GetMapRequest` 创建专属副本。
5. Match 再调用 `Match2Map_InitMatchCopyRequest` 初始化 Map 的 `MatchCopyContextComponent`。
6. Match 按 `GateActorId -> PlayerIds` 分组，只向相关 Gate 发送 `Match2G_MatchSuccess`。
7. Gate 只处理本地真人玩家，给客户端发 `G2C_MatchSuccess`，并通过 `MapManager2Map_NotifyPlayerTransferRequest` 发起转场。
8. Map 中 `M2M_UnitTransferRequestHandler` 完成单位进图后的标准化初始化，并登记真人进入。
9. 当 `MatchCopyContextComponent` 发现所有真人已进入时，本地创建机器人并完成 AI 初始化。

## 协议调整

### `Match_S_22010.proto`

- `Match2G_MatchSuccess` 新增 `MapId`。
- 新增 `Match2Map_InitMatchCopyRequest / Map2Match_InitMatchCopyResponse`。

## 为什么这样改

### 1. 避免全 Gate 广播

Match 已经知道每个玩家来自哪个 Gate，就没有必要把结果广播给所有 Gate 再本地过滤。

### 2. 避免 Gate 越权

Gate 的核心职责应该是连接、会话和转发，不应该创建战斗单位或承担玩法生成逻辑。

### 3. 避免串房

如果多个 Gate 在匹配成功后各自用 `MapId=0` 去申请副本，`MapManager` 会优先复用同图未满副本，存在把不同对局并到同一副本的风险。

现在改为 Match 先生成唯一 `MapId`，再由所有参与 Gate 和目标 Map 围绕这个固定副本工作。

### 4. 机器人初始化口径统一

机器人改成 Map 本地创建后，出生点分配、阵营、AI Buff、武器初始化都走地图内统一入口，和真人进图时的处理更一致。

## 验证点

1. 同一局跨多个 Gate 的玩家，客户端收到的 `MapId` 必须一致。
2. 不相关 Gate 不应再收到该局 `Match2G_MatchSuccess`。
3. 目标 Map 中，机器人只能在所有真人进入后才创建。
4. 同图并发多局时，不应出现串房。
5. `dotnet build ET.sln` 必须通过。
