# 索敌遮挡与移除手动锁定设计文档

**创建时间**：2026-03-31
**最后更新**：2026-04-01
**状态**：未回归
**关联任务**：M0.2-W2 #13（FEAT-003，与 BUG-010 共用方案）
**涉及包**：cn.etetet.statesync, cn.etetet.btnode, cn.etetet.recast, cn.etetet.map

## 需求概述

当前自动索敌只基于 `AOI + 阵营 + 距离 + 存活` 判断目标合法性，导致墙体后方单位仍可能被玩家自动攻击、机器人 AI、怪物 AI 选中并持续攻击。

本轮用户已确认三点：

1. 玩家自动攻击、机器人 AI、怪物 AI 要一起收敛，不允许只修一条链路。
2. 遮挡判定接受基于现有 `NavMesh/Recast` 能力实现，不额外引入 Unity 物理射线作为服务端主方案。
3. 不再保留“手动锁定目标”功能，相关字段、入口和文档语义都要删除或收敛。
4. 不再保留“直接点击场景中的单位 / 交互点触发交互”链路；ECA、NPC、任务相关交互统一改为交互按钮触发。

当前已完成代码实现与自动化验证，待局内回归；`Raycast` 语义已通过 `Test_Navmesh_SDCMap_LineOfSight_Test` 进行最小闭环验证。

## 问题现状

### 现有根因

- 服务端索敌主逻辑位于 `TargetSelectorHelper`，当前没有任何墙体遮挡判断。
- `BTWeaponHasTarget`、机器人战斗检查、机器人武器战斗检查都依赖同一套 `TargetSelectorHelper.IsValidTarget/SelectTarget`。
- `TargetSelectorComponent` 仍保留 `ManualTargetId`，服务端索敌优先级仍是“手动目标 > 自动目标”。
- 地图点击单位消息 `C2M_ClickUnitRequest` 会把被点击单位直接写入 `TargetComponent.Unit`，形成另一条手动锁定入口。

### 当前受影响链路

- 玩家自动攻击
- 机器人近战/远程 AI
- 怪物及其他复用 `TargetSelectorHelper` 的目标选择链路
- 客户端战斗指示圈/相机文档中的“锁定目标”语义

### 前置核对结论

在开始编码前，已完成两项仓库事实核对：

1. 当前仓库内的 `DotRecast.Detour.DtNavMeshQuery` 已暴露 `Raycast(...)` 方法，源码位于 `Packages/cn.etetet.recast/Scripts/Core/Share/Detour/DtNavMeshQuery.cs`。
2. `cn.etetet.statesync/package.json` 已直接声明依赖 `cn.etetet.recast`，本轮若在 `statesync` 调用 `recast` 能力，不需要额外补包依赖。

但仍需注意：

- 当前工程尚未出现业务层直接调用 `query.Raycast(...)` 的现成案例，因此实施前必须补最小验证用例，不能只凭接口存在就默认行为完全符合预期。
- `AGENTS.md` 的包层级示例没有列出 `cn.etetet.recast`，这是文档清单不全，不等于工程里没有依赖关系。

## 技术方案

### 整体思路

采用“服务端统一目标合法性 + Recast 视线遮挡 + 删除手动锁定语义”的收敛方案。

核心原则：

1. **遮挡判断只放一处**：统一落在 `TargetSelectorHelper` 及其下沉的 Recast 视线辅助方法，避免玩家、机器人、怪物各写一套。
2. **先粗筛再遮挡**：先做 `AOI/阵营/距离/存活` 的低成本过滤，再对候选目标做 NavMesh 视线校验，避免每帧对全部可见单位做重计算。
3. **删除手动锁定，不删除当前战斗目标**：`TargetComponent.Unit` 仍保留，作为当前战斗主目标；删除的是 `ManualTargetId`、`SetManualTarget`、点击敌方单位改写战斗目标这类“手动锁定语义”。
4. **不改 AOI，不改伤害，不改物理层**：本轮只收敛“目标是否可被选中”，不扩散到可见性系统、弹道碰撞或技能命中规则。

### 方案分层

#### 第一层：Recast 视线遮挡辅助

在 `cn.etetet.recast` 的 `PathfindingComponentSystem` 中新增统一辅助方法，例如：

- `HasLineOfSight(float3 from, float3 to, float unitRadius, float maxVerticalDelta, out float hitT)`

建议语义：

- 起点使用施法者/攻击者当前位置
- 终点使用目标当前位置
- 主判断基于当前仓库内已存在的 `DtNavMeshQuery.Raycast(...)`
- 实现时只投影起点以获取 `startRef/startPos`，终点保持原始射线方向，不先吸附回 NavMesh
- 从当前仓库源码注释看，`hit.t == float.MaxValue` 表示无墙体命中；但实施时仍以本仓库单元验证结果为准，不把这一语义写死成无法调整的前提
- 当 `0 <= hit.t < 1` 视为中途撞墙，被遮挡
- 由于该 Raycast 是 2D NavMesh 表面检测，需额外增加一个 `Y` 轴高度差阈值，避免上下层场景误判为可见；初始建议值先用 `4f`

注意：

- 若 `PathfindingComponent` 缺失、起点未投影到 NavMesh，先按兼容策略放行并打诊断日志，避免非战斗场景直接失去索敌能力。
- 该辅助只服务“短距离战斗 LoS”，不作为完整战争迷雾或复杂多层视线系统。
- 实施第一步先补一个最小验证：确认本仓库 `Raycast` 在“无遮挡”“中途撞墙”“上下层同 XZ 不同 Y”三种输入下的实际返回语义，再决定最终业务判断分支。

#### 第二层：TargetSelector 统一接入遮挡

在 `TargetSelectorHelper` 中收敛目标合法性：

- `GetEnemiesInRange` 继续承担粗筛，不在这里做重排序
- `FindBestTarget` 保留现有评分逻辑，但只在“候选目标集合”上挑选可见目标
- `IsValidTarget` 增加遮挡判断，确保缓存目标、Threat 回退目标、BT 复用目标都走同一口径

推荐执行顺序：

1. `AOI`
2. 敌对阵营
3. 射程
4. 存活
5. 视线无遮挡
6. 评分选择

这样可以保证“当前目标被墙挡住”时立即失效并重新索敌，而不是继续对墙后单位保持攻击。

缓存策略补充：

- `FindBestTarget()` 的“重新索敌”过程不使用缓存，仍然对候选目标逐个做实时 LoS 判断。
- 缓存只服务“当前目标是否仍然有效”的高频校验场景，例如 BT 高频 Tick 重复校验当前目标时，避免对同一个目标短时间内重复 Raycast。
- 因此这里的缓存设计不是为了优化全候选扫描，而是为了优化“当前目标续锁”的重复校验。

#### 第三层：统一收敛玩家/机器人/怪物

由于以下入口都依赖 `TargetSelectorHelper`，本轮不建议分别修：

- `BTWeaponHasTarget`
- `AI_RobotCombatCheckHandler`
- `AI_RobotWeaponCombatCheckHandler`
- 其他复用 `TargetSelectorHelper.IsValidTarget/SelectTarget` 的怪物或战斗行为树

原则是：

- 入口层只保留日志和调用
- 目标合法性完全收敛到 `TargetSelectorHelper`

#### 第四层：移除手动锁定与场景直点交互功能

本轮删除的是“手动锁定语义 + 直接点击场景目标触发业务”的整条链路，不是删除当前战斗目标引用，也不是删除交互按钮能力。

明确删除范围：

- `TargetSelectorComponent.ManualTargetId`
- `TargetSelectorComponentSystem.SetManualTarget`
- `TargetSelectorHelper` 中“手动目标优先于自动目标”的逻辑
- 相关测试里对 `ManualTargetId/SetManualTarget` 的断言
- 点击敌方单位后直接改写 `TargetComponent.Unit` 的行为
- 客户端场景点击命中的 `UnitClickHelper.Click(...)`
- 单位信息面板点击后触发的 `UnitClickHelper.Click(...)`
- `C2M_ClickUnitRequest` 内对 `ECAPoint / NPC / 任务 / 非敌对单位` 的业务处理

明确保留范围：

- `TargetComponent.Unit` 作为当前战斗目标引用继续保留
- `C2M_ECAInteract` 及其交互按钮触发链路继续保留
- 目标信息面板仍可基于“当前战斗目标”展示，不再依赖手动锁定来源

对点击链路的最终口径：

- `C2M_ClickUnitRequest` 本轮只保留协议兼容壳，服务端 handler 直接 no-op，不再承担任何交互、任务、NPC 或战斗目标语义
- 客户端不再从场景点击、单位信息面板点击发起 `UnitClickHelper.Click(...)`
- 若后续仍需要“点敌人查看信息”或“点 NPC 弹出信息”，必须走独立按钮或独立协议设计，不能复用旧 click-unit 语义

#### 第五层：客户端表现语义收敛

当前客户端仍有“锁定目标”命名残留，例如：

- `CombatLockCameraComponent`
- `CombatCameraTuningView` 的“锁定目标”参数
- 旧相机文档中“明确锁定目标”描述

本轮建议文档和实现口径同步收敛：

1. 删除“手动锁定目标驱动相机”的产品语义。
2. 战斗圈/UI 只认当前战斗目标，不再区分“手动目标”和“自动目标”。
3. 若自动索敌驱动镜头偏移会造成镜头抖动，则目标偏移能力应整体下线，只保留移动前视偏移；不要在“手动锁定已删除”的前提下保留一套名义上的“锁定镜头”。

墙角抖动风险补充：

- 角色贴墙、探头、墙角擦边时，NavMesh LoS 可能在“可见/不可见”之间快速切换。
- 第一版不建议一开始就引入复杂状态机，但建议预留最小去抖机制：
  - 当前目标连续 `2` 次 LoS 检查失败，或连续遮挡持续 `100ms~150ms` 后，再判定为真正失效。
  - 新索敌流程仍直接实时判定，不增加额外宽限。
- 如果首轮局内回归没有出现明显抖动，可以保持最简实现；若抖动明显，再把上述去抖机制转为正式规则。

## 数据结构与判定规则

### 目标可选中条件

目标必须同时满足：

1. 在 AOI 可见集合中
2. 与施法者敌对
3. 在有效射程内
4. 生命值大于 0
5. 通过 Recast 视线遮挡校验

### 遮挡判定规则

- 优先使用攻击者自身 `PathfindingComponent`
- `NavMesh Raycast` 无遮挡时才允许目标进入最终候选
- 当目标与攻击者的垂直高度差超过 `4f` 时，默认按“不可见”处理，作为上下层误判的首轮保护阈值
- 当前目标被判断为遮挡时，不建议单帧立即失效；建议首版采用“连续 2 次检查失败”或“连续遮挡 >= 100ms~150ms”后失效，防止墙角抖动
- 重新索敌不保留“墙后追踪宽限”，一旦当前目标正式失效，新的候选必须重新通过无遮挡校验
- `PathfindingComponent` 缺失或起点无法投影到 NavMesh 时，按兼容策略放行并打日志，不让非标准场景直接失去攻击能力

### 非目标内的问题

本轮明确不处理：

- AOI 可见性本身的墙体遮挡
- 子弹/技能是否会被墙阻挡
- 多层楼完整视线系统
- 美术碰撞体与 NavMesh 不一致时的精细化修正

## 验收标准

- [ ] 玩家自动攻击不会选中墙体后方敌人。

- [ ] 目标从墙后绕出后，能够重新被自动索敌选中。
- [ ] 同时存在多个候选目标时，被遮挡目标不会被选为最终目标。
- [ ] 不再保留 `ManualTargetId / SetManualTarget / 点击敌方单位锁敌` 这套手动锁定功能。

- [ ] `PathfindingComponent` 缺失或起点无法投影到 NavMesh 的场景下，系统按兼容策略放行，不发生“全部丢失索敌”的功能性退化。
- [ ] 遮挡状态从“不可见”切回“可见”后，目标能在可接受的延迟内重新进入索敌结果。
