# 移动轨迹回放测试说明

## 目的

- 解决“普通单测跑不出玩家真实操作链路”的问题。
- 把一次真实操作里的输入发送时序固化成可回放测试。
- 为后续“点一下走两步 / 转一圈补转一圈 / 松手后尾巴很长”这类问题提供稳定复现入口。

## 为什么旧测试抓不住

- 旧测试大多直接构造客户端 pending 输入或直接喂权威包。
- 它们验证的是“局部算法”，不是完整时序链路。
- 这次真实问题涉及：
  - 客户端输入采样与合并发送
  - `NetClient -> Gate -> Map` 到达顺序
  - 服务端 `Move16msTick`
  - 客户端权威同步与本地预测冻结

## 新增日志点

- 客户端发送：
  - `[NavMove][TraceInputSend]`
- 服务端处理输入：
  - `[NavMove][TraceServerInputRecv]`
- 客户端接收权威包：
  - `[NavMove][TraceAuthRecv]`

这些日志都带精确时间戳，可用于还原真实链路。

## 回放格式

当前测试支持两种输入格式：

### 1. 紧凑格式

```text
# deltaMs|seq|dirX|dirZ
0|1|1.000000|0.000000
32|2|0.707107|0.707107
32|3|0.000000|0.000000
```

- `deltaMs`：相对上一条输入的等待时间
- `seq`：客户端输入序号
- `dirX/dirZ`：发送给服务器的世界方向

### 2. 直接粘贴客户端发送日志

```text
[NavMove][TraceInputSend] unitId=..., clientNow=123456, seq=260, dirX=0.736886, dirZ=-0.676017, source=joystick, reason=coalesced-turn
[NavMove][TraceInputSend] unitId=..., clientNow=123489, seq=261, dirX=0.710785, dirZ=-0.703409, source=joystick, reason=coalesced-turn
[NavMove][TraceInputSend] unitId=..., clientNow=123522, seq=262, dirX=0.707794, dirZ=-0.706419, source=joystick, reason=coalesced-turn
[NavMove][TraceInputSend] unitId=..., clientNow=123551, seq=263, dirX=0.000000, dirZ=0.000000, source=idle, reason=force
```

测试会自动用 `clientNow` 计算每一步的 `deltaMs`。

## 当前测试文件

- `Packages/cn.etetet.test/Scripts/Hotfix/Test/Test_Joystick_TraceReplay_Test.cs`

当前包含 3 类用例：

- `Test_Joystick_TraceReplay_Smoke_Test`
  - 最小冒烟用例，验证轨迹文本可解析、可回放、可量化 stop 接受延迟与 stop 后继续前进距离。
- `Test_Joystick_TraceReplay_LogSeq29_StopTail_Test`
  - 使用 `2026-03-26` 真实 `Editor.log` 中 `seq=26..29` 的输入发送节奏做回放。
  - 目标是把“真实输入节奏”固定下来，不再只跑人造压力输入。
- `Test_Joystick_TraceTimeline_LogSeq29_StopTail_Test`
  - 使用同一段真实日志里的 `TraceInputSend/TraceServerInputRecv/TraceAuthRecv` 做离线时序断言。
  - 目标是固定这次真实问题的关键特征：
    - `seq=29 stop` 从客户端发出到服务端收到，延迟 `205ms`
    - 客户端从 stop 发出到收到停步权威包，延迟 `492ms`
    - stop 发出后，服务端旧输入尾巴仍连续发了 `18` 个权威移动包
    - 这些尾巴包的 `moveSeq` 范围是 `590..607`，真正停步包是 `608`

这 3 类用例分工不同：

- `Smoke` 看“能力存在”
- `Replay_LogSeq29` 看“真实输入节奏回放”
- `Timeline_LogSeq29` 看“真实故障样本分析”

## 录制真实轨迹的方法

1. 进入游戏，打开包含上述 `Trace*` 日志的版本。
2. 按真实方式复现一次问题。
3. 从 `Editor.log` 中提取同一段的：
   - `[NavMove][TraceInputSend]`
   - `[NavMove][TraceServerInputRecv]`
   - `[NavMove][TraceAuthRecv]`
4. 先把 `TraceInputSend` 粘进测试，形成“客户端发送轨迹回放”用例。
5. 如果还不够接近真实问题，再补“服务端接收时序回放”测试层。

## 下一步建议

- 如果后面又抓到新的真实坏样本，优先补：
  - `TraceInputSend`
  - `TraceServerInputRecv`
  - `TraceAuthRecv`
- 然后做两件事：
  - 先新增一条 `TraceReplay` 用例，固定真实输入节奏
  - 再新增一条 `TraceTimeline` 用例，固定真实坏样本的关键时序指标
- 这样可以把“是否真能复现”和“这次日志到底坏在哪里”分开验证，避免旧压力测试通过但真实操作仍然出问题。
