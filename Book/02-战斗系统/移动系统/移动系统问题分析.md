## 问题一：补帧时 `nowMs` 不递增，节流逻辑失效（中）

### 位置

`TimerComponentSystem.cs` → `UpdateChannel` → while 补帧循环（约第 487 行）

### 问题描述

补帧 while 循环中，每次 Tick 传递给业务的 `NowMs` 是同一个值（`UpdateChannel` 入参的 `nowMs`），即本轮 `Update` 的当前时间，不随补帧次数递增。

```csharp
while (channel.AccumulatorMs >= channel.IntervalMs && frameTickCount < channel.MaxCatchUpCount)
{
    // ...
    EventSystem.Instance.TryInvoke(
        channel.TickInvokeType,
        new HighFrequencyTickCallback
        {
            NowMs = nowMs,  // 每次补帧 nowMs 都是同一个值
            DeltaTimeMs = channel.IntervalMs,
            // ...
        });
    channel.AccumulatorMs -= channel.IntervalMs;
}
```

### 影响

- `TickFixedStep` 里基于 `nowMs` 的日志节流（`LastTickTraceLogTime`、`LastNavResolveLogTime`）在补帧时全部失效，同一帧内多次补帧会打出大量重复日志
- 将来任何 Tick 内基于 `nowMs` 的时间相关逻辑都会在补帧时产生错误结果

### 修复建议

每次补帧时 `nowMs` 应对应该帧的逻辑时间：

```csharp
int catchUpIndex = 0;
while (channel.AccumulatorMs >= channel.IntervalMs && catchUpIndex < channel.MaxCatchUpCount)
{
    long tickNowMs = nowMs - channel.AccumulatorMs + channel.IntervalMs;
    // 传 tickNowMs 而不是 nowMs
    channel.AccumulatorMs -= channel.IntervalMs;
    ++catchUpIndex;
}
```

## 问题二：`uint` 序号回绕导致移动失效（中）

### 位置

`C2M_JoystickInputHandler.cs`，约第 22 行

### 问题描述

输入序号使用 `uint`，服务端用 `<=` 直接比较来丢弃旧包：

```csharp
if (message.InputSequence <= joystickMove.LastClientInputSequence)
{
    // 丢弃
}
```

当序号从 `0xFFFFFFFF` 回绕到 `0` 时，回绕后的小序号会被认为是旧包而全部丢弃，导致玩家移动完全失效，直到重连。

`uint` 的最大值约 42 亿，单局游戏时间不长时触发概率很低，但对于长期在线服务来说是确定存在的 Bug。

### 修复建议

使用环形序号比较：

```csharp
private static bool IsSequenceNewer(uint incoming, uint last)
{
    // 环形比较：差值在半圈以内认为是新包
    return (int)(incoming - last) > 0;
}
```

或者改用 `long` 类型序号，彻底避免回绕问题。

## 问题三：`InputSequence == 0` 绕过序号校验（中）

### 位置

`C2M_JoystickInputHandler.cs`，约第 20 行

### 问题描述

```csharp
if (message.InputSequence > 0)
{
    // 才做序号校验
}
```

当客户端发送的包 `InputSequence == 0` 时，完全跳过序号校验，直接应用输入。这意味着：

- 旧输入包可以用 `InputSequence = 0` 绕过防乱序保护
- 停步之后如果收到 `InputSequence = 0` 的移动包，会重新触发移动

### 修复建议

序号从 `1` 开始，服务端不接受 `InputSequence == 0` 的包，或者去掉 `> 0` 的特判，统一走序号校验逻辑。

## 问题四：`BulletTickComponent` 重复注册通道（低）

### 位置

`BulletTickComponentSystem.cs`，`Awake` 方法

`FiberInit_Map.cs`，约第 19 行

### 问题描述

`FiberInit_Map` 中已经注册了 `Bullet33ms` 通道：

```csharp
highFrequencyScheduler.RegisterChannel(HighFrequencyChannelConfigFactory.CreateBullet33ms());
```

`BulletTickComponent.Awake` 中又注册了一次：

```csharp
scheduler?.RegisterChannel(HighFrequencyChannelConfigFactory.CreateBullet33ms());
```

`RegisterChannel` 对重复注册会做配置一致性校验，配置一致时静默通过，目前不会出错。但职责不清晰：一旦两处配置出现不一致，会直接抛异常，且错误信息不容易定位根因。

### 修复建议

`BulletTickComponentSystem.Awake` 去掉 `RegisterChannel` 调用，通道注册统一在 `FiberInit_Map` 中完成。

## 问题五：自机收到权威包直接硬设位置，无平滑处理（低）

### 位置

`M2C_JoystickMoveHandler.cs`，约第 65 行

### 问题描述

自机收到服务端权威位置后直接硬设：

```csharp
if (unit.IsMyUnit())
{
    unit.Position = newPosition;
    return;
}
```

`JoystickMoveAuthorityStateComponent` 中保存了 `LastSpeed`、`LastDirection`、`LastSyncTime` 等状态，但客户端渲染层没有消费这些数据做插值，这些字段目前只用于日志打印。

如果网络抖动导致某一帧服务端包延迟到达，自机会直接瞬移到权威位置，用户侧表现为角色跳帧。

### 修复建议

对自机应用权威位置时，根据延迟大小决定是否插值：
- 位置差异在阈值以内（如 `0.5m`）：平滑插值
- 位置差异过大（如 `>2m`）：直接硬校正

## 问题六：`M2C_JoystickMoveHandler` 中两个连续的 `IsMyUnit()` 判断（低）

### 位置

`M2C_JoystickMoveHandler.cs`，约第 59~70 行

### 问题描述

```csharp
if (unit.IsMyUnit())
{
    // 打日志
}
if (unit.IsMyUnit())
{
    unit.Position = newPosition;
    return;
}
```

两个连续的 `if (unit.IsMyUnit())` 可以合并为一个。不影响正确性，但说明这段代码是分阶段添加的，结构不清晰，后续维护容易遗漏。

### 修复建议

合并为一个 `if` 块。

## 问题七：`JoystickMoveComponent` 不随停步移除（低）

### 位置

`C2M_JoystickInputHandler.cs`，约第 12 行

### 问题描述

组件在首次收到输入时按需创建：

```csharp
JoystickMoveComponent joystickMove = unit.GetComponent<JoystickMoveComponent>();
if (joystickMove == null)
{
    joystickMove = unit.AddComponent<JoystickMoveComponent>();
}
```

但没有对应的「停步后移除组件」逻辑，组件会一直挂在 Unit 上，直到 Unit 销毁才释放。

对于机器人（Robot）频繁创建销毁的场景，每个 Robot 停步后会留下一个空载的 `JoystickMoveComponent`，直到 Robot Unit 被销毁才释放内存。数量多时会产生不必要的内存占用。

### 修复建议

可以接受当前行为（组件生命周期绑定 Unit），但需要确认这是有意为之，并在注释中说明。如果后续有大量 Robot，建议在停步确认后移除组件。

## 附：补帧引发位移突变的机制说明

`HighFrequencySchedulerComponent` 由 ET 的 `IUpdate` 驱动，`Update` 调用间隔不固定。当服务器某帧业务较重时，`elapsedMs` 可能超过 50ms，`Move16ms` 通道会触发最多 3 次补帧，这 3 帧在同一个 `Update` 调用内同步执行。

表现：玩家在 3×16ms = 48ms 内连续移动了 3 步，但这 3 步对应的广播是在同一个真实帧内发出的，客户端会在同一帧内连续收到 3 个位置更新，产生明显的位置跳变。

`MaxCatchUpCount=3` 的上限保证了不会无限补帧，是正确的兜底机制。但补帧本身引起的位移突变目前没有在客户端做任何缓解处理（参见问题五）。
