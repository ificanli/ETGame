# 移动预测系统简化重构设计文档

**创建时间**：2026-03-29
**最后更新**：2026-03-29
**状态**：可实施
**关联任务**：M0.2-W2（从 W1 #2 摇杆拉回修复演化而来）
**涉及包**：cn.etetet.map, cn.etetet.statesync

## 需求概述

W1 #2 摇杆拉回修复经过 6 轮迭代仍未通过实机验收，根本原因不是参数调不对，而是当前架构本身的复杂度已经超出了项目需要。本文档提出一个简化重构方案，彻底替换现有的"输入回放重协调（Replay Reconciliation）"架构。

## 问题分析

### 当前架构回顾

现有移动预测基于 FPS 竞技级的"输入回放重协调"模型：

```
FinalTarget = AuthoritativePosition + PredictedDelta + VisualCorrection
```

客户端维护最多 64 条未确认输入历史（`PendingMoveInputs`），每收到一个服务端权威包，就从权威位置出发重放所有未确认输入，重新计算 `PredictedDelta`。在此基础上还叠加了 6 层平滑/补偿机制。

### 6 轮迭代失败的根因

| 轮次 | 修复内容 | 引入的新问题 |
|------|---------|------------|
| 1 | 保留活跃输入 lead，修复每包清零 | target 后退抖动 |
| 2 | target 后退量转 VisualCorrection | 急转向跳点 |
| 3 | 超限重定向统一限速 | PredictedDelta 持续失控增长 |
| 4 | 双层限幅（运行期 + 回放重建） | 停步被硬钉死，明显卡顿 |
| 5 | 停步改 authority 收敛 → 又回退到冻结语义 | 仍未解决，做 A/B 验证中 |
| 6 | lead 窗口 0.12→0.06 | 手感变差，立即撤回 |

每轮修复都是在上一轮的补丁上叠新补丁。6 层平滑机制互相耦合，23 个 magic constants 中任何一个变化都连锁影响其他层，参数空间已经不可人工搜索。

### 架构与项目需求不匹配

Replay Reconciliation 的适用场景是：

- **高延迟 PvP**（100ms+ RTT）
- **命中判定精度要求高**（FPS/格斗）
- **服务端广播频率低**（需要客户端用更多输入历史填补空白）

本项目实际情况：

- **PvE 俯视角射击 + 肉鸽**，不需要毫秒级命中判定
- **服务端 16ms 高频 tick + 广播**，客户端几乎实时收到权威位置
- **内网/局域网为主**，延迟极低
- **真正的体验痛点**是"流畅度"和"不穿墙"，不是"预测精度"

## 目标

核心验收目标（按优先级）：

1. **平地持续移动不拉回** — 持续同向推杆，无可感知的抖动或回撤
2. **松手不续走** — 松手后角色立即停步，不被 authority 尾包带着平滑前移
3. **贴墙不穿墙** — 保留沿墙滑动能力，不引入新的穿墙
4. **远端不抖** — 远端单位移动表现平滑

预期收益（不作为验收标准）：

- 客户端移动代码量显著减少
- 可调常量从 23 个降到个位数
- 默认无诊断日志刷屏

## 技术方案

### 核心思路：即时本地运动 + 权威融合

抛弃"输入回放重协调"，改用三层单向数据流：

```
Authority（服务端广播）
   ↓ 只写 AuthoritativePosition
Local（客户端输入 + NavMesh）
   ↓ 只写 LocalPredictedPosition → TargetPosition
Visual（Transform 渲染跟随）
   ↓ 只读 TargetPosition → 做 MoveTowards 平滑
GameObject.transform.position
```

**写权限边界（硬规则，不可违反）**：

| 数据 | 谁可以写 | 谁可以读 |
|------|---------|---------|
| AuthoritativePosition | 仅 M2C_JoystickMoveHandler 收包时 | Local 层、诊断日志 |
| LocalPredictedPosition | 仅 Update 中的本地运动 + 权威修正 | Visual 层 |
| TargetPosition | 仅 Update 末尾赋值 = LocalPredictedPosition | MoveVisualTowardsTarget |
| transform.position | 仅 MoveVisualTowardsTarget | 渲染管线 |

**禁止反向写回**：transform 不得写回 TargetPosition，TargetPosition 不得写回 LocalPredictedPosition，Local 不得写回 Authority。当前旧代码中 `ChangePosition_SyncGameObjectPos` 里存在的类似反写必须在重构中清除。

### 与现有方案的对比

| 维度 | 现有方案（Replay Reconciliation） | 新方案（Local + Blend） |
|------|-----------------------------------|------------------------|
| 数据流 | 双向混杂，多处互写 | 单向 Authority→Local→Target→Transform |
| 位置概念 | Auth + PredictedDelta + VisualCorrection | Authority + Local（显示层只做渲染跟随） |
| 平滑机制 | 6 个独立的、互相耦合 | 1 个统一的 authority 融合 |
| 停步处理 | PendingStop + Anchor + Freeze + Cap | 零输入方向守卫（见下文） |
| 墙碰撞 | 服务端 + 客户端双重 NavMesh + blocked 计数 + hold | 客户端本地 NavMesh（输入运动 + 权威修正均走表面约束） |
| 输入历史 | 64 条 PendingMoveInputs + Replay | 不需要 |
| 包排序 | MoveSequence 去重 | **保留 MoveSequence 去重**（底线设施） |
| 可调常量 | 23 个 | ~7 个 |

#### 2. 本机单位每帧更新

```csharp
// UnitViewInterpolationComponentSystem.Update（本机单位路径）
public static void Update(this UnitViewInterpolationComponent self)
{
    float dt = Time.deltaTime;
    var pathfinding = self.GetParent<Unit>().GetComponent<PathfindingComponent>();

    // 第一步：本地输入运动（NavMesh 约束）
    if (self.LocalMoveSpeed > 0.01f)
    {
        Vector3 desired = self.LocalPredictedPosition
            + self.LocalMoveDirection * self.LocalMoveSpeed * dt;
        if (pathfinding != null)
            pathfinding.TryMoveAlongSurface(self.LocalPredictedPosition, desired, out desired);
        self.LocalPredictedPosition = desired;
    }

    // 第二步：权威融合（也走 NavMesh 约束）
    ApplyAuthorityCorrection(self, pathfinding, dt);

    // 第三步：更新视觉目标
    self.TargetPosition = self.LocalPredictedPosition;
    MoveVisualTowardsTarget(self, dt);
}
```

#### 3. 权威融合

```csharp
const float SnapThreshold = 2.0f;         // 超过此距离直接传送
const float CorrectionRate = 8.0f;         // 比例修正系数（gap * rate * dt）
const float CorrectionDeadzone = 0.005f;   // 低于此距离不修正，避免微抖

static void ApplyAuthorityCorrection(
    UnitViewInterpolationComponent self,
    PathfindingComponent pathfinding,
    float dt)
{
    Vector3 diff = self.AuthoritativePosition - self.LocalPredictedPosition;
    float gap = new Vector2(diff.x, diff.z).magnitude;

    if (gap > SnapThreshold)
    {
        // 传送
        self.LocalPredictedPosition = self.AuthoritativePosition;
        return;
    }

    if (gap <= CorrectionDeadzone)
        return;

    // 零输入方向守卫：本地无输入时，只允许修正缩小 gap，不允许把 local 往前拉
    // 这防止松手后被 authority 尾包带着"平滑续走"
    if (self.LocalMoveSpeed < 0.01f)
    {
        // 判断 authority 是否在 local 前方（沿 local→auth 方向）
        // 如果 authority 跑到了 local 前方，不追
        // 只有当 local 跑到了 authority 前方时才允许修正（回拉到 authority）
        Vector3 localToAuth = self.AuthoritativePosition - self.LocalPredictedPosition;
        // 使用上次有输入时的方向来判断"前方"
        // 简化为：不修正。零输入时 local 已经停了，等 authority 也停了再说
        // 如果 authority 最终停在 local 后方（local 超前），才需要修正回来
        // 这里用一个简单判断：如果 gap 在增大（authority 在远离），不追
        return; // 零输入时不修正，让 local 原地等待
    }

    // 有输入时：比例修正，gap 越大修正越快，自然趋零
    float correction = gap * CorrectionRate * dt;
    Vector3 correctedPos = Vector3.MoveTowards(
        self.LocalPredictedPosition, self.AuthoritativePosition, correction);

    // 修正也走 NavMesh 约束，避免切墙
    if (pathfinding != null)
    {
        pathfinding.TryMoveAlongSurface(self.LocalPredictedPosition, correctedPos, out correctedPos);
    }

    self.LocalPredictedPosition = correctedPos;
}
```

**关键设计决策**：

**Q: 为什么零输入时不做 authority 修正？**

因为松手后服务端仍在处理最后几个尾包，authority 会继续前进。如果此时追 authority，就会出现"松手后角色被带着走"的续走问题——这正是 W1 #2 最难搞的 bug。

零输入时让 local 原地停住。服务端处理完尾包也会停下来。最终两者之间的 gap 极小（正常延迟下 < 0.05m，不可感知）。如果由于异常情况 gap 较大，下次玩家按下摇杆时修正会自然生效。

**Q: 这不会导致稳态误差吗？**

不会。有输入时的修正公式 `correction = gap * rate * dt` 是比例控制，gap 指数衰减趋零，没有固定的 threshold 死区来卡住收敛。`CorrectionDeadzone = 0.005f` 只是为了避免浮点微抖，远低于可感知阈值。

**Q: 为什么 CorrectionRate 用固定系数 8.0 而不是 speed * ratio？**

比例修正的收敛速度由 `rate` 决定，与角色移动速度无关。rate=8 意味着每秒修正当前 gap 的 800%，相当于 gap 每帧缩小约 13%（60fps），大约 0.15s 内从 0.1m 收到不可感知。这个值可以实测微调，但范围在 5-15 之间都是合理的。

#### 4. 停步语义

停步不需要显式的 PendingStop 状态机，只靠权威修正中的**零输入方向守卫**：

```
松手 → LocalMoveSpeed = 0 → local 停住
       ↓
服务端尾包 → authority 继续前进
       ↓
零输入守卫 → 不追 authority → local 原地不动 → 无续走
       ↓
服务端也停 → authority 停在 local 前方一点点（< 0.05m）
       ↓
玩家下次按摇杆 → 有输入，修正生效 → gap 自然消解
```

**兜底**：如果停步后 gap 持续 > SnapThreshold（不应发生，但防御性设计），snap 会强制对齐。

**如果实测发现零输入原地等待不够好**（例如某些场景下 authority 停的位置和 local 差距可感知），可以降级到"最小停步状态"：只加一个 `bool StopAnchorActive` + `Vector3 StopAnchorPosition`，在松手时记录当前位置作为锚点，直到服务端报告 speed=0 时清除。但**先以无状态方案入手**，能不加就不加。

#### 5. 收到权威消息时

```csharp

if (message.MoveSequence <= syncState.LastAppliedMoveSequence)
```

**保留 MoveSequence 去重**是底线设施，防止乱序/重复包。
**保留 LastProcessedInputSequence** 用于日志对账和未来可能的停步时序判断，但不参与任何 replay 逻辑。

#### 6. 远端单位

远端单位复用同一套 `LocalPredictedPosition` + `LocalMoveDirection/Speed` 字段：

- 收到权威包 → 重置 `LocalPredictedPosition = message.Position`，更新方向和速度
- 每帧 Update → 按方向/速度线性外推（不走 NavMesh，远端无 pathfinding）
- 收到新包时自然重置，MoveVisualTowardsTarget 本身已经是平滑的

与现有远端逻辑实质不变。

**保留**：

- `ReplayPendingMoveInputs` / `ReplayPendingMoveSegment`

- `ResolveLocalConstrainedPrediction` / `TryResolveConstrainedStep` / `TryGetAlignedConstrainedMotion`

#### 8. 按需诊断（默认静默）

保留 3 个诊断点，全部在编译期开关 `ET_ENABLE_MOVE_DIAGNOSTIC` 下：

1. **权威包到达时**：如果 `gap > 0.5m`，打一次 warning（节流 200ms）
2. **零输入超时**：如果松手后 > 1s 仍有 gap > 0.1m 且 authority speed > 0，打一次 warning
3. **snap 触发时**：记录 snap 前后位置

日志量预估：正常游玩 = 0 条；异常时 < 5条/秒。

## 回归测试计划

重写 `Test_ClientInputReplayReconciliation_Test.cs`，覆盖 4 组场景：

### 1. 持续同向移动

- 模拟：本机持续向 +X 输入，每 33ms 收到一个 authority 包（位置沿 +X 前进）
- 验证：`LocalPredictedPosition` 持续平滑前进，gap 在 `CorrectionDeadzone` ~ `0.1m` 之间波动，无回退
- 关键指标：连续 10 个 authority 包后，`gap < 0.1m`

### 2. 松手停步

- 模拟：先持续移动建立 gap，然后本地输入置零，再收 2-3 个 authority 尾包
- 验证：`LocalPredictedPosition` 在输入置零后不再前进（零输入守卫生效），即使 authority 继续前进
- 关键指标：松手后 `LocalPredictedPosition` 偏移量 < 0.001m

### 3. 贴墙滑动

- 模拟：本机向墙体方向输入 + 权威修正
- 验证：`TryMoveAlongSurface` 对输入运动和权威修正都生效，不穿墙
- 关键指标：`LocalPredictedPosition` 始终在 NavMesh 表面上

### 4. 旧包/乱序包丢弃

- 模拟：发送 MoveSequence = 5, 3, 6
- 验证：sequence=3 被丢弃，authority 只更新了 5 和 6
- 关键指标：`LastAppliedMoveSequence` 最终 = 6

## 风险评估

| 风险 | 严重度 | 缓解措施 |
|------|--------|---------|
| 零输入不修正导致停步后 gap 可感知 | 中 | 正常延迟下 gap < 0.05m 不可感知；如实测不够好，加最小停步状态（见第 4 节末尾降级方案） |
| 权威修正走 NavMesh 有性能开销 | 低 | 每帧最多 1 次 TryMoveAlongSurface 调用，与本地输入运动相同量级 |
| 客户端 NavMesh 与服务端不一致造成持续偏移 | 中 | 比例修正持续生效 + SnapThreshold 兜底 |
| 高延迟环境下 gap 持续较大 | 低 | PvE 可接受；CorrectionRate 可调高 |

## 验收标准

- [ ] 持续同向平地移动时流畅，无可感知的拉回或抖动
- [ ] 松手立即停步，无续走（不被 authority 尾包带着走）
- [ ] 贴墙时沿墙滑动，不穿墙
