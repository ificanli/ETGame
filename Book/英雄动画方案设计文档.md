# 英雄动画方案设计文档

## 1. 背景

当前已经完成以下链路：

- 客户端可以在 Lobby 中选择英雄与武器。
- 进入对局场景后可以成功生成对应英雄。
- Unit 生成时已经自动挂载 `AnimatorComponent`。
- 武器切换和开火消息已经有客户端处理入口。

当前需要解决的问题是：

1. 英雄动画如何设计，才能覆盖空手、持武器、射击、切枪等状态。
2. 在当前 ET + Unity + YooAsset + Package 架构下，应该继续使用 `Animator`，还是切换到 `Playable`。
3. 现有动画资源尚未绑定到目标角色骨骼，应如何完成绑定与导入。

## 2. 当前项目现状

### 2.1 场景内角色已经接入 Animator 体系

角色创建完成后，当前会自动添加 `AnimatorComponent`：

- `Packages/cn.etetet.map/Scripts/HotfixView/Client/AfterUnitCreate_CreateUnitView.cs`

说明：

- 角色的表现主链路已经是 Unity `Animator`。
- 如果要改为 `Playable` 主驱动，需要额外替换整条运行时驱动链路。

### 2.2 现有 Animator 驱动方式

当前 `AnimatorComponentSystem` 的工作方式是：

- 启动时读取 `Animator` 和参数表
- 通过 `SetFloat / SetBool / SetInt / SetTrigger` 控制状态
- 通过 `MotionType` 触发部分动作

相关文件：

- `Packages/cn.etetet.map/Scripts/ModelView/Client/Unit/AnimatorComponent.cs`
- `Packages/cn.etetet.map/Scripts/HotfixView/Client/Unit/AnimatorComponentSystem.cs`
- `Packages/cn.etetet.map/Scripts/Model/Share/MotionType.cs`

这说明当前项目已经具备：

- 参数驱动型 Animator 接入方式
- Unit 级别的动画入口
- 可继续扩展的动作控制基础

### 2.3 武器链路已经预留动画接入口

武器切换消息里已经明确留了 TODO：

- `Packages/cn.etetet.statesync/Scripts/Hotfix/Client/M2C_SwitchWeaponHandler.cs`

其中已经写明：

- 切换武器模型
- 切换动画状态机

这说明武器姿态动画本来就应该接在这条客户端消息链路上，而不是另起一套完全独立的表现系统。

### 2.4 资源层已有可复用动画控制器资产

项目内已经存在 Blink 角色控制器与 Mask 资源，例如：

- `Packages/cn.etetet.statesync/Assets/GameRes/Blink/Characters/Animators/CharacterAnimator.controller`
- `Packages/cn.etetet.statesync/Assets/GameRes/Blink/Characters/Animators/Mask/UpperBody.mask`

现有控制器中已经能看到这些参数或状态：

- `MoveSpeed`
- `MeleeAttack1`
- `MeleeAttack2`
- `MeleeAttack3`
- `GetHit`
- `Dead`
- `isAiming`

这说明项目并不是“没有动画基础”，而是当前英雄动作需求与现有控制器还没有完成映射。

## 3. 已有动画资源整理

当前你给出的目标动画资源是：

- 空手 Idle
- 空手移动
- 持某个武器的 Idle
- 持某个武器的射击
- 持某个武器的移动
- 切换武器

从系统设计角度看，这批资源最自然可以拆成三类：

### 3.1 姿态类

- 空手 Idle
- 持武器 Idle

### 3.2 移动类

- 空手移动
- 持武器移动

### 3.3 动作类

- 持武器射击
- 切换武器

这三类在运行时的地位不同：

- 姿态类和移动类是持续态
- 射击和切枪是一次性动作

因此不能把它们都按“同一种状态”处理。

## 4. 推荐动画方案

## 4.1 总体结论

推荐方案：

- 场景内战斗角色继续使用 `Animator` 作为主动画系统。
- 动画设计采用“持续态 + 一次性动作”分层。
- 多个骨架兼容的人形英雄共用一套基础状态机。
- 不同英雄的差异动作通过 `AnimatorOverrideController` 覆盖。
- UI 预览角色后续可以单独考虑 `Playable`，但不作为当前主链路。

不推荐方案：

- 当前阶段直接把战斗主链路整体改成 `PlayableGraph`。

原因：

- 工程收益低于改造成本。
- 当前 Unit 创建、消息驱动、BT 动作入口、动画参数系统都已围绕 `Animator` 建立。
- 现在最缺的是状态设计和资源绑定，不是动画图运行时能力。

## 4.2 动画状态设计

推荐把角色动画拆成三个维度。

### 4.2.1 Locomotion 层

负责角色持续状态：

- 空手待机
- 空手移动
- 持武器待机
- 持武器移动

建议使用参数：

- `MoveSpeed: float`
- `WeaponPose: int`

建议定义：

- `WeaponPose = 0`：空手
- `WeaponPose = 1`：主武器姿态
- `WeaponPose = 2`：副武器姿态

如果当前阶段主武器和副武器动作完全一样，也可以先统一成：

- `WeaponPose = 0`：空手
- `WeaponPose = 1`：持武器

### 4.2.2 Action 层

负责一次性动作：

- 射击
- 切换武器

建议使用参数：

- `Fire: Trigger`
- `SwitchWeapon: Trigger`

### 4.2.3 WeaponModel 层

负责手上的可见武器模型，不直接塞进 Animator 状态机。

应由武器切换消息驱动：

1. 卸下旧武器模型
2. 挂上新武器模型
3. 设置 `WeaponPose`
4. 触发 `SwitchWeapon`

### 4.2.4 UpperBody 层

如果角色需要边移动边射击，那么动画设计不能只靠单层全身状态机，必须支持上下半身分离。

推荐做法：

- 下半身继续播放 locomotion
- 上半身单独播放持枪、射击、切枪

推荐使用：

- `Animator Layer`
- `AvatarMask`

而不是当前阶段直接切到 `Playable` 主驱动。

### 4.2.5 Skill 层

不同角色可以有不同技能动作，但不建议因此为每个角色单独做一整套 Animator Controller。

推荐做法：

- 所有英雄共用同一套基础状态机结构
- 技能动作以“动作槽位”形式预留
- 每个英雄通过 `AnimatorOverrideController` 覆盖对应槽位的 clip

建议技能动作先按槽位设计，而不是直接按技能 ID 设计。

第一版建议预留：

- `Skill1`
- `Skill2`
- `Skill3`
- `Ultimate`

如果后续技能类型复杂，也可以改成动作类别槽位，例如：

- `CastShort`
- `CastMedium`
- `DashSkill`
- `ChannelSkill`
- `Ultimate`

## 4.3 推荐状态机结构

推荐先做一个 Controller，不要一开始就拆多套 Controller。

推荐命名：

- 基础状态机：`HeroBase.controller`
- 英雄覆盖控制器：
  - `Agou_Override.overrideController`
  - `Ayin_Override.overrideController`
  - `Aniao_Override.overrideController`

### Base Layer

- `EmptyLocomotion`
  - `EmptyIdle`
  - `EmptyMove`
- `ArmedLocomotion`
  - `ArmedIdle`
  - `ArmedMove`
- `SwitchWeapon`
- `Fire`
- `GetHit`
- `Dead`
- `Skill1`
- `Skill2`
- `Skill3`
- `Ultimate`

第一版如果暂时还没有上下半身分离资源，可以先用全身版本：

- `SwitchWeapon`
- `Fire`
- `Skill1`
- `Skill2`
- `Skill3`
- `Ultimate`

在后续支持边移动边射击后，再把 `Fire` 和部分 `SwitchWeapon` 迁移到上半身层。

### UpperBody Layer

- `UpperIdle`
- `UpperArmedIdle`
- `UpperFire`
- `UpperSwitchWeapon`
- `UpperSkill`（后续可选）

层设置建议：

- `Blending = Override`
- `AvatarMask = UpperBody`

该层只覆盖：

- Spine
- Chest
- Shoulder
- Arm
- Hand

尽量不要覆盖腿部和 Root。

### 过渡规则

- `WeaponPose == 0` 时进入 `EmptyLocomotion`
- `WeaponPose != 0` 时进入 `ArmedLocomotion`
- `MoveSpeed <= 0.1` 播 idle
- `MoveSpeed > 0.1` 播 move
- 任意武装持续态收到 `Fire` 时进入 `Fire`
- 任意状态收到 `SwitchWeapon` 时进入 `SwitchWeapon`
- 任意状态收到 `Skill1` 时进入 `Skill1`
- 任意状态收到 `Skill2` 时进入 `Skill2`
- 任意状态收到 `Skill3` 时进入 `Skill3`
- 任意状态收到 `Ultimate` 时进入 `Ultimate`
- `Fire` 和 `SwitchWeapon` 播放完成后回到当前 locomotion
- `Skill1/Skill2/Skill3/Ultimate` 播放完成后回到当前 locomotion

如果启用上下半身分离，则规则调整为：

- Base Layer 只根据 `MoveSpeed` 和 `WeaponPose` 决定空手/持枪下的待机与移动
- UpperBody Layer 根据 `WeaponPose` 维持持枪上半身姿态
- UpperBody Layer 收到 `Fire` 时进入 `UpperFire`
- UpperBody Layer 收到 `SwitchWeapon` 时进入 `UpperSwitchWeapon`
- 某些可边移动释放的技能可以进入 `UpperSkill`
- `UpperFire` 和 `UpperSwitchWeapon` 播放完成后回到 `UpperArmedIdle`

### 4.3.1 第一版可直接制作的状态机设计

这是当前阶段建议你直接照着制作的 Animator 结构。

#### 参数

- `MoveSpeed : float`
- `HasWeapon : bool`
- `Fire : trigger`
- `SwitchWeapon : trigger`
- `Skill1 : trigger`
- `Skill2 : trigger`
- `Skill3 : trigger`
- `Ultimate : trigger`
- `Dead : bool`
- `GetHit : trigger`

如果你已经开始做不同武器姿态，也可以把 `HasWeapon` 直接升级为：

- `WeaponPose : int`

但第一版为了简单，优先用：

- `HasWeapon`
- `MoveSpeed`

#### Base Layer 建议状态

- `EmptyIdle`
- `EmptyMove`
- `ArmedIdle`
- `ArmedMove`
- `Fire`
- `SwitchWeapon`
- `Skill1`
- `Skill2`
- `Skill3`
- `Ultimate`
- `GetHit`
- `Dead`

#### Base Layer 建议过渡

- `EmptyIdle -> EmptyMove`
  - 条件：`HasWeapon == false`
  - 条件：`MoveSpeed > 0.1`

- `EmptyMove -> EmptyIdle`
  - 条件：`HasWeapon == false`
  - 条件：`MoveSpeed <= 0.1`

- `ArmedIdle -> ArmedMove`
  - 条件：`HasWeapon == true`
  - 条件：`MoveSpeed > 0.1`

- `ArmedMove -> ArmedIdle`
  - 条件：`HasWeapon == true`
  - 条件：`MoveSpeed <= 0.1`

- `EmptyIdle -> ArmedIdle`
  - 条件：`HasWeapon == true`

- `EmptyMove -> ArmedMove`
  - 条件：`HasWeapon == true`

- `ArmedIdle -> EmptyIdle`
  - 条件：`HasWeapon == false`

- `ArmedMove -> EmptyMove`
  - 条件：`HasWeapon == false`

- `Any State -> Fire`
  - 条件：`Fire`
  - 建议只在 `HasWeapon == true` 的角色逻辑里触发

- `Any State -> SwitchWeapon`
  - 条件：`SwitchWeapon`

- `Any State -> Skill1`
  - 条件：`Skill1`

- `Any State -> Skill2`
  - 条件：`Skill2`

- `Any State -> Skill3`
  - 条件：`Skill3`

- `Any State -> Ultimate`
  - 条件：`Ultimate`

- `Any State -> GetHit`
  - 条件：`GetHit`

- `Any State -> Dead`
  - 条件：`Dead == true`

#### 一次性动作回退规则

以下状态全部勾 `Has Exit Time`，播完后自动回退：

- `Fire`
- `SwitchWeapon`
- `Skill1`
- `Skill2`
- `Skill3`
- `Ultimate`
- `GetHit`

回退目标：

- 如果 `HasWeapon == false` 且 `MoveSpeed <= 0.1`，回 `EmptyIdle`
- 如果 `HasWeapon == false` 且 `MoveSpeed > 0.1`，回 `EmptyMove`
- 如果 `HasWeapon == true` 且 `MoveSpeed <= 0.1`，回 `ArmedIdle`
- 如果 `HasWeapon == true` 且 `MoveSpeed > 0.1`，回 `ArmedMove`

### 4.3.2 第二版上下半身分离设计

当你开始支持“边移动边射击”后，建议把状态机升级成下面这种结构。

#### Base Layer

只保留：

- `EmptyIdle`
- `EmptyMove`
- `ArmedIdle`
- `ArmedMove`
- `GetHit`
- `Dead`
- 一部分必须全身播放的技能动作

#### UpperBody Layer

增加：

- `UpperArmedIdle`
- `UpperFire`
- `UpperSwitchWeapon`
- `UpperSkill`

#### 上下半身职责划分

- Base Layer：腿部移动、站立、全身受击、死亡
- UpperBody Layer：持枪姿态、射击、切枪、可边移动释放的技能

#### 哪些技能放 UpperBody

适合放 `UpperBody Layer`：

- 抬手施法
- 单手发射技能
- 边跑边射击技能
- 边移动边丢投掷物

不适合放 `UpperBody Layer`：

- 跳斩
- 突进
- 重击
- 大幅度位移技能
- 明显会影响下半身重心的技能

## 4.4 第一版建议不要过度设计

第一版只做下面这组最小闭环：

1. 空手 Idle / 空手 Move
2. 持武器 Idle / 持武器 Move
3. Fire
4. SwitchWeapon

先把核心闭环跑通，再考虑：

- 上半身开火覆盖
- 瞄准姿态
- 换弹
- 受击打断
- 多武器类型细分

如果你已经明确需要“边移动边射击”，那第一版最小闭环应调整为：

1. Base Layer 支持空手/持武器待机与移动
2. UpperBody Layer 支持持武器待机
3. UpperBody Layer 支持 `Fire`
4. 切枪时至少有一版 `UpperSwitchWeapon`

## 5. Animator 还是 Playable

## 5.1 推荐当前阶段继续使用 Animator

原因如下。

### 5.1.1 当前项目已经围绕 Animator 建好接入口

已有能力：

- Unit 创建后自动接 `AnimatorComponent`
- 移动速度已经通过参数驱动
- BT 系统已有 Animator 操作节点
- 武器切换消息已预留动画接入口

所以当前最短路径是：

- 扩展参数
- 补状态机
- 接消息

而不是重写底层驱动。

### 5.1.2 当前需求本质上是“标准角色状态机”

你的动作集合只有：

- 待机
- 移动
- 射击
- 切枪
- 上下半身分离
- 武器切换后的不同持枪姿态
- 多英雄共用状态机
- 不同英雄覆盖专属技能动作

这是一套非常典型的 Animator 场景。

它不需要 `Playable` 才能解决。

### 5.1.3 当前最主要的风险不是播放，而是资产一致性

你现在真正的风险在这里：

- 动画与角色骨架是否兼容
- 武器姿态是否统一
- 武器切换时模型挂点是否正确
- HeroDisplay 与场景角色是否共用一套表现规则

这些问题用 `Playable` 并不会自动消失。

## 5.2 Playable 适合什么场景

`Playable` 更适合下面几种需求：

- 演出动画
- UI 角色预览自由播片
- 程序化混合多个 clip
- 上半身和下半身复杂叠加
- 不想维护复杂 Animator Controller

如果未来出现以下需求，可以考虑局部引入：

- 多武器类型的上半身独立开火层
- 运行时动态替换大量动作片段
- 英雄预览界面中自由切换任意 clip

## 5.3 为什么当前不建议改成 Playable 主链路

如果现在直接切主链路到 `Playable`，需要额外处理：

- 每个 Unit 的 `PlayableGraph` 生命周期
- 图初始化、销毁和异常恢复
- 一次性动作播完后的回落逻辑
- 与现有 `AnimatorComponent` 的接口统一
- 与移动、BT、武器切换消息的同步
- UI 预览和场景战斗是否共享实现

在当前阶段，这些改造成本明显高于收益。

## 5.4 推荐的中期路线

### 短期

- 战斗主链路继续用 `Animator`

### 中期

- UI 预览角色可以补一个 `Playable` 调试器或试播器

### 后期

- 如果武器动作矩阵变复杂，再演进为
  - `Animator` 负责 locomotion
  - `Playable` 负责局部 one-shot 或上半身叠加

## 6. 具体实现建议

## 6.1 不建议把所有武器动作都塞进 MotionType

当前 `MotionType` 更适合通用动作，例如：

- Idle
- Run
- GetHit
- Dead

不建议继续往里堆下面这种内容：

- RifleIdle
- RifleMove
- RifleFire
- ShotgunIdle
- ShotgunMove
- ShotgunFire

这样会导致：

- 枚举膨胀
- 参数命名和资源命名失控
- 武器类型一多就难维护

## 6.2 推荐新增动画参数层，而不是新增大量 MotionType

建议新增 Animator 参数：

- `HasWeapon: bool`
- `WeaponPose: int`
- `Fire: trigger`
- `SwitchWeapon: trigger`
- `Skill1: trigger`
- `Skill2: trigger`
- `Skill3: trigger`
- `Ultimate: trigger`
- `GetHit: trigger`
- `Dead: bool`

`MoveSpeed` 可以继续复用现有参数。

第一版如果想先简单落地，可以只用：

- `MoveSpeed`
- `HasWeapon`
- `Fire`
- `SwitchWeapon`

第二版再升级到：

- `WeaponPose`
- `Skill1/Skill2/Skill3/Ultimate`

## 6.3 推荐增加一个轻量的客户端动画门面

建议新增一个专门负责角色动画语义的客户端组件或 Helper，例如：

- `UnitAnimationComponent`
- 或 `UnitAnimationHelper`

职责只做一件事：

- 把“游戏语义”翻译成 Animator 参数

建议提供的接口：

- `SetWeaponPose(unit, poseType)`
- `SetHasWeapon(unit, hasWeapon)`
- `PlayFire(unit)`
- `PlaySwitchWeapon(unit)`
- `PlaySkill(unit, slotType)`
- `SyncMoveSpeed(unit, speed)`
- `AttachWeaponModel(unit, weaponId)`
- `DetachWeaponModel(unit)`
- `GetCurrentMuzzle(unit)`

这样有几个好处：

- 武器消息处理器不直接写一堆 Animator 参数细节
- 后续若切到混合 Animator + Playable，实现层可以替换
- HeroDisplay 若要共用同一套语义，也更容易复用

## 6.4 建议的接入点

### 移动

继续沿用当前 `MoveSpeed` 驱动。

### 武器切换

在 `M2C_SwitchWeaponHandler` 中补：

1. 根据 `message.WeaponId` 切换手持武器模型
2. 第一版先设置 `HasWeapon = true`
3. 第二版按武器类型设置 `WeaponPose`
4. 触发 `SwitchWeapon`

### 射击

在 `M2C_WeaponFireHandler` 中：

1. 找到 `caster`
2. 触发 `Fire`
3. 从当前武器模型读取枪口挂点
4. 再创建投射物或枪口特效

注意：

- 射击动画必须由开火事件驱动，而不是只靠本地输入驱动。
- 这样观战、他人角色和自己的角色都能统一表现。

### 技能播放

不同角色释放不同技能动作时，不建议：

- 为每个角色单独做一整套状态机
- 为每个技能直接硬编码一个动画名

建议做法：

1. 技能系统只决定触发哪个“动作槽位”
2. 动画层只关心 `Skill1/Skill2/Skill3/Ultimate`
3. 不同角色通过 `AnimatorOverrideController` 覆盖这些状态里的 clip

示例：

- 英雄 A 的 `Skill1` 状态播放 `Agou_Skill1.anim`
- 英雄 B 的 `Skill1` 状态播放 `Ayin_Skill1.anim`
- 但 Animator 参数仍然统一触发 `Skill1`

这样能保证：

- 技能逻辑统一
- 状态机结构统一
- 角色差异通过资源覆盖实现

### 武器模型挂载

建议新增独立的武器表现组件，例如：

- `WeaponViewComponent`

该组件只负责客户端表现，不负责数值逻辑。

建议数据包括：

- 当前武器模型实例
- 槽位 1 武器模型缓存
- 槽位 2 武器模型缓存
- 当前枪口挂点
- 当前左右手挂点

切枪流程建议：

1. 根据 `WeaponId` 查询武器表现配置
2. 如缓存中没有，则异步加载对应武器 prefab
3. 卸下或隐藏旧武器模型
4. 将新武器模型挂到角色手部骨骼
5. 刷新 `WeaponPose`
6. 触发 `SwitchWeapon`

优化建议：

- 本地玩家：预加载两个槽位武器模型，切换时直接显隐
- 其他玩家：只保留当前武器模型，切换时再替换

### 武器表现配置建议

不建议在消息处理器里直接写：

- 哪把枪加载哪个 prefab
- 哪把枪用哪个挂点
- 哪把枪用哪套持枪姿态

建议配置化，优先放在武器相关配置中，或者新增客户端武器表现配置。

建议字段至少包括：

- `WeaponViewPrefab`
- `WeaponPoseType`
- `RightHandBindPoint`
- `LeftHandBindPoint`
- `MuzzleBindPoint`
- `HolsterBindPoint`

这样可以保证：

- 武器模型可替换
- 动画姿态可复用
- 枪口特效位置统一从配置和挂点读取

## 6.5 武器类型与动画姿态的关系

建议先引入“武器姿态类型”，而不是“每把武器一个动画类型”。

例如：

- `None`
- `OneHandGun`
- `TwoHandGun`
- `HeavyGun`

然后由 `WeaponConfig` 配一个姿态类型字段。

运行时流程：

- 切武器时读取武器配置
- 得到姿态类型
- 设置 `WeaponPose`

这样后续新增武器时只要归类到姿态类型，不需要每次重做整套状态机。

这一步的核心思想是：

- 武器模型可以一把枪一个 prefab
- 但动画姿态不要一把枪一套状态机
- 动画应当按“姿态类型”复用

否则武器数量一多，动画状态机会迅速失控。

### 6.5.1 共用状态机与角色覆盖策略

如果多个角色骨架兼容，建议：

- 全部共用 `HeroBase.controller`

不同角色的差异通过两种方式处理：

1. 不同 Avatar
2. 不同 `AnimatorOverrideController`

推荐职责划分：

- `HeroBase.controller`
  - 定义所有参数
  - 定义所有状态
  - 定义所有过渡

- `Ayin_Override.overrideController`
  - 覆盖 `EmptyIdle`
  - 覆盖 `EmptyMove`
  - 覆盖 `ArmedIdle`
  - 覆盖 `ArmedMove`
  - 覆盖 `Skill1`
  - 覆盖 `Skill2`
  - 覆盖 `Skill3`
  - 覆盖 `Ultimate`

这样即使后续新增英雄，也不需要复制一份新的状态机结构。

## 7. 动画资源没有绑定骨骼，应该怎么处理

这个问题必须先区分资源状态，否则很容易误判。

## 7.1 情况一：角色模型有骨骼，动画也有骨骼，但不是同一套骨架

这是最理想的情况。

处理方式：

1. 角色模型 FBX 设置为 `Rig = Humanoid`
2. 角色模型 `Avatar Definition = Create From This Model`
3. 动画 FBX 设置为 `Rig = Humanoid`
4. 动画 FBX `Avatar Definition = Copy From Other Avatar`
5. 指向角色模型的 Avatar

这样 Unity 会进行 Humanoid Retarget。

如果你的英雄是标准人形，优先走这条路线。

## 7.2 情况二：角色模型没有蒙皮或没有骨骼绑定

这种情况下，Unity 不能直接“自动让动画生效”。

你需要先在 DCC 工具里完成角色绑定：

- Blender
- Maya
- 3ds Max
- Mixamo
- AccuRig

流程是：

1. 给角色建立骨架
2. 蒙皮
3. 调整权重
4. 导出带骨骼和蒙皮的角色 FBX
5. 再回 Unity 设置 Humanoid 或 Generic

## 7.3 情况三：动画资源本身没有骨骼动画数据

如果动画资源只是：

- 纯模型文件
- 没有骨骼曲线
- 没有正确导出的动画轨道

那么 Unity 内部无法直接修复。

必须：

- 回源文件重新导出
- 或在 DCC 工具里重做绑定与动画导出

## 7.4 推荐绑定路线

如果你的英雄是人形，建议优先统一成 `Humanoid`。

优点：

- 动画复用成本低
- 多英雄复用动作方便
- UI 预览和场景角色更容易共享动画
- 后续做武器姿态扩展更稳

只有当以下情况出现时，再考虑 `Generic`：

- 骨骼结构不是标准人形
- 需要完全保留原始骨骼动画
- 某些特殊骨骼部位不能走 Humanoid 重定向

## 7.5 具体导入检查清单

在 Unity 导入时，至少检查以下内容：

### 角色模型

- `Animation Type` 是否为 `Humanoid`
- `Avatar` 是否成功生成
- `Configure Avatar` 是否全部绿色
- 根骨骼朝向是否正确
- 手掌朝向是否正确

### 动画资源

- `Animation Type` 是否与角色一致
- 是否能正确预览到角色上
- Root Motion 是否关闭或按项目规则处理
- 循环动画是否勾选 `Loop Time`
- 切枪、射击这类 one-shot 动画不要勾无限循环

### 挂点

- 武器挂点是否存在
- 枪口挂点是否存在
- 投射物发射位置是否正确
- 左右手持握位置是否正确
- 武器切换后枪口挂点是否同步切换
- 上半身层播放时武器是否仍然稳定跟手

## 8. 第一阶段落地建议

建议按下面顺序做，避免一次做太大。

### 第一步：整理骨骼和动画导入

目标：

- 让角色模型和已有动作能在 Unity 预览面板里正常播放

交付标准：

- 空手 Idle 正常
- 空手 Move 正常
- 持武器 Idle 正常
- 持武器 Move 正常
- Fire 正常
- SwitchWeapon 正常

### 第二步：建立最小 Animator Controller

目标：

- 单角色单控制器跑通

参数只保留：

- `MoveSpeed`
- `WeaponPose`
- `Fire`
- `SwitchWeapon`

如果明确需要边移动边射击，则这一步要直接升级为：

- 一个 Base Layer
- 一个 UpperBody Layer
- 一个 `UpperBody AvatarMask`

建议第一版的实际制作顺序：

1. 先做 `HeroBase.controller`
2. 先只放 4 个基础状态：
   - `EmptyIdle`
   - `EmptyMove`
   - `ArmedIdle`
   - `ArmedMove`
3. 参数先只保留：
   - `MoveSpeed`
   - `HasWeapon`
4. 跑通后再加：
   - `Fire`
   - `SwitchWeapon`
   - `Skill1/Skill2/Skill3/Ultimate`

### 第三步：接客户端消息

目标：

- 切枪时表现正确
- 开火时表现正确

接入点：

- `M2C_SwitchWeaponHandler`
- `M2C_WeaponFireHandler`

### 第四步：接武器模型挂点

目标：

- 手上的武器模型与动画姿态一致
- 枪口特效从当前武器模型真实枪口发出
- 边移动边射击时武器不漂移

### 第五步：再考虑高级扩展

包括：

- 上半身开火覆盖
- 瞄准层
- 换弹动画
- 受击打断
- 不同武器姿态细分

## 9. 风险评估

## 9.1 当前最主要风险

不是代码，而是资源一致性。

高风险项：

- 动画与角色骨架不兼容
- 武器模型挂点不统一
- 开火动画长度与实际攻击间隔不一致
- 切枪动画期间是否允许开火未定义
- 上半身动画覆盖时，武器模型手部跟随不稳定
- 不同武器模型尺寸差异过大，导致持握位置偏差明显

## 9.2 工程实现风险

中风险项：

- 直接在多个消息处理器里散写 Animator 参数，后期会难维护
- 继续把武器语义全塞进 `MotionType`，后期会膨胀
- 每个角色复制一份独立状态机，后期难同步维护
- 技能动画直接写死具体 clip 名，后期难替换

## 9.3 当前最优策略

先把以下三件事做对：

1. 骨骼绑定与导入规则统一
2. Animator 参数和状态机统一
3. 武器消息与动画消息统一

做完这三件事，再讨论更复杂的混合系统。

## 10. 最终建议

最终建议如下：

### 方案选择

- 当前阶段：使用 `Animator`
- UI 预览调试：后续可补 `Playable`
- 中后期复杂混合：再考虑 `Animator + Playable`

### 状态设计

- 持续态：空手/持武器 Idle 与 Move
- 一次性动作：Fire、SwitchWeapon
- 分层策略：下半身负责移动，上半身负责持枪、射击、切枪
- 技能策略：基础状态机统一，专属技能动作通过 OverrideController 覆盖

### 参数建议

- `MoveSpeed`
- `HasWeapon`
- `WeaponPose`
- `Fire`
- `SwitchWeapon`
- `Skill1`
- `Skill2`
- `Skill3`
- `Ultimate`
- `GetHit`
- `Dead`

### 资源导入建议

- 人形角色优先走 `Humanoid`
- 动画优先做 Avatar Retarget
- 没有骨骼或没有蒙皮时，先去 DCC 工具补绑定
- 上下半身分离前先准备好 `UpperBody AvatarMask`

### 落地顺序

1. 先绑骨并导入成功
2. 先做 `HeroBase.controller` 的最小 4 状态版本
3. 再做 Base Layer + UpperBody Layer 的升级版
4. 再补武器模型挂点与武器表现配置
5. 再接切枪、开火、技能消息
6. 最后再做高级扩展
